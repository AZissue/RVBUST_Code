## 2. `normalizePose()` 完整实现 + 用到的 SDK API

```cpp
bool normalizePose(const double raw[6], bool rawIsMillimeter, bool rawIsDegree,
                   RobotPose::Pose& out)
{
    if (raw == nullptr)
        return false;
    for (int i = 0; i < 6; ++i) {
        if (!std::isfinite(raw[i]))
            return false;
    }

    const double lengthScale = rawIsMillimeter ? 1.0 : 1000.0;
    const double angleScale = rawIsDegree ? 1.0 : kDegPerRad;   // kDegPerRad = 180/pi

    RobotPose::Pose pose;
    for (int i = 0; i < 3; ++i) {
        const double mm = raw[i] * lengthScale;
        if (!std::isfinite(mm))
            return false;
        pose.xyz[static_cast<std::size_t>(i)] = mm;
    }
    for (int i = 0; i < 3; ++i) {
        const double deg = raw[3 + i] * angleScale;
        if (!std::isfinite(deg))
            return false;
        pose.rpy[static_cast<std::size_t>(i)] = deg;
    }

    // 转换全部成功后才写 out（失败路径不改 out）。
    out = pose;
    return true;
}
```

约定：`raw[0..2]` = x/y/z（长度），`raw[3..5]` = a/b/c（姿态）；
非 mm 时 ×1000，非度时 ×180/π；**不做任何轴序交换**（见第 3 节）；任一输入非有限值、
或换算后溢出成 inf 都返回 false 且 `out` 一个字节都不动。

用到的 SDK 读位姿 API（`third_party/EfortSDK/include/EfortSdk.h` 原文，行号 40/41/208）：

```cpp
ROBOTAPI_API int ConnectRobot(const std::string robot_addr, unsigned int& devId, const bool reConnectFlag = false, const bool debugFlag = false);
ROBOTAPI_API void DisconnectRobot(unsigned int& devId);
ROBOTAPI_API int GetBaseCoordinatePos(RobotPos& value, unsigned int devId = 0);
```

（`BaseController.h:201` 同一接口的注释原文：`// 获取机器人基坐标下的TCP数据，不带CFG参数`。）
`RobotPos` 定义在 `SdkStructDef.h:23`：`double x; double y; double z; double a; double b; double c;`
（其后还有 ej1..ej6 与 cfgx/cfg1/cfg4/cfg6，本适配器不用）。

`readPose()` 里 `RobotAPI::RobotPos pos; RobotAPI::GetBaseCoordinatePos(pos, m_devId);`
成功后 `const double raw[6] = { pos.x, pos.y, pos.z, pos.a, pos.b, pos.c };` 再交给 `normalizePose(raw, true, true, out)`；
读取失败时按返回码映射（`statusFromSdkCode`）：
`ERROR_CONNECT_FAILED(1)/ERROR_NO_CONNECTION(2)/ERROR_CONNECTION_BROKEN(3) → NotConnected`、
`ERROR_THIRD_OPERATION_TIME_OUT(10024) → Timeout`、
`ERROR_ACCESS_REJECTED(4)/ERROR_PARA_INVALID(14)/ERROR_DEVICE_NOT_EXIST(10022)/ERROR_DEVICE_EXIT(10021) → ConfigError`、
其余 → `ProtocolError`；未连接时直接返回 `NotConnected`（不碰 SDK）。返回码与中文都进 `lastError()`。

## 3. 判据 7 — 埃夫特位姿的欧拉角约定：**未确认**

- **结论：未确认。** SDK 目录里只有 `include/`、`lib/`、`bin/`，没有文档 / 头文件注释说明 `RobotPos.a/b/c`
  的旋转顺序与单位；我在全部头文件里 grep 过 `euler / Euler / 欧拉 / ZYX / zyx / 姿态`，没有任何命中，
  唯一相关注释是 `BaseController.h:201` 那句「获取机器人基坐标下的TCP数据，不带CFG参数」（只说明是基坐标下的 TCP，不说角序）。
  没有真机（用户已确认），所以**无法**用一次读数验证。
- **本轮的实现选择**：`normalizePose()` 对 a/b/c 做**恒等映射**（`rpy = {a, b, c}`，只换单位），
  即按「控制器报的就是项目约定的静态 XYZ、R = Rz·Ry·Rx 的三个分量」理解。
  代码里 `readPose()` 调 `normalizePose(raw, true, true, out)`，也就是把 SDK 的数值当成 mm + 度。
  这两个假设都写进了 `EfortPoseReader.h` / `.cpp` 的注释，标注为「未经真机确认」。
- **为什么没有做 FANUC 那样的反序处理**：项目里 FANUC WPR 的坑是「顺序反了」，
  而 FANUC 的坑是**已知**并被记录的；埃夫特这边连"是不是 ZYX"都没有依据，凭猜做交换风险更大
  （猜错 = 静默给出错误姿态，猜对也只是巧合）。所以选择恒等 + 显式声明未确认，
  而不是照 FANUC 的先例反着摆。
- **真机确认时的检查办法**（交给用户/Codex）：让机器人单轴单独旋转——
  (a) 只让末端绕基座 Z 转 +30°，若 `c` 变化而 `a` 不变 → 记为 (a,b,c) = (Rx,Ry,Rz)，恒等映射正确；
  若 `a` 变化而 `c` 不变 → EFORT 报的是反向序 (Rz,Ry,Rx)，此时应在 `normalizePose()` 里把
  `rpy = {raw[5], raw[4], raw[3]}`（并确认符号方向）而不是现在的 `{raw[3], raw[4], raw[5]}`。
  (b) 同时看一段已知长度的位移，确认 x/y/z 是 mm（不是 m）——若不是 mm，把 `readPose()` 里的
  第二个实参改成 `false` 即可，`normalizePose` 本身已经支持两种单位。
- **单位同理未确认**：`RobotPos` 的 x/y/z 我按 mm 传（`rawIsMillimeter = true`），
  依据是 EFORT 示教器通常以 mm/度 显示，但这同样**不是**从 SDK 文档得到的，属未确认项。

## 5. 不确定点

- **欧拉角顺序 / 单位未确认**（详见第 3 节）——这是本轮最大的不确定项，恒等映射是"按项目约定直读"的
  保守选择，真机一验就可能要改成反序，改动只在 `normalizePose()` 一处。
- **`ConnectRobot` 的地址串格式未确认**：头文件只写 `const std::string robot_addr`，没说要不要端口、
  也没给默认端口，SDK 里找不到任何端口常量（`grep port` 只有 UDP/实时数据的自建 socket）。
  我的实现：host 里带 `:` 就原样传；否则 `port != 0` 时拼成 `"host:port"`，`port == 0` 就只传 IP；
  UI 在埃夫特协议下把端口框**隐藏**并传 0，所以默认发出去的就是纯 IP。
  如果真机需要 `"ip:端口"`，用户目前**没法在界面上填端口**（这是这一处取舍的副作用），
  届时要么把隐藏那行去掉、要么把默认端口改成实测值——都只改 `updateProtocolFields` 一行。
- **`ERROR_ACCESS_REJECTED(4)` 我归到 `ConfigError`**（控制器不允许 API 访问，属配置问题而非协议错），
  `ProtocolError` 因此只兜底代码里没列举的那些码。这是判断，不是 SDK 的明示。
- **`__declspec(dllexport)` 的导入库链接**：`EfortSdk.h` 对 `_MSC_VER` 无条件 dllexport（没做
  `BUILDING` 宏切换），所以我们的 exe 会对这一百多个函数产生导出项。本轮实测链接通过（退出码 0），
  但这是我事前最担心的点，已记录；若将来换 SDK 版本出现 `LNK2001`，第一嫌疑就是头/库版本不一致。
- **`EfortSdk.h` 顶部有 `using namespace std;`**：因为只在 `EfortPoseReader.cpp` 里包含，
  污染面被限制在这一个编译单元（这里也是我特意把 `normalizePose` 的声明放在不含 SDK 的头文件里的原因）。
  如果 Codex 的单测把 `EfortPoseReader.cpp` 加进 `tests/`，需要给 `unit_tests` 目标补
  `EfortSDK::EfortSDK`（include 目录随之而来）——`tests/` 我一个字没动。
- **没有真机**：所有 SDK 调用只做了编译与静态走查，连接/读位姿的实际返回值、`devId` 语义、
  `DisconnectRobot` 之后能否重连都**未经验证**；「模拟连接成功」路径也只覆盖 UI，不经过 SDK。
- `m_robotPort->setVisible(false)` 是按协议动态显隐的：切回 Modbus/UR/博纳斯 会恢复显示，
  但埃夫特协议下那个 spin 里仍留着上一次的数值（0 被 range 夹成 1），只是不参与连接。
  由于 `protocol == 3` 时 emit 的是常量 0，这个残留值不会影响任何行为。
