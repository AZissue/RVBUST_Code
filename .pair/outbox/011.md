# 011 交回 — 调用 EfortSDK 前把 CWD 切到 exe 目录，调用完立刻还原

## 1. 改动点（哪个函数、怎么保证异常时也还原）

只改 **1 个文件**：`src/logic/EfortPoseReader.cpp`。新增 1 个文件内 RAII 类 + 3 处使用点；
`EfortPoseReader.h`、`MainWindow`、`ToolsPanel`、`run.bat`、`src/CMakeLists.txt`（010 的
`log4cpp.conf` 部署保留原样）、`tests/` 都没动。009 的 try/catch 结构一字未改，CWD 切换是加在
每个 try **内部**、紧贴 SDK 调用的。

**(a) 匿名命名空间新增 `ScopedWorkingDir`**（RAII，构造时切、析构时还原）：

```cpp
class ScopedWorkingDir {
public:
    ScopedWorkingDir()
        : m_previous(QDir::currentPath())
    {
        const QString exeDir = QCoreApplication::applicationDirPath();
        if (!exeDir.isEmpty() && exeDir != m_previous)
            QDir::setCurrent(exeDir);
    }

    ~ScopedWorkingDir()
    {
        // 还原到进入前的原值；setCurrent 不抛异常，析构因此是 noexcept 的。
        if (m_previous.isEmpty() || QDir::currentPath() == m_previous)
            return;
        QDir::setCurrent(m_previous);
    }

    ScopedWorkingDir(const ScopedWorkingDir&) = delete;
    ScopedWorkingDir& operator=(const ScopedWorkingDir&) = delete;

private:
    QString m_previous;
};
```

另加 `#include <QCoreApplication>`、`#include <QDir>`。

**(b) 三个使用点**（每处都是 `const ScopedWorkingDir cwdGuard;` 紧贴在 SDK 调用之前，
且**在 try 块内部**）：

| 函数 | 位置 | 调用 |
| --- | --- | --- |
| `EfortReader::connect()` | try 块内，`toStdString()` 之后 | `RobotAPI::ConnectRobot(addr, devId)` |
| `EfortReader::readPose()` | try 块内 | `RobotAPI::GetBaseCoordinatePos(pos, m_devId)` |
| `EfortReader::disconnect()` | try 块内 | `RobotAPI::DisconnectRobot(devId)` |

**异常时为什么也还原**：`cwdGuard` 声明在 try 的复合语句里，作用域在 catch **之前**结束——
所以正常返回、提前 `return false`、以及 SDK 抛异常展开栈这三种情况，析构函数都在进入
catch 处理器之前被调用，路径一定还原。析构里只调 `QDir::currentPath()/setCurrent()`（都不抛），
所以还原路径自身不会再抛（否则异常展开期间抛异常会直接 terminate）。
`m_previous` 为空（极罕见）或当前已经等于原值时直接返回，不做多余切换。

**只影响埃夫特链路**：切换只在这三个调用的动态范围内有效；`MainWindow`/`run.bat`/程序别处
没有任何 `setCurrent`，全局 CWD 在连接前后应保持不变（判据 3）。

## 3. 不确定点

- **SDK 是否还依赖别的相对路径文件/目录**：本轮只对齐了 CWD（`log4cpp.conf` 已在 010 部署到
  exe 旁边）。如果 SDK 连接时还会去找别的相对路径文件（例如 log4cpp.conf 里 `appender` 指定的
  **日志输出目录/文件**），在 CWD = exe 目录的前提下它会落在 `build/src/Release/` 下——
  写权限通常没问题，但若配置里指向的是不存在的子目录，仍可能抛 `ConfigureFailure` 一类的异常。
  真机验证时如果报错不再是 "File log4cpp.conf does not exist" 而是别的文件/路径类异常，
  下一个怀疑对象就是 log4cpp.conf 的内容（本轮任务书明确"不调 log4cpp 配置内容"，我没读没改）。
- **CWD 切换的是进程级状态**：这三个 SDK 调用期间，同一进程里其它线程（Qt 的 GUI 主线程、
  QtConcurrent 的 worker、相机/日志线程）若同时做相对路径操作，会短暂看到 exe 目录。
  这些调用都是**同步阻塞**、在 GUI 线程里、时间窗极短，且程序自身没有别的相对路径依赖
  （运行日志用绝对路径），所以判断为安全；但严格说这是"进程级副作用"，如果以后有别的模块
  在后台按相对路径写文件，需要改成 SDK 的 `SetLogPath`（`EfortSdk.h:36`）这类不带全局状态的方案。
- **`QDir::setCurrent` 失败时不报错**：若 exe 目录不可访问或原目录已被删除，切换/还原会静默
  失败（函数返回 bool，我没检查）。这种情况下 SDK 报的还是 "File log4cpp.conf does not exist"，
  与现在的行为一致，不会更糟；要不要把失败也写进 `lastError()` 留给 Codex 定。
- **判据 3（CWD 前后不变）我无法自证**：这里不能启动 GUI，只能从代码上保证"记录原值 → 无条件
  还原"。真机请用启动日志里的 `cwd:` 行核对；另外注意：如果程序在连接**之后**又因为别的原因
  改了 CWD，那是别处的行为，不在这条链路里。
- **`QCoreApplication::applicationDirPath()`**：返回 exe 所在目录（不带尾部分隔符）；
  绿色版/快捷方式/不同 cwd 启动都一样。若以后打包成带子目录的结构（exe 与 dll 分层），
  这个值仍是 exe 目录，与 010 的部署位置（`$<TARGET_FILE_DIR:...>`）一致。
- 真机验收（判据 2/4）由 Codex 做：本轮的判断依据全部来自代码与 009/010 的实测日志，
  我没有埃夫特真机，也没有启动过 GUI。
