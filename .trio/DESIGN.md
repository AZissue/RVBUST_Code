# 设计决策记录

这份文件回答"**为什么这么做**"。操作规程在 `PROTOCOL.md`，角色定义在 `roles/`。

## 1. 命题

人只跟 A 交互；A 理解需求、出解决方案、驱动 B、独立验收；B 只实现。
听起来和上一版（`.pair/`）一样——**但上一版的症结不在角色划分，在架构。**

## 2. 症结诊断

上一版是**单轮 headless 驱动**：A 写任务书 → 起一个 B 进程 → **等它跑完** → A 才拿到结果。

于是：**B 执行期间，A 是瞎的、聋的、无权的。**

所以"B 自写自测、陷入死循环、钱烧掉了"不是纪律问题——`PROMPT.md` 里明明白白写着
"禁止自写自测、禁止长自主循环"，它照样发生了。**规则写在提示词里，后门写死在白名单里。**

A 只能事后从 `outbox` 读到 B 的一面之词，而钱已经烧完了。

**结论**：要动的是架构——把 A 从"发单员"变成"监工"。这也解释了"工作群"这个隐喻
为什么是对的：群的本质不是聊天，是**同一条可观察、可介入的时间轴**。

## 4. 关键论证（值得单独记住的几条）

### 4.1 红线：一个懒惰的 A 也必须被机制兜住

判据：**如果一个"懒惰的 A"照样能让系统跑起来并烧钱，那这套架构就没修好。**

所以机械闸在**路由器**里，不在 A 里。A 睡着的时候它照样工作。

而上一版把"不要自写自测"写进提示词——那是**纪律**，不是**边界**。
判一份角色文件有没有用，看这一条：**把它删掉，系统还拦不拦得住越界？**

### 4.2 掐断要分两层，因为 A 是回合制的

A 睡觉的时候掐不了。所以：

- **机械闸**（路由器）：同一命令重复 ≥3 / 连续无写入 / 事件量堆积 / 墙钟 / 花费
  → **立刻 `stop`，并往群里发事件唤醒 A**。不用模型，不会被说服，不会疲劳。
- **判断闸**（A）：回灌 / 换策略 / 升级给人。

### 4.3 用「事件量」量烧钱，不用「工具调用次数」

对上一版那轮烧掉钱的日志（`.pair/logs/turn-001.stream.jsonl`）做回放：

```
22620 个事件，只有 12 次工具调用
```

**动作数看上去很"老实"，事件量才是花掉的钱。** 所以闸门加了以事件量为基准的一对
（软告警 2000 / 硬掐断 8000），并且**在真实历史日志上验证过**：

| 日志 | 结果 |
|---|---|
| `turn-001`（烧钱那轮） | 软告警 @2000 事件，**硬掐断 @8000 事件**（只到原轮次的约 1/3） |
| `turn-102`（成功轮） | **不触发**（988 事件） |
| `turn-103`（成功轮） | **不触发**（428 事件） |

零花费、可复现：`python .trio/router.py replay --stream .pair/logs/turn-001.stream.jsonl`

### 4.4 软告警的存在理由

一刀切会误杀：稍大的任务本来就需要先读一批文件再动手。
所以两级：**软告警不掐断**，只往群里发一条 `SYSTEM/note`——这是 A 在烧完之前介入的机会。

### 4.5 B 的边界做三重，因为单靠任何一层都会漏

1. **工具白名单**（机制）——`python -c` 已拆掉
2. **工作集**（任务书声明，越界即失败）——同时治耦合、治上下文预算、治 A 的验收带宽
3. **总线权限矩阵**（`bus.PERMISSIONS`）——B 发不出 `verify`/`escalate`/`task`/`kill`；
   `as.py` 不接受 `--role`，冒充 A 在机制上不可能

## 5. 为什么 A 是 Codex

原本的直觉理由是"Codex 能操控电脑、能截图、你能给它发图"。核实之后理由更硬：

- `codex.exe` 0.155.0-alpha.9.2 有 `exec`（非交互）、`exec resume <会话>`、
  **`queue --thread <会话> --message <文本>`（向正在跑的会话注入消息）**、
  `app-server daemon`（常驻本地服务）、`-i/--image`（程序化喂图）、
  `--sandbox` / `--approve-for-me`（权限模型）、`--worktree`。
- 更重要的是**异源**：A 和 B 是两个不同厂家的模型，互查才有意义。
- B 侧需要的东西 Claude Code 恰好独有：`--max-budget-usd`（回合内花费硬中止）、
  `--bg` / `attach` / `logs` / `stop`（长驻会话 + 取日志 + 掐断）、
  `--input-format stream-json`（实时注入）。**把成本硬闸装在烧钱的那一侧。**

## 6. 这套框架"成了"的标准

拿贪吃蛇跑**一个含真机项的真实需求**（GUI / 音频这种只能在真机上验的），四条同时满足：

1. 人 **0 次人工中转**（没帮 A 往 B 那儿传过一句话）
2. 死循环被**自动**掐断，且人**在群里看得到掐断原因**——
   注意"看得到"是指**人真的看到了**，不是"消息被写进了日志"。界面没开就是没看到（见 §8.3）
3. 真实花费 **≤ ¥3**
4. A 交的证据人能**独立复现**（命令 + 原始输出）

任何一条不满足，就是架构还没修好。

**注意**：贪吃蛇能**证伪**（抓出致命缺陷），不能**证实**（证明大项目上成立）。
上下文预算、耦合、拆解粒度这三类问题只在"超出单个上下文窗口的代码库"里暴露，
所以 §8 的四条大项目对策在 v1 就写进去了。

## 7. 已知边界与未验证前提

见 `PROTOCOL.md` §11（待验证前提）与 §12（已知软边界）。最要紧的一条：

**~~`codex queue` 能否投进正在跑的会话，尚未实测。~~**
**2026-09-23 实测：能**——投出去的那条自测消息真的出现在 A 的会话里，队列里那条也随之被消费。
于是 A 的唤醒不再依赖人敲回车：B 的 `deliver` 与机械闸触发会经 `bus.post` 自动叫醒 A
（接线与证据见 `PROTOCOL.md` §11）。

## 8. 设计过程中的两次自我修正（留档，因为方法比结论重要）

1. **第一次**：我推断"白名单里一定放着跑测试的命令"。核实后**错了**——
   默认白名单是 `Read,Glob,Grep,Edit,Write,Bash(python -c *),Bash(python -m py_compile *)`，
   没有测试命令，而且三轮的 `permission_denials` 都是空的。但结论方向没变：
   `Bash(python -c *)` 是一把**万能钥匙**，比"明着放测试命令"更隐蔽。
2. **第二次**：我断言"Codex 没有可编程 CLI"。核实后**错了**——我只查了 `which codex`
   （不在 PATH），而真正的二进制在 `~/AppData/Local/OpenAI/Codex/bin/<hash>/codex.exe`。
   这条修正直接推翻了"A 只能是 Claude Code"的结论。

教训：**探针下钻得不够深，就会拿不完整的证据下结论。**
这也是为什么 §6 第 4 条要求"证据能被人独立复现"——包括 A 的证据，也包括我的。

3. **第三次（2026-09-22，被人在真机上撞出来）**：`.trio/` 全部建完、29 条自测全绿、
   三份历史日志回放全对、七个接口实测全通——**然后人在 Codex 上跑了一整轮，什么也没看见。**
   群里其实有 30 条消息、4 个任务、机械闸真的掐断过一次、A 真的回灌了、真提交了 3 个 commit、
   花了 ¥1.01；**人一条都没看到，因为端口上没有任何听众。**

   根因不是界面坏了（我用真实数据测过，30 条渲染正常），是两个我自己犯的错：

   - **我把"建好了"当成了"会开"。** `KICKOFF.md` 里写的是「双击 `start.cmd`（我会自己开，
     你不用碰浏览器）」——我把开界面这件事推回给人，还明确让 A 别碰。结果谁也没开。
     这跟上一版的病**是同一个**：上一版是"不要自写自测"写在提示词里、后门写死在白名单里；
     这次是"界面在这儿"写在一句注释里。**判据还是那一句：把它删掉，机制还拦不拦得住？**
   - **我的自检全是组件级的。** 29 条单测、3 份回放、7 个接口——没有一条测的是
     **"人打开浏览器能不能看见东西"**，而那恰恰是当初问"用什么看"那个问题的全部理由。

   修法照着红线来：**开界面这件事不能指望谁的记性，得由 router 自己保证**——
   每次 `drive` 前 `ensure_group_ui()`，没跑就起一个并开浏览器。另外补了一条
   **真渲染测试**（`.trio/tests/page_render.mjs`）：把页面那段 JS 真跑一遍，
   喂进真实形状的数据，再看 DOM 上出现了什么。**人这一侧从此有测试。**

   顺带被 A 抓出来的两个真 bug：session id 用了 `uuid4().hex`（claude CLI 拒绝，
   第一次 drive 直接 exit=1），以及成本闸 `spent_task` 拿的是会话总额（等于半睡着）。
   两条都不是设计问题，是**我写完没在真机上跑过一次**。

   教训：**组件全绿不等于系统能用。绿灯要照到人身上，才算数。**

4. **第四次（2026-09-23，A 在真跑需求 1 时撞出来）**：`cost-session` 那道「单会话 ¥3」的闸，
   量错了对象——`spend.json` 的 `start_balance` **只在第一次 drive 时写一次、之后永不重置**，
   于是它量的是"自那天起账户余额掉了多少"。而余额是**账户级**的：本机任何 DeepSeek 用量
   （人在别的项目里跑 Claude Code）都会算进来。结果同一天咬了两次：

   - 第一次：A 起 T-005，B **0 个动作、¥0.00**，闸报「本会话真实花费 ¥3.85 > ¥3.00」直接掐断；
   - A 把基线重置成当前余额（旧基线留档）后接着干，五轮交付跑完再起 T-006，
     同样的假阳性又来一次：**¥4.30 > ¥3.00**，B 又是 0 动作。

   修法照着红线来：**闸门测的量必须是它声称测的那个量**。现在
   「一轮需求」= 同一任务的全部 drive（含回灌）累计，**换任务自动重开基线**，旧基线进
   `history`；外加 `drive --reset-session` 作为显式逃生口。同时把「余额是账户级的、
   这道闸会误杀」写进 `PROTOCOL.md` §5——**已知会误杀的闸要写在明面上，不能装作它准**。

   教训：**闸门本身也要有判据。**「这道闸量的是什么、它会不会误杀、误杀了怎么办」
   三个问题答不上来，那它不是闸，是随机停机的理由。
