## 1. 为什么回来

A 在复核 `read()` 时发现：你按**声明类型**解码 x/y/z 这件事做对了，但同一个函数里
还有一条**同类的"静默错值"路径**没堵上 ——

```cpp
} else if (token == "property") {
    if (inVertex) {
        ...
        p.size = detail::typeSize(type);      // int64 / uint64 / long / ulong … → 0
        if (p.size > 0) vertexProps.push_back(p);   // ← 认不出来的属性被**悄悄丢掉**
    }
}
```

被丢掉的属性**不进 `recordSize`**，于是它后面的 x/y/z 偏移整体前移 —— 读出来的是
前一个属性的尾巴。文件完全合法（`int64` 是 PLY 规范里的标量类型），测试也不会
"失败"，只是**坐标全是错的**。这正是本任务要消灭的那一类。

## 3. 这轮要什么

**二选一，A 都接受**：

1. **把宽度补全**：`int64` / `uint64`（以及 `long` / `ulong` 这类同义写法）按 8 字节算进
   `recordSize`，x/y/z 正常解出 `1.5 / 2.5 / 3.5`；
2. **明确拒绝**：遇到认不出的顶点属性类型时，`ok = false` + 可读 `error`
   （例如 `unsupported vertex property type: int64`），不要继续按错的布局读。

**不接受**：`ok == true` 但坐标是从错位置拼出来的。

判据还是那一条：`python reports/tools/qt_class_probe.py pixel_to_3d 19` → `PASS`
（A 已经把这条用例加进 `tests/test_pixel_to_3d.cpp`，现在是 17 passed / 1 failed）。
