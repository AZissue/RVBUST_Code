## 1. 背景

来源是 A 代码审查第 4 条。`PlyPointReader::read()` 里的 `readScalar()`
（`src/logic/PlyPointReader.h:50`）**只看字节数，不看声明类型**：

```cpp
if (size == 4) { ... memcpy(&f, &raw, 4); return f; }   // 不管声明的是 int 还是 float
if (size == 8) { ... memcpy(&d, &raw, 8); return d; }
return 0.0;                                             // 1/2 字节直接给 0
```

头文件里的 `type` 字符串在 `typeSize()` 里换算成字节数之后就**被丢掉了**
（`detail::Property` 只有 `name/size/num`）。后果：

- `property int32 x/y/z` 的二进制文件 → 整数位被当成 IEEE float 重新解释，
  `12` 变成 `1.68e-44` 这种反规格化数：**看着有值、其实全错**；
- `property short / ushort / uchar x/y/z` → 恒为 `0.0`。

RVC 自己导出的 PLY 是 float32，所以现场一直是好的；但「工具 → 像素→3D（离线）」
这个页面就是让人**手挑文件夹**的，挑到第三方 PLY 就会拿到一串静默的错值，
而且没有任何错误提示。

**做完之后人能看到的**：第三方 PLY 的坐标要么正确解码，要么明确报错——
不再出现"值看着正常、其实荒谬"的数字。

## 3. 明确不做

- **不要**改成"拒绝非 float 的 x/y/z"——本任务要求**正确解码**（`char/int8`、
  `uchar/uint8`、`short/int16`、`ushort/uint16`、`int/int32`、`uint/uint32`、
  `float/float32`、`double/float64`，**有符号/无符号要分开**）。
- 不要动 T-004 刚加的那道"声称顶点数 vs 文件剩余字节"的上界检查（同一个文件，别改回去）。
- 不动 ascii 路径的解析方式（仍是十进制文本），不要把 ascii 结果变成别的数。
- 不改 `read()` / `Result` 签名；不新增 .cpp；不引第三方库。
