# T-011 任务书（A → B）— 相机析构与预览 worker 之间的 use-after-free 窗口

> 判据 `.trio/tasks/T-011.checks.py`。**先读 §5 工作集与 §6 契约冻结。**
> 这条来自 A 的代码审查（第 7 条）。**先读 §1 里"为什么红判据是结构性的"。**

## 1. 背景

`CameraManager::onPreviewTick()`（`src/logic/CameraManager.cpp:998`）把一帧预览丢给线程池：

```cpp
QtConcurrent::run([this, gen, token]() {          // ← 捕获裸 this
    if (!token || token->cancelRequested.load()) return;
    ...
    frames = capturePreviewFrameX1();             // ← 这里在用 this / m_impl
    QMetaObject::invokeMethod(this, [...]{ ... }, Qt::QueuedConnection);
});
```

而 `~CameraManager()`（`:208`）只做了两件事：

```cpp
m_impl->destroying = true;
if (m_workerToken) m_workerToken->cancelRequested = true;   // ← 只置标志
shutdown();
m_impl.reset();                                             // ← 把 m_impl 拆掉
```

worker 的 token 检查在**入口**。一旦某个 worker 已经越过检查、正走在
`capturePreviewFrameX1()` 里（那里面到处是 `m_impl->…` 与 `this`），析构就把 `m_impl` 拆了 ——
经典的 use-after-free。窗口很窄（微秒级），所以：

- **红判据是结构性的**：A 试过用"反复连相机→预览→关窗口"去复现，
  跑不出稳定崩溃（见 `reports/T-011/exit_cycles.py` 的说明）。所以红判据
  （`reports/T-011/preview_lifetime.py`）钉的是**机制**，不是"崩没崩"。
- **绿判据是真机的**：那 5 轮开关窗口必须不崩、退出码正常 —— 它保证你**没有把退出路径弄坏**。

两条一起才说明这件事被处理了：一条证明机制对了，一条证明行为没坏。

## 2. 判据

| # | 判据 | 怎么验 | 期望 |

| 4 | 只动了工作集里的文件 | `verify: auto` —— `python reports/tools/workingset_guard.py …（见 §5）` | exit 0 |

判据 1 接受**两种**合法修法（任一即可，探针会分别报）：

- **A**：预览 worker **不再捕获裸 `this`**（改成捕获 `shared_ptr` 生命周期凭据 / `weak_ptr<Impl>` 之类）；
- **B**：析构路径**确实等**在飞的预览 worker（对预览的 future/watcher 调 `waitForFinished()` 或等价的显式同步）。

同时探针会确认**预览仍然跑在线程池里**（`QtConcurrent::run` 还在）——不许为了好过判据把它挪回 UI 线程
（那是 T-009 的反向操作，会把界面冻住）。

## 3. 明确不做

- 不改 `shutdown()` 的公开语义与幂等性（`tests/test_camera_manager_release.cpp` 钉着它）。
- 不动 `CaptureFlow` / `MainWindow` / 测量相关文件（T-012 的 WIP 还在工作树里，别碰）。
