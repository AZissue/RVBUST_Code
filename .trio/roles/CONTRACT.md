# 共享契约：A 和 B 都按这里的格式干活

这份文件是**两边唯一共享**的格式约定。别在 `A.md` / `B.md` 里各抄一份——抄了就会不一致。

---

## 1. A 的「解决方案」

写到 `.trio/solutions/<批次号>.md`。至少含这七块：

| 块 | 内容 | 为什么必须有 |
|---|---|---|
| 需求复述 | 人说了什么、你怎么理解 | 理解错了能被当场否决 |
| 验收场景 | 人**亲口能说**的"我要看到什么" | 把主观的东西翻译成可观察的 |
| 边界 | 明确不做 / 不能破坏的既有契约 | 把最容易顺手扩大的范围写死 |
| **可执行判据** | 每条都能写成命令或断言 | 判据写不成机器能判的，说明需求还没想清 |
| 待拍板取舍 | 需要人决定的、有代价的选择 | 别替人做有代价的决定 |
| 任务拆分 | 按**能独立验收的一条用户可见路径**切 | 按层次切（先 core 再 render）是耦合的温床 |
| 回灌策略 | 失败时带什么原文、提什么小要求 | 回灌带全量上下文等于重跑一遍 |

> **"实现了 X" 不是判据。**「命令 Y 退出码 0 且输出含 Z」才是。

## 2. 任务书（A → B）

写到 `.trio/tasks/<任务号>.md`。六块 + 两块大项目对策：

1. **背景**：一段话，为什么做、现在什么状态。
2. **判据**：编号列表，每条可验证。

   > **判据要同时落成一份能跑的文件**（2026-09-23 加）：`.trio/tasks/<任务号>.checks.py`，
   > 纯数据，照这张表直译（格式见 `.trio/verify.py` 开头）。A 验收时跑
   > `python .trio/verify.py <任务号>`，不再一条条手敲命令。
   >
   > **每个判据号都要有归宿**：要么写进 `CHECKS`，要么写进 `MANUAL`（人眼判的，如"手感"）。
   > `verify.py` 会检查编号有没有**断档或重复**——漏掉一条就报错，
   > 因为"某条判据被悄悄跳过"正是这套框架最防的事。
3. **明确不做**：写死最容易顺手扩大的范围。
4. **不能破坏的既有契约**：现有测试数、既有 API 语义、源码级契约。
5. **本轮自检限制**：最多一次，只能用 `check.py` / `py_compile`。
6. **交回格式**：文件清单 / 实际执行的命令与原文 / 逐条对照 / 不确定点。
7. **工作集**（大项目对策）：
   ```
   ## 工作集（只准动这些）
   - snake/core.py
   - snake/render.py
   工作集外的文件一律不改；需要动别的文件就停下来在群里说。
   ```
   **这一块同时治三样病**：越界即判失败（治耦合）、框住 B 的上下文预算（治探索空转）、
   让 A 的验收从"读全量 diff"变成"审越界"（治验收带宽）。
8. **契约冻结**（大项目对策）：把"不许破坏的接口"写成显式的**文件 + 符号 + 语义**，
   而不是一句"不能破坏既有契约"：
   ```
   ## 契约冻结
   - snake/core.py::Game.step() 仍然是纯函数：不改全局状态
   - snake/render.py 的 draw_* 签名不变
   契约破了即使判据全绿也判失败。
   ```

## 3. B 的交回说明

用 `as.py b --kind deliver` 发进群，并在正文里给：

- **文件清单**：改了哪些、每个文件改了什么（一句话）
- **实际执行的命令与原文输出**：不要复述，要原文
- **逐条对照**：任务书每一批判据 → 你的判断 → 依据
- **不确定点**：你没把握的地方（**写出来比藏着好**）

---

## 4. 验收证据（A → 群）

用 `as.py a --kind verify` 发，正文里给：命令原文 + 原始输出 + 截图路径（`--ref` 引用，群里会内联显示）+ 结论（通过/不通过/升级给人）。

**不采信实现方的自述**：B 的 `deliver` 只是它的说法，只有 A 复现过的才算数。

**判据那部分走一条命令**（2026-09-23 定）：`python .trio/verify.py <任务号>`。
它自己会写 `reports/<任务号小写>/verify.json`（**这就是判据汇总证据**，`--ref` 指过去即可）。
人要在自己机器上从头复现，仍然是 `python .trio/reproduce.py`——两件事，别混：

| 谁 | 跑什么 | 治什么 |
|---|---|---|
| A 验收**一个任务** | `verify.py <任务号>` | 那一个任务的判据 |
| 人独立复现**整仓证据** | `reproduce.py` | 全套记录在案的期望值 |

### 证据必须落成文件

真机截图、探针脚本、实测数值，落到 **`reports/<任务号>/`**，再用 `--ref` 指过去。
只贴在消息正文里的东西**不复现**——群里的话是给人读的，`reports/` 下的文件才进版本库。

```
reports/T-005/real_key_probe.py         ← 探针写成文件，别用一次性命令
reports/T-005/level1-base.png           ← 真机截图
reports/T-005/tick-rate-level1.json     ← 实测数值
```

**不要**把原始事件流放进 `reports/`（那是 `.trio/log/raw/` 的事，它不进版本库）。
判据见 `PROTOCOL.md` §3「什么进版本库」。

### 证据的体积：**判据汇总进库，原始流不进库**（2026-09-23 定）

探针跑出来的东西分两层：

- **进版本库**：探针脚本本身、判据汇总（几 KB 的 JSON）、真机截图、命令原文与结论；
- **不进版本库**：完整逐帧/逐事件原始流（几十上百 KB、每次都不一样）——
  文件名带 `.raw.json` / `.jsonl`，由 `.gitignore` 挡在外面。

为什么定这条：T-005 第一版把 9000+ 行的逐帧读数直接提交，一次提交多出 28k 行，
把真正的记录（脚本 / 结论 / 截图）淹了。可复现性由**脚本 + 命令 + 汇总值**保证，
不需要把原始流塞进版本库——谁要复现，跑一遍脚本就有。

## 5. 机器可判的消息类型

| 类型 | 谁能发 | 用途 |
|---|---|---|
| `say` | 全部 | 普通发言 |
| `task` | A | 发布任务书（**唯一能唤醒 B 的类型之一**） |
| `plan` / `deliver` | B | 技术方案 / 交付 |
| `verify` | A | 验收结论（**B 无权发**） |
| `escalate` | A / SYSTEM | 升级给人 |
| `gate` / `kill` | SYSTEM / A / HUMAN | 机械闸触发 / 掐断 |
| `evidence` | HUMAN | 人贴证据（截图等） |
| `note` | 全部（除 HUMAN） | 记录，不唤醒任何人 |
