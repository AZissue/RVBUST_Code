# 设备管理数据迁移方案 — 关系库 → 新页面存储

> 编制日期：2026-09-17
> 目标：把关系型数据库中的设备/借测/维修数据一次性迁入新「设备服务管理」页面的存储，后续只保留新页面
> 实施方式：由开发同事按本方案实现，服务器侧按部署流程更新（不在服务器直接改代码）

---

## 一、问题背景（现状诊断，均为实测结论）

本次更新合入了新「设备服务管理」页面（含设备总览/借测/维修三个 tab），但**它使用的是全新存储，与原有关系库无关**：

| 项目 | 现状 |
|---|---|
| 新页面数据源 | `GET /api/html-device-flow/snapshot` → 读取 `html_flow_state` 表（整份数据以 JSONB 快照存放） |
| 新存储现状 | `html_flow_state` 空（返回 `{"revision":0,"data":{"records":[],"devices":[],"recycle":{...}}}`） |
| 关系库现状 | 借测单表、维修单表、设备表中有真实数据（借测 3 条：2 有效 + 1 软删除；设备 2 台） |
| 结果 | 新页面看起来"空的"，但数据没丢——旧接口仍能取到（实测 `/api/loans` 返回 2 条） |

**结论：数据未丢失。本次要做的是"数据源切换 + 迁移"，不是数据恢复。** 09-15 的数据库备份里没有这些记录（创建于 09-16/09-17），且用它覆盖现库会造成更大损失——**不要用备份恢复**。

---

## 二、⚠️ 必须先决策：迁移后哪些功能会受影响

这是本方案最重要的部分。新页面自成一套存储，但**其他模块仍在读关系库**，实测确认：

| 仍在读关系库的功能 | 具体位置 | 迁移后（若关系库停写）的影响 |
|---|---|---|
| 仪表盘设备类待办（逾期借测、待处理维修、排队未完善、待评分、久未跟进） | `dashboard.service.ts` | 新页面新建的记录**不会出现在待办里** |
| 工单↔借测/维修联动（M1–M4：勾选创建、时间线同步、关单拦截、联动待办） | `linkage`（`linkage.listener.ts` 等） | 新页面创建的借测/维修**无法与工单联动** |
| 设备台账统计（客户档案下的设备、借测/维修历史） | `customers.service.ts`、`devices.service.ts` | 客户详情里的设备流转链**看不到新数据** |
| 借测/返修 Excel 导出与模板导入 | `loans-excel.service.ts`、`repairs-excel.service.ts` | 导出**不包含新数据** |
| 工单里的设备关联、按 SN 查询 | `tickets.service.ts` | 新录入的设备**查不到** |

### 三条可选路线

**路线 A（双源并存，不推荐）**：迁移历史数据进新存储，同时关系库继续写。→ 同一业务两套数据，必然不一致，避免。

**路线 B（新存储为唯一数据源 + 改造下游）**：迁完后新页面独占数据，再逐个改造仪表盘/联动/导出读新存储。
- 优点：保留新页面的完整形态（它就是按新结构设计的）
- 代价：改造面大（联动功能是几轮迭代才成型的，重做成本高，且 JSONB 快照做统计/关联查询比关系库笨拙得多）

**路线 C（关系库为唯一数据源，新页面改读关系库）** ← 建议优先评估
- 做法：给新页面加一层数据适配——把关系库的借测/维修/设备查询结果，转换成新页面期望的数据结构返回（`records[]` / `devices[]`），前端几乎不用改
- 优点：**所有既有功能（联动、待办、导出、客户档案）自动继续工作**，无需重写；不动数据、零迁移风险；关系库仍是唯一事实来源
- 代价：需要一个适配层（建议做成一个新的 API 端点，例如让 `/api/html-device-flow/snapshot` 由关系库实时组装）
- 关键点：新页面的写操作（新建/编辑/删除记录）也要落到关系表，一进一出都走适配层

> 如果目标是"只留新页面、且保留联动与待办"，**路线 C 的总体工作量通常小于路线 B**，且风险最低。建议先评估 C，再决定是否走 B。

**下文按路线 B 编写迁移细节**（若最终选 C，则不需要迁移，只需实现适配层）。

## 三、目标数据结构（新存储，从原型代码提取）

### 3.1 `html_flow_state.data`

```jsonc
{
  "records": [ /* 借测/维修记录，见 3.2 */ ],
  "devices": [ /* 设备台账，见 3.3 */ ],
  "recycle": { "records": [], "devices": [] },   // 回收站
  "settings": {}
}
```
- 单例行：`id = 'main'`，另有 `revision`（整数，每次同步 +1，用于并发保护）

### 3.2 record 字段（借测与维修共用一个结构，靠 `type` 区分）

```jsonc
{
  "id": "R...",              // 记录唯一 id
  "orderNo": "LN-260916-001",
  "type": "loan" | "repair",
  "sn": "设备序列号",         // 记录与设备通过 SN 关联
  "model": "相机型号",
  "customer": "客户名称",
  "contact": "联系人",
  "phone": "电话",
  "address": "客户通讯地址",
  "reportDate": "报修日期（维修用）",
  "appearance": "外观描述（维修用）",
  "reason": "故障现象/原因（维修用）",
  "loanStart": "借测开始日期",
  "loanDue": "借测到期日期",
  "loanPurpose": "借测用途",
  "inboundCarrier": "客户归还物流公司",     // 借测
  "inboundTracking": "客户归还快递单号",
  "outboundCarrier": "寄出物流公司",        // 维修时固定「顺丰」
  "outboundTracking": "寄出快递单号",
  "status": "见 3.4 状态取值",
  "owner": "负责人（原型中留空未用）",
  "accessories": "随附配件",
  "notes": "备注",
  "photos": { "0": "图片URL", "1": "..." },   // 键为槽位序号 0-7
  "agreement": { "name": "借测协议.pdf", "data": "文件URL" },
  "followUps": [],           // 在线模式下跟进记录已拆到 html_flow_followups 表
  "createdAt": "YYYY-MM-DD HH:mm:ss",
  "updatedAt": "YYYY-MM-DD HH:mm:ss"
}
```

- 照片槽位标签（固定 8 位）：`['正面','背面','左侧','右侧','顶部','底部','配件图1','配件图2']`，对应键 0–7
- 图片 URL 形态：`/api/html-device-flow/files/{文件记录id}`

### 3.3 device 字段

```jsonc
{
  "id": "D...",
  "sn": "序列号",            // 唯一键（SN 相同视为同一台）
  "model": "型号",
  "ownership": "公司资产" | "客户设备",
  "status": "在库" | "借测中" | "维修中",
  "customer": "当前客户/使用方",
  "assetNo": "公司资产编号",
  "note": "备注",
  "createdAt": "YYYY-MM-DD HH:mm:ss",
  "deletedAt": "（回收站中才有）"
}
```

### 3.4 状态取值（新页面只有这些）

| 类型 | 可选状态 |
|---|---|
| 借测记录 | `借测中`、`已归还` |
| 维修记录 | `待寄回`、`维修中`、`已完成` |
| 设备 | `在库`、`借测中`、`维修中`（由记录的 SN 与状态推导，见 `normalizedDeviceStatus`） |

### 3.5 关联表

**`html_flow_followups`（跟进记录）**：`id`、`record_id`、`sequence`（同记录内序号）、`person`、`date`、`content`、`source`、`deleted_at`、`created_at`

**`html_flow_files`（附件）**：`id`、`storage_key`（物理文件名，存于上传目录）、`original_name`、`mime_type`、`size_bytes`、`created_by_id`、`created_at`

## 六、迁移脚本设计

建议放在 `migration/` 下（与既有导入脚本同目录），命名如 `migrate-device-flow-from-db.mjs`。

**硬性要求：**

1. **默认 dry-run**：不带 `--apply` 只输出统计与差异报告（各表读取条数、将生成的 record/device/followup/file 条数、跳过的异常数据），不写库
2. **幂等**：按 `record.id`（原 UUID）与 `device.sn` 判重；已存在则更新而非重复插入；重复执行结果一致
3. **单事务写入**：`html_flow_state` 的 JSONB 与 `html_flow_followups`、`html_flow_files` 在同一事务内提交，失败整体回滚
4. **写前备份**：执行前把 `html_flow_state` 当前内容导出为文件（带时间戳），便于回滚
5. **revision 递增**：写入后 `revision` +1，避免前端并发覆盖
6. **拒绝在生产库误跑的保护**：脚本内校验目标库连接串，并在执行前打印连接目标要求人工确认（参考既有脚本做法）
7. **异常数据不静默丢弃**：SN 为空/重复、订单无组织的记录，单独输出清单，由人工决定处理方式

**执行顺序**：设备（先） → 借测记录 → 维修记录 → 跟进记录 → 附件 → 组装 `recycle`（软删除记录）。

## 七、实施步骤

1. 决策第二节的路线（B 迁移 / C 适配），确定是否保留关系库
2. 确认第五节所有「需业务确认」项（状态映射、照片槽位、一单多设备处理）
3. 实现脚本（dry-run 版），在预览库上跑，输出统计
4. 与关系库实际数据核对（条数、状态分布、抽样比对字段）
5. 实现 `--apply`，在预览库完整执行 + 前端页面验证（列表、详情、跟进、图片、回收站）
6. 生产库执行：先导出 `html_flow_state` 备份 → dry-run → apply → 页面验证
7. 关系库处置：先设为只读归档（不删表），观察一段时间；确认无遗漏后再决定是否下线
8. 若选路线 B，另需排期改造仪表盘/联动/导出读新存储

## 八、校验清单

- [ ] 借测/维修记录条数与关系库一致（含软删除记录进入回收站）
- [ ] 每条记录的客户、联系人、电话、用途/故障描述、日期字段与关系库逐条一致
- [ ] 状态映射符合约定（尤其 `CANCELLED`、`RETIRED`、`SHIPPED` 等边缘状态）
- [ ] 设备台账条数与 SN 唯一性正确；同一 SN 不重复出现
- [ ] 图片可在新页面正常显示（数量、槽位标签正确），且磁盘上没有产生重复文件
- [ ] 借测协议可预览/下载
- [ ] 跟进记录条数、顺序、时间与关系库一致
- [ ] 新页面新增/编辑/删除一条记录后，数据落到预期存储（若走路线 B，需确认联动与待办是否受影响）
- [ ] 重复执行脚本不产生重复数据（幂等验证）
- [ ] 回收站可恢复被软删除的记录

## 九、风险与回滚

| 风险 | 说明 | 应对 |
|---|---|---|
| 下游功能失效 | 仪表盘待办、工单联动、Excel 导出仍读关系库，迁移后对新数据不生效 | 第二节路线决策；若走 B，需同步排期改造 |
| 一单多设备 | 借测单可含多台设备（明细表一对多），新存储是"一 SN 一条记录" | 迁移时拆分为多条记录（共享单号），或与业务确认是否允许 |
| SN 缺失/重复 | 新存储以 SN 关联设备与记录 | 迁移前清洗；异常清单人工处理 |
| 状态语义丢失 | 新存储状态种类少于枚举 | 按第五节映射，边缘状态人工确认 |
| 双写不一致 | 若迁移后仍有人用旧页面 | 迁移完成即下线旧入口，或旧接口改只读 |
| 回滚 | — | 执行前备份 `html_flow_state`；关系库不删表（原数据始终在），可随时重跑迁移 |

## 十、待决策清单（请评估后逐条确认）

1. **路线选择**：B（迁移 + 改造下游）还是 C（新页面改读关系库）？——建议先评估 C
2. **一单多设备**：拆成多条记录，还是限制一单一台？
3. **状态映射**：`CANCELLED`（已取消借测）、`RETIRED`（报废设备）、`SHIPPED`（已寄出维修）分别如何落到新状态？
4. **照片槽位**：关系库的 `SERIAL`（序列号图）与 `ACCESSORIES`（配件图）在新页面 8 个槽位中如何安置？
5. **地址字段**：新页面有"客户通讯地址"，关系库联系人表无此字段——是否需要先补字段并录入？
6. **关系库去留**：迁移后只读归档，还是最终下线？（建议先只读归档观察）
7. **旧页面入口**：迁移完成后是否彻底移除 `/loans`、`/repairs` 的兼容路由与旧页面文件？
