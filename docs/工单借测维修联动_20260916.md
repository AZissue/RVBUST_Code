# 工单 ↔ 借测/维修联动闭环（M1–M4）

时间：2026-09-16
分支：`crm_system_v2`
对应提交：`1af6065`（M1 勾选创建）、`c547e1b`（M2 双向时间线）、`ca40ff6`（M3 状态汇聚+通知）、`3ad4efd`（M4 待办+e2e）

## 目标与原则

在同一个工单内完成售前借测、硬件维修两条业务线的联动处理，形成完整可追溯的时间线闭环：

- **单一编排者**：借测/维修模块互不引用，所有联动逻辑收敛在 `apps/api/src/linkage/` 模块
- **opt-in**：自动动作均需显式勾选（DTO 默认 false），不勾选行为与旧版完全一致
- **幂等**：同一工单同时最多一张进行中的借测单/维修单，部分唯一索引 + P2002 兜底
- **单向、不改业务状态**：监听器只写时间线事件和跟进，工单/子单状态的唯一来源是用户操作；同步事件带 `syncedFrom: 'linkage'` 标记，SYSTEM 来源跟进不回写，杜绝 A→B→A 回声

## 数据模型变更

迁移 `20260916073331_ticket_linkage_m1`：

- `TicketCategory` 新增 `LOAN_REQUEST`（借测需求）
- `TicketEventType` 新增 `LINK_CREATED`、`LINK_UPDATE`
- 部分唯一索引（Prisma 表达不了，迁移内手写 SQL）：
  - `loan_orders_one_active_per_ticket`：`status IN ('QUEUED','ONGOING','OVERDUE') AND deleted_at IS NULL`
  - `repair_orders_one_active_per_ticket`：`status IN ('RECEIVED','DIAGNOSING','REPAIRING','SHIPPED') AND deleted_at IS NULL`
- 历史完结/取消单据不受约束，归还后可再次借测

已有外键直接复用：`LoanOrder.ticketId` / `RepairOrder.ticketId`（SetNull）、`FollowUp` 的三可空外键（loanOrderId/repairOrderId/ticketId）+ `SYSTEM` 来源。

## 后端 API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/tickets` | 新增可选字段 `createLinkedLoan` / `createLinkedRepair`；联动失败时响应带 `linkageErrors`（前端提示，工单本身保留） |
| POST | `/api/tickets/:id/loan-requests` | 从工单创建借测单（幂等，预填客户/联系人/用途=描述前200字） |
| POST | `/api/tickets/:id/repair-requests` | 从工单创建维修单（幂等，预填 symptom/SN/receivedAt） |
| GET | `/api/tickets/:id/links` | 工单下借测/维修单摘要 |
| GET | `/api/dashboard/linkage-todos` | 仪表盘联动待办（见下） |
| GET | `/api/system/linkage-config` | 任何登录用户可读，返回 `{ defaultCreate: { loan, repair } }` |

`GET /api/tickets/:id` 的 include 新增 `loanOrders(id/loanNo/status/infoComplete)` 与 `repairOrders(id/repairNo/status)`。

## 事件总线与双向同步

引入 `@nestjs/event-emitter`（进程内总线）。子模块只发事件、不互相引用，linkage 监听器统一回写：

| 事件 | emit 方 | 效果 |
|---|---|---|
| `loan.scored` / `loan.infoCompleted` | loans.score / loans.update | 工单时间线「评分 N 分，评估结论：…」「借测信息已完善」 |
| `loan.statusChanged` | fixOverdue / ship / return / cancel | 「已借出 / 已逾期 / 已归还 / 已取消」 |
| `loan.followUpAdded` | loans.addFollowUp | 「跟进：…」（SYSTEM 来源跳过，防回声） |
| `repair.statusChanged` | repairs.transition | 「已受理 / 诊断中 / 维修中 / 已发货」；CLOSED 且有结论时写闭环事件「已完结并返回客户，结论：…」 |
| `repair.followUpAdded` | repairs.addFollowUp | 同上 |
| `ticket.customerReply` | tickets.addEvent | 自动向进行中子单追加 SYSTEM 跟进「客户回复：…」（不再回写工单事件） |

所有自动回写事件 `visibility: INTERNAL`，metadata 带 `{ linkType, linkId, linkNo, syncedFrom: 'linkage' }`。

## 状态汇聚（闭环规则）

- 工单有进行中借测/维修单时，标记 RESOLVED 被拦截并提示具体单号（事务内查询，含事项转换路径）
- 子单全部完结 → 工单详情联动卡片显示「关联业务已完结，可标记解决并关闭工单」
- 不自动关闭工单，系统只负责拦截 + 提醒

## 通知矩阵（6 类，均带去重）

| 时机 | 接收人 |
|---|---|
| 借测单入队 | 工单负责人 + admin：「请完善借测信息并评分」 |
| 新维修单 | admin：「待受理」 |
| 借测逾期 | 工单负责人（受 `linkage.notifyOnOverdue` 开关控制） |
| 子单全部完结 | 工单负责人：「可关闭工单」 |
| 借测信息超时未完善（默认 24h） | 工单负责人（创建人兜底），每小时 cron 扫描，20h 内不重复 |
| 维修无跟进（默认 48h） | 维修单负责人（未指派时 admin），同上 |

工单负责人为空时退化为工单创建人。去重：监听器按「同前缀未读跳过」；cron 按「20 小时时间窗跳过」。

## 配置项（SystemSetting）

| Key | 默认 | 说明 |
|---|---|---|
| `linkage.defaultCreate` | `{"loan":false,"repair":false}` | 创建工单弹窗勾选框默认值（`GET /system/linkage-config` 对全员开放） |
| `linkage.infoCompleteTimeoutHours` | 24 | 借测信息完善超时阈值（系统设置页可改） |
| `linkage.repairFollowupTimeoutHours` | 48 | 维修无跟进超时阈值 |
| `linkage.notifyOnOverdue` | true | 借测逾期是否通知 |

## 前端

- **创建工单弹窗**：分类为售前咨询/借测需求时出现「☑ 同时创建借测单并加入排队」，硬件故障时出现「☑ 同时创建维修单」（默认取 linkage-config，切分类重置）；勾选维修单但未填 SN 时提交前校验阻止
- **工单详情「业务联动」卡片**（时间线上方）：单号可点击跳转、状态徽标、待完善信息橙色角标、完结单据弱化、补建按钮（防重复点击）、全部完结横幅
- **时间线**：LINK_CREATED/LINK_UPDATE 特殊样式，单号渲染为跳转链接（/loans/:id、/repairs/:id）
- **借测详情/维修抽屉**：顶部「来源工单：RVC-xxx」链接一键返回；新增 `/repairs/:id` 直达路由
- **仪表盘「联动待办」**：待完善借测信息 / 待评分 / 维修超时未跟进 / 借测逾期 四组，各 5 条 + 总数，live 刷新
- **系统设置页**：「联动设置」区块（两个超时阈值 + 逾期通知开关）
