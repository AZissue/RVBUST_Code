## 1. 目标与验收标准

**目标**：在无机器人硬件、无相机的条件下可闭环验证"点云经手眼矩阵 + 机器人位姿落到机器人基座系"这条链路正确；在真机上可一键接入。

**验收标准（全部可量化、可复跑；v2 口径）**

| 编号 | 验收条款 | 判定方式 | 门槛 |
|---|---|---|---|
| A1 | 变换链数学正确 | `tests/test_transform_chain.py`：随机 `T_base2tool` + 随机 `T_cam2tool` + 合成点云，逐点与解析真值比（眼在手上 / 眼在手外两分支）。**v3 口径修正**：@feas 报"真值与实测两边都调 `transform_points_mm`，所以 err 恒为 0"——**只对 §[2] 直通节成立**。实读 `test_transform_chain.py:73-79`：§[1] 的真值是内联矩阵乘 `(T_base2tool @ T_cam2tool) @ [p,1]`，**没有**调被测函数 → §[1] 是有效独立证据（同时锁乘序与逐点变换）；§[2] 两边同函数，属自洽性检查，**禁止引用为数学正确性证据**；唯一第三方独立证据是 §[5] DLL oracle | 最大偏差 **< 1e-9 mm**（≥3000 点抽样）；DLL oracle 门限 **1e-4 mm**（@feas 两次实跑 0.000076/0.000073/0.000064 → 0.000081/0.000070/0.000060 mm，同量级；离散来自 `nn_max` 的 500 点抽样）。**v3 新增：skip ≠ pass** —— oracle 缺失时现状打印 `[SKIP] oracle 不可用` 且 `exit 0`（实读 `test_transform_chain.py:134-137`），远程/换机复跑无法区分"真跑了"与"没跑"。故 oracle 升为**必需判据**：缺失时须打印 `[ORACLE SKIPPED]` 且 **exit≠0**，仅 `--allow-skip-oracle` 显式降级为 0（@qa 记入回归手册）。**v4 再加两条**：① **oracle 版本可追溯** —— §[5] 必须打印 DLL 路径 + 版本 + sha256。成因：`handeye-tools/handeye_sdk.py:16-42` 自动取桌面**版本号最高**的 `RVCHandEyeCalibration_v*_win_release`，桌面多装一版 oracle 就**静默换实现**、`nn_max` 无法跨机比对（本次 oracle = `RVCHandEyeCalibration_v3.9.0_20260828_win_release`，DLL 64,244,224 B；**sha256 = `2ab43b6b5ba968f712f2cee840ab2eb5eb781a7b24c2da1b12536511337c29b4`** —— @arch 2026-09-23 在本机实算，`SDK/C++/External/HandEyeSDK/Win64/bin/` 与 `UI/` 两份同值、逐字符一致。要求 §[5] 由测试**程序打印**该值；本值曾在消息传递中丢过一个字符，见 §10 证据纪律）② **套件可迁移**（R12）：只拷原型目录运行会死在 §[4]，`[5]` 与本节新升的"oracle 必需"判据根本执行不到 ③ **降级路径同样必须显形（v4.2 硬条款，@feas RG-09）**：`--allow-skip-oracle` 是合法降级路径，但现状末行仍是裸 `[ALL OK]`、退出码 0，**只有中间那行 `[ORACLE SKIPPED]` 能区分** → 任何只看末行/只看退出码的 CI 或第三方脚本，在"允许降级"这个新入口上踩回 RG-01 同一个坑（危险从默认路径搬到了降级路径，没有消失）。**要求**：任何降级/跳过路径的末行禁止出现裸 `[ALL OK]`，必须写成 `[ALL OK — 已降级：A1 独立判据(§[5]) 未执行]`，且汇总块必须出现"降级"字样 |

> - **A3 门禁路径必须唯一**：只有**戳点（绝对位置度量）**能判退化矩阵（err_mean 110.005 mm）。**两帧重合度不是门禁**——@feas 给出数学恒等证明：两帧相对错位 = `‖R₁δ − R₂δ‖`，当平移误差 δ **平行于两位姿之间的旋转轴**时**恒等于 0**（实测 median/p95 = 0.000/0.000 mm）；@qa 实测同轴两位姿 median 0.263 mm，在 1.0 mm 阈值下**判 PASS**，跨轴才 6.359 mm 抓住。机器人在单轴上移动取两帧是最自然的操作 → 该路径必被误用，故只能 warning。
> - **A2 单位显式化**：矩阵单位与位姿单位都显式必选 + 范数窗口 + 绝对度量复核；禁止"应该是毫米"的假设，也禁止用范数**比值**做判据（R1 实测无判别力）。

## 3. 候选路线对比

### 路线 A（推荐）—— 独立原型 `prototypes/robot_handeye_transform/`，组件层复用主 UI
- **做法**：新建子目录（`core/` + `app/` + `tests/`），core 直接 import `src/core`；UI 用 `EmbeddedPointCloudViewer` + `CameraPreviewCard` + `WorkerThread` + 主项目主题自建控制面板。
- **优点**：符合 `prototypes/README` 既定流程；不影响主程序行为，风险隔离；无相机/无机器人可 100% 跑通。
- **代价**：控制面板要新写（约 2.5 人日）。
- **风险**：UI 视觉与 ui_v2 略有差异（同一 theme/icons 可压到最小）。
- **适用条件**：本子功能还在验证阶段 —— 就是现在。

### 路线 B —— 直接做 ui_v2 第 4 张模式卡片 + `RobotWorkspace` + `backend_bridge` 接线
- **优点**：一步到位成为主功能。
- **代价**：`backend_bridge.py` 体量大且有存量 P0/P1（第六轮审查：`load_session_dir` 删整个会话目录、双份漂移等），新玩法进去后无法区分"新代码错"还是"bridge 旧病"；`prototypes/README` 原则 3 明确"原型阶段不改主程序"。
- **风险**：验证周期被桥接调试吞掉，最坏情况子功能结论不可信。
- **适用条件**：原型验证通过、bridge 存量 P0 已修之后。

### 路线 C —— 改造 `RvbustCloudRegistration_V1.1` 桌面工具
- **优点**：已实机验证过，含中文路径 IO、欧拉角顺序下拉等实用细节。
- **代价**：PyQt5 + Python 3.7 老栈，无法复用主 UI 组件、无法接相机实时流 —— 与用户"复用主功能 UI"要求直接冲突。

### 推荐
**走路线 A**。核心风险（单位错、退化矩阵、退化数据判可用）全是**算法/入口层**问题，不需要 bridge 参与就能验；core 资产已被真值测试 + 厂商 DLL 双重验证。路线 B 留作原型通过后的合并动作。

**为什么不把 hash 写进本文档**：v2 把 `BASE_SRC_DIFF_SHA` 写死在 §1-A8 里，有两个必然发生的事件会让它失效 —— ① 批 0 改完注释，hash 本身就该变；② 本方案后续改版、他人在 `src/` 的改动，都会让它与实际漂移。基线必须放在**跟原型一起走、且进版本控制**的位置。

**锚点文件**：`prototypes/robot_handeye_transform/BASELINE.md`，批 0 完成时由 @dev 建立，固定 6 项：

| 项 | 含义 |
|---|---|
| `BASE_HEAD` | 原型开工时的 HEAD = `8221b82` |
| `BASE_SRC_DIFF_SHA` | **K2 改前** `src/` 未提交 diff 的 sha1 = `7eceb8c3a8826bc13076a235205fb18d44717c6a`（v3 复核，与 @feas 一致） |
| `POST_K2_SRC_DIFF_SHA` | **K2 改后**的 sha1，批 0 执行时回填 |
| `K2_BEFORE` / `K2_AFTER` | `robot_stitch_workflow.py:11-13` 的改前 / 改后原文（各 3 行） |
| `CMDS` | 生成命令原文（见下） |
| `PROTO_COMMIT` | 原型首次 commit 的 sha（批 1.5） |

**hash 口径钉死**（两个坑，本机实测踩过）：

```bash
git diff -- src/ 2>/dev/null | sha1sum | awk '{print $1}'
```

- 直接接 `| sha1sum` 的输出带文件名尾巴（`7eceb8c3… *-`），是 `sha1sum` 读 stdin 的标记，**不是纯 hash**，不能当键值直接比对；
- `git diff` 的 14 条 CRLF 警告走 **stderr**，比对脚本必须 `2>/dev/null` 或分离 stdout，否则日志里看起来像"两次输出不一致"。

**证据纪律（v4 新增；v4.1 更正起因与归因）**：任何要当键值/复核锚点用的 hash、路径、版本号，必须由**程序打印**并原样粘回，禁止人工转述或跨行重排。

**实际事故记录（@arch 复盘）**：DLL 的 sha256 正确值为 `2ab43b6b5ba968f712f2cee840ab2eb5eb781a7b24c2da1b12536511337c29b4`（64 位，两份副本同值），但 @arch 收到的消息里该串为 **63 位**——自第 22 位起 `cee840` 变成 `ce840`，只丢了 1 个 `e`；@arch 据此误发作"报方转录错误"的归因，@scribe / @dev 用程序复核后更正，@arch **撤回该归因**（值本身始终是对的）。对本条规则的要求不变，但补三条教训：① **长度异常先自查消息流水线**，不要先归因于人；② 长 hex 一律由测试打印 **并落盘**（`REGRESSION.md` / `BASELINE.md`），不靠聊天窗口传递；③ 同一值只保留一份"程序产生"的落盘副本，其余引用一律指向它。同理 `BASE_SRC_DIFF_SHA` 必须用本节固定命令生成。

### 10.1 锚点表的时效性（v4.3 新增，起因是一次真实假阳性）

@qa 复核发现 `BASELINE.md`"批 1.5 后"表里 `tests/test_matrix_guard.py` 哈希已失效（表 `f275647d…`、磁盘 `1a1862ba…`）：该表记的是 `15cedf0` 时刻的值，批 2（`05fd446`）改了这个文件（就是 §4.2 那条"禁兜底窗口"的 `inspect.getsource()` 断言），而 `384615c` 只回填了 `app/` 三个文件。**这是结构性缺陷、不是笔误**：BASELINE.md 给的复核命令是 `sha1sum core/*.py tests/*.py`——**量工作树**——却与**历史 commit** 的值比对，只要有人动文件就必然假阳性；这种"狼来了"几次之后，锚点就没人看了，等于没有。

1. 哈希表一律**按 commit 分节**，取值命令钉死为 `git show <commit>:<path> | sha1sum`——与工作树状态无关、任何时候可复现；
