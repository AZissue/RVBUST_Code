# 工作台（今日工作台）审查与优化建议

日期：2026-09-08 ｜ 视角：数据库系统架构师 + 软件开发 ｜ 范围：`DashboardPage.tsx`、`dashboard.service.ts`、相关入口

审查基准：工作台要回答一个核心问题——**"我今天该干什么"**。一切功能和 UI 都应服务于：待办可见、异常可察、一键可达。

---

## 一、数据库系统架构师视角

### 1.1 指标口径与一致性问题（高）

**三个独立请求拼装一个页面，数据互相不一致**

`DashboardPage.tsx:15-17` 同时发三个请求：`/dashboard`、`/loans?status=OVERDUE&mine=1`、`/repairs`（全量）。问题：

- 三个请求到达时刻不同，刷新按钮（`DashboardPage.tsx:25`）只重新拉 `/dashboard`，另外两个用旧数据——页面上 7 个指标卡来自不同时间快照；
- `/repairs` **无分页拉全表**只为前端算一个"返修进行中"计数（`DashboardPage.tsx:22`），数据量增长后是白白传输全表；`/loans` 同理。应改为后端 `summary` 一并返回 `repairingCount` 和 `overdueLoanCount`，前端一次请求拿全。

**指标语义偏差**

- "今日待办"（`dashboard.service.ts:20`）= PENDING 且计划完成时间空或早于明天末——但 IN_PROGRESS 且计划今天完成的单不在内，"今日待办"名不副实；建议口径改为"未解决且 plannedAt ≤ 今天末"，或干脆改名为"待指派/待启动"；
- "今日已完成"按 `resolvedAt` 落在今天计（`dashboard.service.ts:21`）——昨天解决、今天点关闭的工单不算"今日完成"，而团队习惯以"关闭/解决动作发生日"看产出。建议在工单上加 `closedAt`，或口径改为 `OR[resolvedAt, updatedAt 落入今天且状态为终态]`；
- "等待反馈"把等待客户和等待研发相加（`DashboardPage.tsx:23`），但下方异常提醒区又把两个数拆开显示——同一页面两套口径，用户会对不上账。

### 1.2 查询性能（中）

- `dashboard.service.ts:15-25`：9 个查询**全部串行 await**。每次进工作台 = 9 次数据库往返。本地毫秒级无感，树莓派 + 外网部署后每次进页 9 次 RTT 会被放大。改 `Promise.all` 即可，零风险；
- 指标卡下钻需要索引支撑：`ticket` 表常用过滤是 `(assigneeId, status)` 与 `(status, plannedAt)`，当前索引覆盖不全（见审查报告 6），加 `@@index([assigneeId, status])`、`@@index([status, plannedAt])`。

### 1.3 缺失的时间维度数据（功能缺口，中）

工作台目前只有"状态维度"，没有"时间维度"——而对技术支持最有价值的恰恰是时间提醒：

- **停滞工单**：`updatedAt` 超过 N 天（建议 3 天）未动的未解决工单——往往意味着卡住或忘了；
- **计划逾期**：`plannedAt < now` 且未解决的工单——承诺了客户时间没兑现的，应该置顶提醒；
- **等待超时**：WAITING_CUSTOMER / WAITING_RND 超过 N 天的，提示该催客户或催研发。

这三个查询都便宜（上面的索引正好覆盖），但当前 schema 和接口完全没有暴露。

### 1.4 其他（低）

- `todayWorklogs` 取 `take: 10`（`dashboard.service.ts:25`），第 11 条起静默丢弃，页面无"还有 N 条"提示；
- `customer` 角色也走同一 summary，指标语义（"我的借测逾期"等）对客户账号无意义，建议 customer 用单独的精简 summary；
- 删除/关闭的工单级联问题在审查报告 3.5 已述，影响工作台的"今日已完成"历史口径——硬删后数字会对不上。

## 二、软件开发视角

### 2.1 指标卡不可点击（高，纯 UX）

7 个指标卡（`DashboardPage.tsx:23,27`）全部是纯展示 `<div>`。用户看到"待处理工单 3"的第一反应是点进去——现在必须再开"我的工作"手动筛选。每个指标卡应跳转对应预筛选视图：

| 指标卡 | 应跳转 |
|---|---|
| 待处理工单 | `/my-work?status=PENDING` |
| 处理中工单 | `/my-work?status=IN_PROGRESS` |
| 等待反馈 | `/my-work?status=WAITING` |
| 我的借测逾期 | `/loans?status=OVERDUE&mine=1` |
| 返修进行中 | `/repairs?mine=1` |

### 2.2 局部刷新与静默失败（中）

- "刷新"按钮只刷 `/dashboard`（`DashboardPage.tsx:25`），借测/返修两个请求不刷；
- `overdueLoans` / `repairs` 加载失败时 `.data` 为 undefined，指标卡显示 **0**（`DashboardPage.tsx:23`）——失败和"真的没有"在界面上无法区分，会误导决策。至少失败时显示"—"或错误标记；
- 系统已有 `crm-data-changed` 跨标签广播（`api.ts:18-21`），但工作台**没有监听**——在工单页操作完切回来，数据是旧的，只能手动点刷新。挂上监听即可实现"改完即新"。

### 2.3 两栏工单列表信息重复（中）

"正在推进"（`activeTickets` = IN_PROGRESS，take 8）和"需要关注的工单"（`myTickets` = 全部未解决，take 6，按优先级排序）——前者是后者的子集，且 myTickets 按优先级排，IN_PROGRESS 高优先级的会在两栏同时出现。建议合并为一栏"我的未解决工单"（状态徽章区分），省出的位置给 1.3 的"停滞/逾期/等待超时"提醒区——这才是工作台真正缺的。

### 2.4 借测逾期只有数字没有清单（中）

"我的借测逾期"是工作台唯一带风险语义的指标，却只有一个计数。应像工单列表一样列出 top 3-5 张逾期借测单（客户、设备 SN、逾期天数），直接可点进单据处理——否则用户看到"逾期 2"还得自己去借测管理里翻。

### 2.5 其他（低）

- "今日工作记录"每条可点但全部跳到 `/worklogs` 总列表（`DashboardPage.tsx:32`），应跳到该记录详情或锚点；当天 0 条记录时给"补记"快捷入口（工作台是写周报的数据来源，空记录天应该被温柔提醒）；
- 异常提醒区（`DashboardPage.tsx:30`）三个数字同样不可点击下钻；
- `TODAY` 英文眉标（系统性问题，见审查报告第 7 节）；
- 页面无自动刷新，考虑 60s 轮询或数据变更广播（见 2.2）。

## 三、优化优先级建议

| 优先级 | 事项 | 视角 | 预估 |
|---|---|---|---|
| P1 | summary 合并返修/借测计数，前端单请求；刷新一次刷全部 | DBA + 开发 | 0.5 天 |
| P1 | 指标卡全部可点击下钻；失败显示"—"不显示 0 | 开发 | 0.5 天 |
| P1 | 加"停滞工单 / 计划逾期 / 等待超时"提醒区（合并重复的两栏工单列表腾出位置） | DBA + 开发 | 1 天 |
| P2 | 借测逾期列 top N 清单可点击；工作记录空天提醒补记 | 开发 | 0.5 天 |
| P2 | 9 个查询改 Promise.all；加 (assigneeId,status)、(status,plannedAt) 索引 | DBA | 0.5 天 |
| P2 | 监听 crm-data-changed 自动刷新；今日工作记录"还有 N 条" | 开发 | 0.5 天 |
| P3 | 指标口径修正（今日待办/今日已完成），工单加 closedAt | DBA | 0.5 天 |
| P3 | customer 角色精简 summary；TODAY 眉标中文化 | 开发 | 顺带 |
