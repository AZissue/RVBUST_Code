# CRM V2 代码审查报告

日期：2026-09-07 ｜ 范围：apps/api（NestJS + Prisma + Postgres）、apps/web（React + Vite）｜ 分支：crm_system_v2

---

## 0. 我们为什么建这套系统（审查基准）

这套系统的存在目的是：**让 10 人规模的技术支持团队，把"客户问题→工单→跟进→解决→沉淀"的闭环高效跑起来**，具体支撑四件事：

1. **工单**：快速记录客户问题、指派负责人、跟踪处理过程到解决；
2. **客户**：客户档案集中管理，能看到该客户名下工单、设备、借测、返修全貌；
3. **借测/返修**：公司样机的借出跟踪、客户资产的返修跟踪，设备台账与单据联动；
4. **沉淀**：工作记录和周报，把处理过程变成可查询、可统计的资产。

后期要部署到树莓派或轻量服务器，**轻量、可维护、数据可信**是硬约束。

下文所有问题按此目的排优先级：影响"数据可信度"和"日常动线效率"的排最前，纯代码整洁的排最后。

---

## 1. 总体评价

这是一套超出 10 人团队典型水准的整洁实现：模块按域划分清晰、DTO 校验严格、安全细节（密码哈希、会话吊销、登录限流、AI 网关 SSRF 防护、密钥信封加密、审计日志）都有考虑，测试（单测 + e2e）覆盖关键路径，前端加载/错误/空态三态处理普遍到位。

问题集中在四类，按影响排序：

| # | 类别 | 一句话概括 |
|---|------|-----------|
| A | **部署与数据安全** | Docker 卷挂错路径，容器重建即丢附件；生产镜像塞满 devDependencies |
| B | **数据可信度** | 设备台账状态可绕过借测/返修单据随手改；多处状态机并发下有漏洞；客户访问口径不一致 |
| C | **日常动线效率** | 工单详情页无法直接写工作记录；"日报/周报/月报"导航名不副实；破坏性操作普遍无确认 |
| D | **半成品抽象与残留** | 数据库权限模型完全空转；一批死代码/死 CSS/英文眉标待清理 |

A、B 类建议尽快修；C 类是分阶段改进项；D 类适合找半天集中清理。

## 2. P0：部署与数据安全（直接影响"能不能上线"）

### 2.1 附件存储路径错误，容器重建即丢文件 —— 高

- `apps/api/Dockerfile:19` 的 CMD 先 `cd apps/api` 再启动，而 `UPLOAD_DIR` 默认 `./uploads`（`apps/api/src/main.ts:20`、`files.controller.ts:16,46`），实际写到容器内 `/app/apps/api/uploads`；
- `docker-compose.yml:34` 却把卷挂在 `/app/uploads`——**两个路径对不上，返修外观图片等附件写在容器可写层，容器重建全部丢失**。
- 修法（二选一）：卷改挂 `/app/apps/api/uploads`；或统一 `UPLOAD_DIR=/app/uploads` 并在 Dockerfile ENV 固定。

### 2.2 生产镜像包含全部 devDependencies —— 中

- `apps/api/Dockerfile:13-14` 整拷贝构建阶段 node_modules，typescript、vitest、@nestjs/cli、prisma CLI 全部进镜像，白白多几百 MB，与树莓派目标直接冲突。
- 修法：构建后 `npm prune --omit=dev`（prisma CLI 若 migrate deploy 需要则单独保留，或改用多阶段把 migrate 拆到一次性 job）。

### 2.3 会话/登录记录无定期清理 —— 低

- `AuthSession`、`LoginAttempt` 表（`schema.prisma:211-233`）只增不删，过期会话靠命中时才清理。10 人规模增长很慢，但建议加一个每日清理任务（或部署时配 cron SQL）。

## 3. P1：数据可信度（系统价值的地基）

### 3.1 设备台账状态可被直接改写，绕过借测/返修单据 —— 高

- 前端 `DevicesPage.tsx:39-42` 提供"借出/返修/回库/报废"四个按钮，直接 `PATCH /devices/:id/status`（`devices.controller.ts:19`），**不创建借测单/返修单、无确认**。
- 后果：台账状态与单据永久脱节——设备显示"借出中"但没有任何借测单，借测/返修统计随之失真。这正是你最关心的"客户那边设备信息"板块，数据不可信则整个板块失去意义。
- 修法：前端这四个按钮改为跳转到"新建借测单/新建返修单"并预选该设备；后端 `changeStatus` 限制为仅允许纠错场景（或仅 admin），状态原则上由单据驱动。

### 3.2 状态机并发漏洞（借出/归还/返修/状态变更）—— 中

统一模式："事务外读取当前状态 → 校验 → 事务内 update 且 WHERE 不带当前状态"。并发下两次流转都会成功，可跳过状态机：

- `loans.service.ts:63-89`：两台相机并发借出同一台在库设备都会成功（无行锁/条件更新）；
- `loans.service.ts:117-130`、`repairs.service.ts:97-122`、`tickets.service.ts:145-160`：归还/关闭/状态变更同理。
- 修法：`quick-tickets.service.ts:39` 已有正确示范——用 `updateMany({ where: { id, status: 预期值 } })` 校验影响行数，行数不符即抛冲突。同一模式推广到以上各处。

### 3.3 返修与借测流程脱钩 —— 中

- `repairs.service.ts:61,119`：LOANED（借出中）设备可直接建返修单；返修 CLOSED 时无条件把设备置回 IN_STOCK，即使设备同时在借出中。
- 修法：建单校验该设备无进行中借测单；关闭时按设备实际单据状态回写。

### 3.4 客户档案访问口径不一致 —— 中

- `customers.service.ts:35-44`：`get()` 对 employee 不限范围（含背景、备注等内部字段），而 `profile()` 却限制只能看自己负责的客户。两处矛盾，实际效果 = employee 可读任意客户完整档案。
- 修法：明确策略（内部成员默认可见全部客户，还是按负责人隔离），两接口统一。对 10 人内部团队，建议统一为"内部成员可见全部"，代码更简单。

### 3.5 其他数据完整性问题（低）

- `schema.prisma:311`：`@@unique([organizationId, serialNumber])` 对公司样机（org 为 NULL）不生效，且 serialNumber 无独立索引，而 `repairs.service.ts:58` 全局按 SN 查设备可能串客户。加 `@@index([serialNumber])` 并按 org 限定查询。
- `tickets.service.ts:187-191`：管理员硬删工单级联删全部事件和附件，追溯丢失。建议软删除或仅允许关闭。
- `files.service.ts:14-20`：附件与事件的两次写入无事务，可产生孤儿附件。
- `loans.service.ts:127`：归还公司设备时 organizationId 一律置 null，借出前若挂靠某客户会丢归属。
- `users.service.ts:56-81`：admin 可通过 update 把自己降权/停用（disable 有自保护，update 没有），可能把系统变成无管理员。

## 4. P1：日常动线效率（围绕"技术支持的一天"优化）

典型动线断点：**跟进完工单 → 写工作记录 → 出周报** 这一段目前全靠人肉跨页操作。

### 4.1 工单详情页无法直接登记工作记录 —— 高

- `TicketsPage.tsx` 详情页没有"写工作记录"入口；用户要到 `/worklogs` 在 14+ 字段的表单里手工找到对应工单（下拉无搜索）。
- 修法：详情页加"登记工作记录"按钮 → 跳 `/worklogs?ticket=<id>` 预选工单；工作记录的关联选择器加搜索。

### 4.2 "日报/周报/月报"导航名不副实 —— 高

- `App.tsx:46-47`：`/reports` 和 `/stats` 指向同一个 `ReportsPage`（实际是统计页）；导航里"日报/周报/月报"入口给的是统计报表，写周报只能人肉抄数。
- 修法：短期——合并导航入口，改名"统计报表"消除歧义；中期——做真正的周报视图（按人/按周聚合工作记录 + 工单处理量，支持导出 Markdown/复制）。

### 4.3 破坏性操作普遍无确认，且行为不一致 —— 中

无确认：工单状态下拉直接生效（切到已解决/已关闭尤其危险）、设备报废、借测取消、用户禁用/拒绝。
有确认：工作事项取消、工作记录删除。规范建议：**凡状态不可逆或跨单据的操作一律二次确认**；工单状态切到 CLOSED/RESOLVED 弹确认并可选填解决说明。

### 4.4 创建工单时客户"静默建档" —— 中

- `TicketsPage.tsx:61-67`：客户名模糊匹配不到时自动新建客户，只在详情页给一次性提示。误输名字（多一个空格、别称）就产生脏客户数据，还会级联产生空档案。
- 注意：这是你之前明确要求的功能（"如果之前没有的客户则自动新建一个，并且提示新建客户"）。建议折中：自动建档保留，但**创建弹窗内联提示"将新建客户『XX』"并要求勾选确认**，而不是事后提示。

### 4.5 提交可靠性问题一组 —— 中

- `TicketsPage.tsx:100`："写入时间线"无 busy/防重，双击重复提交；
- `RepairsPage.tsx:95-97`：附件上传后本地列表与刷新数据合并，同一张图显示两次；
- `RepairsPage.tsx:104`、`WorkItemsPage.tsx:67`：Drawer 用非受控 `defaultValue`，保存后重开仍显示旧值；
- `UsersPage.tsx:46-47`：拒绝/禁用无确认。
- 修法统一：提交中禁用按钮；上传后清本地暂存；Drawer 改受控或关闭时重置 form。

### 4.6 各页细节清单（低）

- 工单详情返回按钮固定 `navigate('/tickets')`，从"我的工作"进入后返回丢上下文（改 `navigate(-1)`）；时间线空态缺失。
- 客户资料编辑弹窗字段不全（名称/行业/地区/等级改不了）；客户页借测/返修/设备行不可点击跳转单据；等级 chip 无颜色定义。
- 借测列表无搜索、无"只看逾期"快捷视图；取消无确认。
- 已建返修单无作废入口，建错只能向前流转。
- 报表页无时间范围切换、无导出。
- `WorkItemsPage.tsx:27`：进度条 onKeyUp 每按一次方向键发一次 PATCH。

## 5. P2：权限模型收敛（半成品抽象）

- `schema.prisma:131-151` 的 Permission/RolePermission 三张表 + 种子权限定义存在，但**全代码库没有任何强制执行点**——实际授权全靠 `RolesGuard` 按角色名硬编码（12+ 处字符串判断），permissions 数组加载后从不消费（`auth.guard.ts:18-21` 每请求还多付 3 表 join）。
- 两条路二选一：**(a) 启用权限码**——把 RolesGuard 换成 PermissionsGuard，角色→权限映射入库；(b) **删掉权限表**，保留纯角色模型。对 10 人内部系统，(b) 更符合轻量目标，(a) 是过度设计。

## 6. P2：性能（当前量级可接受，增长后需关注）

- `tickets.service.ts:42-53`：工单列表无分页上限、include 7 个关系，数据增长后全量返回。建议加分页（take/skip + 总数）。
- `quick-tickets.service.ts:24-30`：相似工单查询把全部工单载入内存做 JS 相似度。建议限制取数上限 + 只比对标题。
- `dashboard.service.ts:15-25`：7+ 个查询串行 await，可 `Promise.all`。
- 搜索均为 `contains` LIKE，无 GIN/trigram 索引；10 人规模可接受，先不动。
- 索引补充建议：`@@index([status, updatedAt])`（工单列表）、`@@index([serialNumber])`、`@@index([ticketEventId])`（附件）。

## 8. 移动端现状

760px 以下侧栏抽屉 + 表格横滚，基本可用；返修 9 列、工单 8 列在手机上纯横滚无卡片降级（中）；760–1120px 平板区间工单侧栏仍挤占主列（低）。考虑到使用场景是办公室电脑，**建议暂不投入移动端优化**，仅在报表/周报做导出以兼容手机阅读。
