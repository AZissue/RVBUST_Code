# 工单接续联动方案（促进工单流转与闭环）

> 目标：新建工单时可接续同一客户最近的未解决工单——旧单时间线留痕并自动关闭，新单承接上下文，形成「周一售前评估 → 周二测试反馈 → 后续跟进」的工单链，减少重复建单和手工改状态。

## 1. 背景与问题

- 一个客户的售前/测试/跟进过程天然分阶段，每阶段一张工单；现状是旧工单长期挂在「处理中/等待客户」，靠人工记得去关，造成未解决工单堆积、重复建单。
- 系统已有可复用的机制：
  - 工单时间线 `TicketEvent`（含 `LINK_CREATED`/`LINK_UPDATE` 类型与前端文案）；
  - M1-M4 工单↔借测/维修联动（双向时间线、关单拦截：有进行中借测/维修单不允许关单）；
  - 快速工单的相似工单检测（`POST /tickets/quick/similar`，相似度评分）。
- 缺口：工单与工单之间没有正式的「接续」关系，状态与上下文无法沿链路传递。

## 2. 核心设计：工单接续（TicketContinuation）

### 2.1 数据模型（新表）

```prisma
model TicketContinuation {
  id           String   @id @default(uuid()) @db.Uuid
  fromTicketId String   @db.Uuid @map("from_ticket_id") // 前置工单（被接续，关闭）
  toTicketId   String   @db.Uuid @map("to_ticket_id")   // 后续工单（新单，承接）
  note         String?  @db.VarChar(500)                 // 接续说明（如「样品已寄出，待客户测试反馈」）
  carryLinks   Boolean  @default(false) @map("carry_links") // 是否迁移进行中的借测/维修单到新单
  createdById  String   @db.Uuid @map("created_by_id")
  createdAt    DateTime @default(now()) @map("created_at")
  fromTicket   Ticket   @relation("TicketContinuationsFrom", fields: [fromTicketId], references: [id], onDelete: Cascade)
  toTicket     Ticket   @relation("TicketContinuationsTo", fields: [toTicketId], references: [id], onDelete: Cascade)
  createdBy    User     @relation(fields: [createdById], references: [id], onDelete: SetNull)

  @@unique([fromTicketId, toTicketId])
  @@index([toTicketId])
  @@map("ticket_continuations")
}
```

Ticket 模型加两个反向关系字段。用关联表而非在 Ticket 上加 `continuedFromId` 字段：支持一张新单合并接续多张旧单（两张相似未解决单合并为一张的场景），同时保留完整留痕。

### 2.2 业务规则

| 规则 | 说明 |
|---|---|
| 同一客户 | 前置单必须与新建工单同一 `organizationId`，否则 400（保证「相同客户」前提） |
| 仅未解决单可接续 | 前置单状态 ∉ {RESOLVED, CLOSED}，且未删除 |
| 线性链 | 一张前置单最多被接续一次（已有 `fromTicketId` 记录则拒绝，提示「已被 TS-xxx 接续」）；一张新单可接续多张旧单 |
| 防环 | v1 只允许「建单时接续」，新单无下游，天然无环；将来若支持关联两张存量单再加传递闭包校验 |
| 接续说明必填 | `note` 必填（2-500 字），前端表单与后端 DTO 双重校验；写入前置单时间线，自动关单时同步填入其 `solution` |
| 默认自动关单 | 创建时「同时关闭所选工单」**默认勾选、可取消**（`autoClose`）；取消时仅建立关联与时间线留痕，前置单保持原状态（适用只想引用不想关闭的场景） |
| 关单拦截兼容 | 前置单存在进行中借测/维修单时（M3 拦截条件）：`carryLinks=true` 则把这些子单 `ticketId` 迁移到新单（两边时间线各留一条），否则整个创建事务回滚并提示先处理关联业务 |

### 2.3 创建流程（单事务）

`POST /tickets` 扩展可选字段：

```
continuations: [{ fromTicketId, note }],   // note 必填（2-500 字）
autoClose?: boolean,                        // 默认 true；false 时仅关联不关闭
carryLinks?: boolean,                       // 默认 false；前置单有进行中借测/维修单时迁移到新单
```

事务内对每个前置单依次：
1. 校验（存在/同客户/未解决/未被接续过；note 非空且长度合规）；
2. 写 `TicketContinuation`；
3. 前置单时间线写 `LINK_CREATED`：自动关单时为「本工单由 {新单号} 接续跟进：{note}，工单关闭」；不自动关单时为「本工单被 {新单号} 关联引用：{note}」；
4. 新单时间线写 `LINK_CREATED`：「接续自 {旧单号}」；
5. `autoClose` 为真时将前置单置 CLOSED（`solution`=note）；若 `carryLinks`，迁移进行中借测/维修单并各写时间线；
6. 通知前置单负责人与创建人：「您负责的 {旧单号} 已由 {新单号} 接续」/「关联」（dedupe key 防重）。

任一步失败整体回滚，不产生半链路。

### 2.4 查询接口

- `GET /tickets/continuable?organizationId=&keyword=` — 接续选择器数据源：该客户近 90 天、未解决、未删除的工单（排除已被接续的），按更新时间倒序，最多 20 条。
- `GET /tickets/:id/chain` — 工单链：向上（祖先）/向下（后代）各遍历 ≤10 跳，环安全；详情页渲染链路。

## 3. 交互设计（三个入口，一套后端）

### 3.1 新建工单表单（TicketForm）
- 选定客户后出现「接续工单」区：复选该客户未解决工单（标题/编号/状态/最近更新），每条选中单需填**接续说明（必填，2-500 字）**。
- 「同时关闭所选工单」复选框**默认勾选、可取消**；取消时提示「仅建立关联，原工单保持开放」。
- 若所选工单存在进行中的借测/维修单，给出提示并出现「迁移关联业务到新单」选项（默认勾选）。

### 3.2 快速工单确认页（QuickTicketInput）
现有相似工单区已有两个动作：**更新现有工单**（追加跟进，不建单）/ **仍然创建新工单**。增加第三个动作：
- **接续此工单** —— 建新单 + 关联 + 关闭该相似单；确认弹窗内要求填写**接续说明（必填，默认带入问题描述前 100 字，可修改）**，并说明「原工单将关闭，可恢复」。三条路径分工明确，正好覆盖「重复提醒」的三种真实意图。

### 3.3 工单详情页
- 新增「接续链」卡片：上游（← 承接自）/下游（→ 已接续至）两张单的编号、标题、状态徽标，可点击跳转；多前置时全部列出。
- 「发起接续工单」按钮：打开预填的建单表单（客户/设备/分类继承，标题默认 `【接续 {单号}】`），隐藏域带 `fromTicketId`，走同一套 `POST /tickets`。

### 3.4 工单列表
- 有接续关系的工单在编号旁显示链形小图标（hover 提示「已被接续 / 有后续工单」），不做重列，保持列表轻量。

## 4. 时间线与事件（复用现有体系）

- 全部接续动作复用 `TicketEventType.LINK_CREATED`（前端文案「联动创建」已存在）；迁移借测/维修单用 `LINK_UPDATE`。
- 事件 `metadata` 带 `{ continuationId, fromNumber, toNumber }`，详情页时间线条目渲染为可点击链接，点击跳转到链上另一张单。

## 5. 闭环促进的补充建议（超出本次需求，按价值排序）

1. **已关闭工单收到客户回复时提示接续**：客户在新一轮反馈里回复了已关闭的旧单，目前跟进会堆在 closed 单上。建议加提示条「该工单已关闭，可一键接续为新工单」（预填客户+原单上下文），把新反馈引回开放链路。
2. **客户画像页工单链视图**：按接续关系把该客户的工单串成脉络（售前评估→实测→返修→复购），比按时间平铺更能看清客户推进阶段，也呼应「客户背景信息」的建设方向。
3. **建单时未解决单提醒**：选定客户后若其存在 N 张未解决工单，表单顶部醒目提示（含接续入口），从入口上减少「同客户重复开放单」。
4. **借测/返修同模式接续（其他环节一致）**：
   - 借测「续借」场景：新建借测单接续原借测单（原单归还关闭，评分/排队记录沿链可查）；
   - 返修「二次返修」场景：新返修单关联原返修单，设备历史自动串联（设备详情页的 history 已具备，补一层显式关系即可）。
   - 实现上与工单接续共用同一模式（关联表+留痕+自动收尾），v1 先做工单，借测/返修接续作为 v2。
5. **报表口径**：接续关闭的单保持 CLOSED 且无 `resolvedAt`（现状语义不变），解决率统计不被接续虚增；后续如需「接续关闭率」可单独加口径，不在 v1 动报表。

## 7. 边界与异常

- 前置单被删除（回收站）：链查询跳过已删单并标注「已删除」；恢复后链自动还原（外键 Cascade 只影响彻底删除）。
- 并发：两张新单同时接续同一前置单——`fromTicketId` 唯一索引兜底，后到事务失败并提示「已被他人接续」。
- 权限：接续操作随建单权限（admin/support/employee 均可发起），关的是同客户旧单，留痕完整，风险可控；通知保证原负责人知情。
