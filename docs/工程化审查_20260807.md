## 一、测试缺口

### T1. 测试框架与 pytest 完全不兼容，且误收 backup_* 目录
- **文件**: 全部 test_*.py（test_core.py:713 / test_ui.py:553 / test_station.py:397 / test_integration.py:346 / test_chain_stitcher.py:256 / test_workflows.py:254 / src/ui_v2/smoke_test.py:127）
- **严重程度**: 中等
- **问题描述**: 所有测试是脚本式运行器（模块级 `assert` + 顶层直接执行），无任何 `def test_*` 函数。实测 `pytest --collect-only`：**0 个用例收集，10 个 collection ERROR**，其中 3 个来自 backup_* 目录（`backup_20260721_pre_autoparams/test_core.py`、`backup_ui_20260721_icons_v1/test_ui.py` 等）——pytest 在 import 阶段就会把整个脚本跑一遍（创建 Qt 应用、起线程），比"收集 0 用例"更危险：误收集即误执行。`src/ui_v2/smoke_test.py` 因文件名带 test 也被收集。
- **建议**: 根目录加 `pytest.ini`：`[pytest] python_files = test_*.py` 且 `addopts = --ignore=backup_20260721_pre_autoparams --ignore=backup_ui_20260721_icons_v1 --ignore=backup_ui_20260721_pre_icons --ignore=backup_20260721_pre_logfold --ignore=src/ui_v2`；长期方案是把脚本式测试改造成 pytest 函数式（或至少加 `if __name__ == "__main__"` 保护 + 收集函数），并给 CI 留 `python test_*.py` 直跑入口。

### T2. 模式 B（移动链式）端到端与"误差报告落盘/重放"零覆盖
- **文件**: test_chain_stitcher.py:66-252、test_workflows.py:147-206、src/ui_v2/backend_bridge.py:465-588
- **严重程度**: 中等
- **问题描述**: ChainStitcher 核心（配准精度/BA/闭环/门限/增量边）有测试，但：① `MobileChainWorkflow.capture_station` 真实路径（拍摄→自动配准→**配准失败自动删除机位**→状态迁移）无端到端测试；② `get_error_report()` 输出的 edges 内容与 `cumulative_rms_mm` 计算正确性无断言（test_workflows [2] 只查了 n_nodes/n_edges）；③ error_report.json 的保存/加载/回放复盘从未被测试（因为该功能根本没落盘，见 D3）；④ backend_bridge 的 `_on_mobile_*` 信号链路（UI 按钮→后台线程→回调）无任何测试。

### T3. 离线会话重放只覆盖 happy path，缺标定板模式与损坏容错

## 二、数据流 / 健壮性

### D1.（严重）会话架构分裂：设计文档的 scans/ 统一会话是死代码，实际三套并存
- **文件**: src/core/session_manager.py:31-193（实现但从未被实例化）、两种拼接方式改进方案.md:231-244（设计）、src/ui_v2/backend_bridge.py:615-641（实际路径）
- **严重程度**: 严重
- **问题描述**: 方案文档 §8 设计 `scans/<mode>_session_时间戳/`（meta.json + calibration.json + frames_calib/ + frames_scan/ + stations/ + error_report.json，可回放复盘）。`SessionManager` 完整实现了该结构，但 **grep 全仓无任何业务代码引用它**（仅 test_workflows [3] 自测）。实际运行时三套并存：`offline_data/session_时间戳/`（OfflineSession，模式 A 保存会话用）、`offline_data/stations/session_时间戳/`（StationManager，模式 B 拍摄即存盘）、以及从不存在的 `scans/`。新人按文档找不到数据，按代码又对不上文档。
- **建议**: 二选一：① 落实方案——让 backend_bridge 的保存/加载统一走 SessionManager（或 OfflineSession 扩展出 calibration.json + error_report.json 字段）；② 若保留 OfflineSession 为唯一会话格式，则删除 session_manager.py 并更新方案文档 §8，避免死代码误导。

### D2.（中等）模式 A 保存会话不含外参 calibration.json，重放后无法直接拼接
- **文件**: src/ui_v2/backend_bridge.py:615-633（_save_fixed_session）
- **严重程度**: 中等
- **问题描述**: 保存会话只落盘帧（标定帧 + 扫描帧），**不写外参结果**。离线重放流程（README 离线会话流程 4 步）依赖"批量标定会话"重新算外参；若用户已标定好只想复用（方案文档的核心卖点："扫描阶段只需 calibration.json + 扫描帧，不依赖标记物"），当前实现做不到——外参只能通过另存的 JSON 文件手动加载，且不随会话走。
- **建议**: `_save_fixed_session` 把 `calibration_engine.pair_results` + `reference_id` 写入 `session_dir/calibration.json`；`_on_open_session` 加载会话时若存在则自动恢复外参并置 locked 状态。

### D3.（严重）模式 B「保存会话」是假的：只打日志，零磁盘写入
- **文件**: src/ui_v2/backend_bridge.py:582-588（_on_mobile_save）、635-641（_save_mobile_session）
- **严重程度**: 严重
- **问题描述**: `_on_mobile_save` 仅调用 `mobile_workflow.get_error_report()`（纯内存 dict）后打日志"会话已保存: N 机位"——**没有任何写盘动作**；`_save_mobile_session` 返回的路径来自 `report.get('session_dir')`，而 `get_error_report()`（mobile_chain_workflow.py:245-250 → chain_stitcher.py:158-178）根本没有 `session_dir` 字段 → 用户永远看到"移动拼接会话已保存: unknown"。`SessionManager.save_error_report()`（session_manager.py:111-116）存在但从未被调用。方案文档 §8 承诺的"error_report.json 每步重合度评估 + 链累计误差，可回放复盘"完全未落地。
- **建议**: `_on_mobile_save` 真正执行：把 get_error_report() 写为 `<session_dir>/error_report.json`（复用 StationManager 的 session_dir），并让 get_error_report() 携带 session_dir；UI 文案改为真实路径。

### D4.（中等）模式 A 保存会话只存每相机最新一帧，且原地改写 frame_id
- **文件**: src/ui_v2/backend_bridge.py:620-631、src/core/fixed_multi_cam_workflow.py:45-46（frames_calib/frames_scan 为 Dict，latest-per-camera）
- **严重程度**: 中等
- **问题描述**: 工作流只保留每相机**最新**一帧（Dict 覆盖），`_save_fixed_session` 最多存 N 标定帧 + N 扫描帧，多拍累积能力（旧 UI OfflineSession 的 frame_0001..000N）在新入口下丢失。且 `frame.frame_id = max_id + 1` **原地修改工作流持有的帧对象**（副作用：保存会话后工作流内帧的 frame_id 与离线状态被污染）；扫描帧与标定帧同 frame_id 冲突时靠"最大 id+1"规避，逻辑脆弱。
- **建议**: 保存时构造副本（copy 或新建 FrameData）再改 frame_id；会话保存改为按拍摄次数递增帧号，保留多拍语义；或明确 UI 只承诺"保存最新一轮"并在文案中说明。

### D5.（中等）相对 CWD 的路径硬编码：打包后数据/日志位置失控
- **文件**: src/core/offline_session.py:59（base_dir="offline_data"）、src/ui_v2/backend_bridge.py:646（os.path.abspath("offline_data")）、src/core/utils.py:17（LOG_FILE="MultiCameraCalibration.log"）、MultiCameraCalibration.spec:11（RVC_RUNTIME 硬编码 "D:\Program Files\RVBUST\RVC\RVCSDK\runtime"）
- **严重程度**: 中等
- **问题描述**: 全部依赖进程 CWD。PyInstaller 打包后从资源管理器/快捷方式/其他程序启动时 CWD 不定，offline_data/ 会话与 .log 会散落到任意目录，且若落在 Program Files 等只读位置则静默写失败（无任何提示）；spec 的 RVC runtime 路径在他人机器上不存在时静默跳过 DLL（无警告日志），打出的包"看起来成功、连不上相机"。
- **建议**: 统一一个 `paths.py`：打包环境用 `os.path.dirname(sys.executable)`（或 `%USERPROFILE%\MultiCameraCalibrationData`），开发环境用项目根；日志与数据目录启动时 makedirs 并失败告警；spec 中 RVC_RUNTIME 改为探测多个候选路径（含环境变量 RVC_SDK_ROOT）并 log 是否找到。

### D6.（轻微）根目录垃圾产出：debug_detect_*.png 无条件落盘 CWD
- **文件**: src/core/marker_detector.py:220-223
- **严重程度**: 轻微
- **问题描述**: 检测 2D 标记失败时把整帧原图写到 CWD 的 `debug_detect_{w}x{h}_{dtype}.png`，无目录、无开关、无清理（根目录已积累 2 个共 3.7MB，且文件名含分辨率会不断覆盖新值）。打包后同样落到 CWD。
- **建议**: 写入 `offline_data/debug/` 或系统 temp，加环境变量/配置开关，保留最近 N 张即可。

### D7.（中等）加载残缺会话后 detect_all 可能对 None 图像崩溃
- **文件**: src/core/offline_session.py:242-251（detect_all）、243-245（仅当 offline_image_path 存在才读盘）
- **严重程度**: 中等
- **问题描述**: `load_session` 中某相机缺 .png 时 `image_np=None` 且 `offline_image_path=None`；`detect_all` 的补读条件 `if frame.image_np is None and frame.offline_image_path and ...` 不满足 → 直接 `detector.detect_3d(None, ...)`，具体行为取决于 detector（marker_detector.py:212 有 `if image_np is None: return []` 兜底，但 CalibBoardDetector 不一定有），且单帧异常会中断整个批量循环（无 per-frame try/except）。
- **建议**: detect_all 内每帧包 try/except，失败记日志继续；image 缺失帧跳过并计入"跳过 N 帧"统计。

### D8.（轻微）meta.json 非原子写，崩溃/断电可能损坏会话
- **文件**: src/core/offline_session.py:88-89、298-299、src/core/session_manager.py:177-184
- **严重程度**: 轻微
- **问题描述**: 全部 `open(path,'w')` 直写；`_write_back_markers` 还是"读-改-写"整文件，进程崩溃在写中途会留下截断的 JSON，下次 load_session 时整帧丢失（只 log error）。
- **建议**: 写临时文件 + `os.replace()` 原子替换。

### D9.（轻微）会话目录无限增长，无清理/归档入口
- **文件**: src/core/offline_session.py:59-76、src/ui_v2/main_window.py（无删除会话 UI）
- **严重程度**: 轻微
- **问题描述**: 每次"保存会话"都新建 `offline_data/session_时间戳/`，永久保留；UI 无删除/归档入口（station 模式有 new_session 归档，模式 A 没有）。现场长期使用会积累大量含 PLY 的大目录。
- **建议**: 会话列表界面加"删除/归档"，或提供启动参数清理超过 N 天的会话。

### D10.（轻微）取消启动小窗后不清理 RVC 资源
- **文件**: main.py:70-71
- **严重程度**: 轻微
- **问题描述**: `launcher.exec() != QDialog.Accepted` 时直接 `return 0`，而 BackendBridge.__init__（backend_bridge.py:75）已 `camera_manager.initialize()`（加载 RVC 系统/枚举设备），未调用 `bridge.cleanup()`/`shutdown()`，SDK 后台线程与句柄不释放（MvSDKLog 持续写）。
- **建议**: 取消路径也走 `bridge.cleanup()` 再 return。

### D11.（轻微）main.py 与 bridge 对 set_mode 双重调用
- **文件**: main.py:53-56 + 76、src/ui_v2/backend_bridge.py:177（_done 里 shell.set_mode）
- **严重程度**: 轻微
- **问题描述**: `on_connect` 调 `bridge._on_device_manager_reopened`（后台线程完成后会 `shell.set_mode(mode, devices)`），随后 main.py:76 又直接 `main_window.set_mode(mode, devices)`——同一模式被设置两次，且依赖调用桥接器私有方法（`_on_device_manager_reopened`），入口与桥接层耦合。
- **建议**: main.py 只负责 `bridge.connect_devices(mode, devices)`（公开方法，内部完成连接+set_mode），或只在 main.py 调用 set_mode、bridge 只做设备连接，二选一消除竞态。

### D12.（严重）「批量扫描」按钮静默失效：信号定义了但从未接线
- **文件**: src/ui_v2/workspaces/multi_cam_workspace.py:81（batch_scan_requested = Signal(int)）、src/ui_v2/backend_bridge.py:97-108（_wire_multi_cam_workspace 未 connect 该信号）
- **严重程度**: 严重
- **问题描述**: UI 上批量连续扫描按钮 emit `batch_scan_requested`，但 backend_bridge 未连接 → 点击后**完全无响应**（无日志、无提示）。属"界面有按钮、功能不存在"的静默失效，现场用户会以为是 bug 重试。
- **建议**: 要么实现（后台连续 capture_all N 次存入 frames_scan），要么至少 connect 一个"未实现"提示；并在 smoke_test 中增加"所有已定义信号均已接线"的断言（遍历 workspace 信号列表检查 bridge 连接）。

## 三、入口与打包

### E1.（中等）PyInstaller spec 不完整：PyRVC 未收集、RVC 路径硬编码、UPX 风险
- **文件**: MultiCameraCalibration.spec:20-33、46-49、67
- **严重程度**: 中等
- **问题描述**: ① hiddenimports 无 `collect_submodules('PyRVC')`，PyRVC 是延迟导入所以构建不报错，但**打包产物永远连不上相机**（除非恰好 build 环境装了 PyRVC 且被隐式收集）；② RVC_RUNTIME 硬编码绝对路径，他人机器构建时 DLL 静默缺失；③ `upx=True`（EXE+COLLECT 两处）对 Qt/Open3D 大型 DLL 偶有损坏案例；④ `console=False` 下无全局异常钩子，崩溃只有窗口化 traceback，无日志落盘。
- **建议**: 加 `collect_submodules('PyRVC')` 与 `collect_dynamic_libs('PyRVC')`；RVC 路径改探测+告警；`upx=False` 或只对非 Qt DLL 启用；main.py 安装 `sys.excepthook` 把未捕获异常写入日志文件。

### E2.（严重）requirements.txt 无法 pip install：裸写 PyPI 不存在的 PyRVC
- **文件**: requirements.txt:7
- **严重程度**: 严重
- **问题描述**: `PyRVC  # 需从 RVC SDK 安装...` 是裸包名，PyPI 无此包 → `pip install -r requirements.txt` **必然失败**（pip 会尝试安装 PyRVC 并报错，其余依赖也可能未装完）。新环境/CI/打包机无法一键复现环境。
- **建议**: 拆 `requirements-base.txt`（PySide6/numpy/opencv-python/open3d/scipy/PyOpenGL）+ `requirements-sdk.txt`（PyRVC，注释说明从 SDK 目录 `pip install` 或加 path 行），README 快速开始同步两段安装命令。

### E3.（轻微）version.py 的 bump 工具链对当前版本号必崩

## 六、异常处理

### X1.（中等）main.py 无顶层异常防护，打包后崩溃无日志
- **文件**: main.py:23-86
- **严重程度**: 中等
- **问题描述**: 初始化/连接/模式切换的任何未捕获异常（缺 OpenGL、SDK 初始化失败、set_mode 崩溃）直接冒泡；开发态是 traceback，打包态（console=False）是窗口化 traceback 弹窗，用户无法提供有效反馈，也无法定位。
- **建议**: `main()` 包 try/except：写日志文件 + QMessageBox 友好提示 + 返回非零码；安装 `sys.excepthook` 全局兜底。

### X2.（轻微）后台任务失败只 log 不恢复 UI 状态
- **文件**: src/ui_v2/backend_bridge.py:195-213（_on_multi_capture._done）等全部 _done 回调

- **问题描述**: `_done(result, error)` 分支普遍只 `shell.log("...失败", "error")`，不重置加载遮罩/按钮状态/工作流状态（如拍摄失败后工作流仍停在旧状态但 UI 已点过按钮），错误路径与状态机脱节。
- **建议**: 统一错误处理：hide_loading + 状态回退（ws.set_state(当前合法状态)）+ QMessageBox 或醒目日志。
