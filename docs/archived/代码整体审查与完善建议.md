# MultiCameraCalibration 代码整体审查与完善建议

> 审查日期：2026-08-07
> 审查范围：全项目 1.8 万行（`src/core/` 16 模块 + `src/ui/` 旧 UI + `src/ui_v2/` 新 UI + 测试/数据流/打包）
> 审查方法：3 个并行子代理分头深挖 + 关键问题实测复现（conda rvc 环境）
> 详细报告：`code_review_bugs_v3.md`（core 算法，含复现证据）｜ `工程化审查_20260807.md`（工程化）｜ UI 层问题见本文 §2

## 0. 总体评价

- **核心算法层**（core）质量不错：标定/拼接主体逻辑清晰，v1/v2 两轮历史 bug 无回归；但存在 **3 个会产出错误结果或直接崩溃的真实 bug**（详见 P0-1~3），均已被独立实验复现。
- **新 UI shell 层**（控件/门控/样式/冒烟测试）质量好，但 **backend_bridge 接线层问题集中**：模式 A（多相机标定，核心功能一）整条链路跑不通；模式 B 存在假保存（数据丢失风险）。smoke_test 只测 shell 不测 bridge，这类问题全部在冒烟覆盖之外。
- **工程化**：会话架构存在三套并存 + 一套死代码（SessionManager 实现后从未被引用）；README 严重过时；根目录垃圾文件多。

## 1. P0 必修（会导致错误结果 / 崩溃 / 数据丢失）

### P0-1 `pose_graph.py:242-243` 邻接表方向存反 → 拼接结果错误 【严重 bug，已实证】
- `add_edge(from, to, T)` 语义是「from→to 的相对位姿」（`get_transform` 应返回 from→to），但邻接表里 **from 侧存了 `T_inv`、to 侧存了 `T`**，BFS 复合后 `get_transform` 返回真值的**逆**。
- 实测：平移 [50,20,0] 的边，查询返回 [-52.7,-11.0]，点变换误差 112mm。
- 现有测试只验自洽性（期望值本身也反了），验不出。当前拼接走 `calibration_engine` 恰好绕开它，但 `node.T_world` / BA 回退路径全错。
- **修**：`add_edge` 中两处对调（from 侧存 `T`，to 侧存 `T_inv`）；并给测试加一个**已知真值**的方向用例。

### P0-2 `chain_stitcher.py:103,124-130` 失败机位残留节点 → 下一次匹配崩溃 【严重 bug，已实证】
- 配准失败的机位未被清理，残留节点在图中；下一帧匹配到残留节点 → `get_transform` 抛未捕获 `ValueError` 直接崩溃。
- 链式拼接「拍废重拍」是高频场景，必踩。
- **修**：配准失败时从图中移除该节点（或 `get_transform` 失败时优雅降级 + 提示重拍）。

### P0-3 `calib_board_detector.py:236` `blobColor=255` 只认亮斑 【严重 bug，已实证】
- 黑圆白底标准标定板（行业默认配色）下 `findCirclesGrid` 直接 `found=False`，反色图才能检测 → **标准板下整条位姿法标定链路失效**。
- **修**：`blobColor` 改为 0（或同时尝试两种配色），并加检测数量/几何校验。

### P0-4 模式 A（多相机标定）全流程断裂：状态机从未启动 【核心功能不可用】
- `backend_bridge.py:189-351` 的六个操作直接调 `fixed_workflow.add_calibration_frame()/calibrate()/add_scan_frame()/stitch()`，**从不调用 `start_calibration()/start_scanning()`**，工作流 `_state` 永远是 `idle` → 实测 add/calibrate/stitch 全部返回 False；bridge 又无视返回值（如 `:206`），日志显示"拍摄完成"但帧没进 `frames_calib`。
- 后果：模式 A 一条链路都跑不通，用户只看到互相矛盾的日志。
- **修**：连接成功 → `start_calibration(reference_id)`；标定质量门禁通过 → `start_scanning()`；所有 `_work` 返回值不得静默丢弃。

### P0-5 模式 B「保存拼接数据」是假保存 【数据丢失风险】
- `backend_bridge.py:582-588, 635-641`：点击保存只打日志「会话已保存: unknown」，**PLY / error_report.json / 会话目录均未生成**（`SessionManager.save_error_report()` 全仓无人调用）。
- **修**：调 `mobile_workflow` 会话/点云导出 + 误差报告写 JSON，失败返回明确错误。误导性日志比报错更危险。

### P0-6 「批量拼接保存」是死按钮 【功能缺失】
- `multi_cam_workspace.py:316-319` emit `batch_scan_requested`，但 `backend_bridge.py:97-108` 未接线 → 点击毫无反应。
- **修**：bridge 实现该槽（循环 capture_scan + stitch + 保存，后台执行）。

### P0-7 两个一启动就崩的入口 【崩溃】
- `run_shell.py:177`：连接 `LauncherDialog` 不存在的 `network_config_requested` 信号 → `AttributeError`（README 明示的演示命令直接崩）。
- `launcher_dialog.py:306-312`：`set_busy()` 引用从未创建的 `_btn_net_cfg` → 任何连接流程调 `set_busy` 即崩。
- **修**：删引用或补实现「网络配置」按钮。

### P0-8 `requirements.txt:7` 裸写 `PyRVC` 【安装必失败】
- PyPI 无此包，`pip install -r requirements.txt` 必失败。
- **修**：注释标明安装方式（`pip install <RVCSDK>/Python` 或离线 wheel），或拆成 `requirements-core.txt` / `requirements-rvc.txt`。

## 2. P1 尽快（功能不完整 / 状态错乱）

### 模式 B（移动链式拼接）状态管理
- **P1-1** `backend_bridge.py:509-512` 「重拍当前」按钮恒失败：信号约定 `-1` 表示当前机位，bridge 直接拼 `"station_-1"` → 恒报「指定机位不存在」。
- **P1-2** 时间线索引与后端机位 ID 错位（`mobile_chain_workflow.py:120-133` 失败后 `_station_seq` 不回退）：第 2 次拍废、第 3 次成功后，时间线 #2 指向不存在的 station_2，选中/重拍/删除全失效。**修**：bridge 按时间线序号从 `get_station_list()` 取真实 ID。
- **P1-3** 重拍不替换节点反而追加（`backend_bridge.py:526-536` + `station_timeline.py:192-206`）：重拍后时间线出现 4 个节点、旧数据残留；`update_station()` 是死代码。**修**：区分「追加」与「替换」。
- **P1-4** 拍摄/评估期间无门控可并发连点（`backend_bridge.py:465-499`）：两次 `capture_station` 并发，链数据竞争。**修**：`_work` 前 `set_state("capturing")`。
- **P1-5** 撤销/删除不扣减累计误差（`mobile_chain_workspace.py:288-295`）→ 误差虚高误触发「建议优化」。
- **P1-6** 全局优化回填假数据 `on_optimize_done(0.0, 0.0)`（`backend_bridge.py:565-580`），且不刷新 3D。**修**：`optimize_global` 返回优化前后误差，成功后刷新点云。

### 模式 A / 主窗口
- **P1-7** 参考相机下拉与后端 ID 体系不一致（`multi_cam_workspace.py:383` serial vs `fixed_multi_cam_workflow.py:135` camN）→ 切换参考相机形同虚设。
- **P1-8** 标定通过后进不了「外参锁定」状态（`backend_bridge.py:276-281` 只 `set_state("calibrated")`，无任何路径置 `locked`）→ 拼接/保存按钮永远置灰、撤板横幅永不显示。
- **P1-9** 主窗口「设备管理」重开无法枚举新设备（`main_window.py:289-321` 只 restore 不 set_devices，刷新只打日志）→ 现场加相机必须重启程序。
- **P1-10** `_on_multi_step_back` 只打日志（`backend_bridge.py:359-362`），步骤回退无实际功能。
- **P1-11** `_dirty` 脏标记从未置 True（`backend_bridge.py:611`）→ 拍了帧/标了定没保存就关窗，无任何提示。

### 算法/数据（core）
- **P1-12** 全局 BA 结果只写 `T_world`，拼接输出完全不用 →「消除漂移」是摆设。
- **P1-13** BA 残差旋转/平移量纲不均衡；`_se3_log` 在 θ→π 处除零。
- **P1-14** `CameraManager.capture()` 不递增 frame_id，连续单拍同号（UI 靠手工重排掩盖）。
- **P1-15** 多帧标定全失败时残留旧 `pair_results`；`_match_markers` 不过滤 NaN 点（标定板模式 <6 对时必失败）。
- **P1-16** 删除/撤销机位不清理 pose_graph；站位会话不可重放（StationManager 无 load）。
- **P1-17** `calibrate_pair` 默认 `ransac_threshold=0.002` 与 mm 数据不符（毫米输入需显式传 2.0）——建议按数据单位自适应。

### 会话/数据流
- **P1-18** 保存会话只存每相机最新一帧且原地改 `frame_id`（`offline_session`）→ 多帧标定数据丢失。
- **P1-19** 会话架构分裂：`SessionManager`（按《两种拼接方式改进方案.md》§8 实现）**从未被引用**（死代码）；实际三套并存，模式 A 会话不含外参、模式 B 无复盘文件。
- **P1-20** 路径硬编码：`offline_data`、`MultiCameraCalibration.log`、spec 里 RVC runtime 绝对路径——全部相对 CWD。
- **P1-21** 会话加载残缺：模式 B 空操作、模式 A 只取最新帧（`backend_bridge.py:670-685`）。
- **P1-22** `version.py` bump 对 `"1.0.0-alpha"` 必崩（`int("0-alpha")`，已实测）。
- **P1-23** 预览定时器在模式切换/断开相机时不停（`backend_bridge.py:149-153`）→ 对已断开相机 10fps 空转刷 warning。

## 6. UI 设计层问题（架构级，非修补可解决）

1. **两套 UI 并存且职责不清**：ui_v2 的 widgets 依赖旧 `ui/viewer_3d.py`/`ui/camera_card.py`；旧 main_window 2110 行仍被 test_ui.py 维护。需明确"旧 UI = 冻结/退役"还是"抽公共依赖为独立子包"（M15/M16）。
2. **ID 体系混乱（根本设计缺陷）**：设备 serial、后端 `camN`、`station_N`、时间线 index 四种 ID 混用，bridge 手工换算必出错（S3/S7）。需统一 ID 语义 + 显式映射层。
3. **两套状态机靠 bridge 手工同步，注定断链**：core `_state` 与 UI `set_state` 无单一状态源（S1/S8）。应 core 状态驱动 UI，而非 UI 手动推。
4. **bridge 契约未立住**：调 core 方法不检查返回值、日志照报成功（S1/S11）。"薄接线"变"盲接线"。
5. **缺"后台任务 + 结果回传"统一设施**：整链点云合并、PLY 写盘在主线程（M9/M10/M13）；旧 UI 有 `_run_background` 未复用。

## 7. RVCSDK 底层规避清单（做架构时必须遵守）

**项目对 SDK 的封装**（camera_manager.py 基本合格）：
- ✅ PyRVC 延迟导入 + 无 SDK 优雅降级；X1/X2/M 统一抽象；safe_destroy + 句柄防覆盖
- ⚠️ 需补：① GigE Open 失败自动重试（Hikrobot MV_E_CALLORDER 时序竞争，现场偶发"连不上"）；② `capture()` frame_id 递增（P1-14）

**SDK 本身 4 个设计坑（架构规避）**：
1. **句柄覆盖语义**：拍下一帧后上一帧 PointMap/Image 句柄可能失效 → 数据必须"拍帧即存盘"（StationManager 模式），UI 层禁止"留帧待用"
2. **cSetPara 默认构造重置全部参数** → 任何参数设置入口必须"先 GetCaptureOptionParameters 再改再写回"
3. **cp310 精确匹配 + runtime 105 个 DLL** → Python 3.10 钉死；打包/部署必须把 SDK runtime 当一等公民（spec 路径硬编码问题 P1-20 的根源）
4. **线扫模式单拍 Capture() 不可用** → 已检测并提示（正确），但 UI 层需明确引导用户去 RVCManager 调整模式

## 9. 性能优化方案

> 原则：**UI 永不阻塞**（所有耗时计算后台化）+ **减少重复计算**（增量合并/缓冲复用）+ **渲染降载**。
> 现状基线：`_run_background`（backend_bridge.py:1161，WorkerThread）已是标准后台设施；viewer_3d 的 VBO 已做增量（仅数据/着色/点大小变化才重建，视角操作不触碰 VBO）——基础好，问题集中在"主线程合并/写盘/预览"与"每次全量重算"。

### 9.1 主线程阻塞（最高优先，用户体验直接相关）

| # | 现状 | 方案 | 涉及文件 | 工作量 |
|---|---|---|---|---|
| P-1 | 每拍/撤销/删除后 `_done` 主线程调 `get_merged_pointcloud()`（整链所有机位变换+后处理）→ 机位多时每步卡顿（M10） | 合并计算移入 `_work`（后台线程），`_done` 只收结果数组刷 viewer；`_run_background` 已支持 | `backend_bridge.py`（_on_mobile_capture_station / on_undo_done / on_delete_done / on_recapture_done 四处） | S |
| P-2 | 模式 A 拼接保存的 PLY 写盘位置需复核（S11 模式 B 已后台化） | 统一规则：**一切 I/O 在 `_work` 里做**，`_done` 只负责日志/UI | `backend_bridge.py` 全部 `_work/_done` 对 | S |
| P-3 | 预览 10fps 主线程抓帧 + `numpy_to_qpixmap`（两个定时器：`_on_preview_tick` + 新增 `_on_card_preview_tick`），无 try/except（M17） | ① tick 加 try/except（相机断开/异常不崩）；② 多卡全开时自动降频（>2 卡 → 5fps）；③ 转换放后台或复用缓冲（见 P-7） | `backend_bridge.py`、`ui/camera_card.py` | M |

### 10.4 建议实施顺序

1. **先做 P-1/P-3/P-8**（主线程合并/预览/检测并行）——纯性能、不动逻辑、收益最大
2. **再 F-1/F-4/F-11**（一键流 + 确认框 + dirty）——流程安全感
3. **P-5 增量合并**（算法层，需要新测试）——机位多时质变
4. **其余按需**（F-9/F-10 会话完整性、F-12 日志、P-9/P-10 渲染降载）

> 每项改动都建议补对应测试（性能项至少要有"机位 N 时合并耗时"的基准断言）。
