## 3. 候选路线对比

| 路线 | 做法 | 优点 | 代价/风险 | 适用条件 |
|---|---|---|---|---|
| **A 最小止血** | 只加：后台线程跑长任务 + 进度/取消 + 估算前 `remove_non_finite_points()` + 法线参数上界面 | 1~2 人日；直接消掉"卡死" | R2 未修：每次交互仍 7.6~12.9 s；内存问题仍在 | 只要"能用"，接受交互慢 |
| **B 止血 + 结构优化（推荐）** | A + LOD 缓存与增量刷新（内容版本号；颜色/可见性走快路径）+ 显示层用 LOD 采样提前出首帧 | 卡死消失且交互回到 ms 级；内存可控；不动公开 API 语义 | 2.5~4 人日；需重过 11 处刷新调用与撤销语义；Open3D 非线程安全，并发边界要设计 | 目标是把原型推到"可并入主程序"（S6/S7 前置） |
| **C 换显示栈** | 弃 PyOpenGL 全量上传，改用 Open3D Visualizer/VTK 或自写 C++/numba 八叉树 | 上限最高 | ≥8 人日；QWidget 嵌入/交互/标量场/DB 树全部返工；与本仓 S3.5 面板结构冲突 | 只有 B 打不满指标时才考虑 |

## 4. 推荐路线：B（最小集 B1+B2+B3，B4 可选）

**为什么不选 A**：R2 是"加载很久"的第二大项（7.6~12.9 s/次，且有 11 个触发点），A 不修它，用户点个"点大小"仍会卡十几秒——与本次反馈的"加载很久"直接同一现象，等于没解决。
**为什么不选 C**：B 的实测预算（首帧 ≤3 s、交互 ≤200 ms、法线 ≤30 s）在 Python 侧可达；C 的收益要到"5000 万点级"才显现，而仓库现状是非目标（S3.5 明确"载入 10M 不崩"）。

**分项**（分两张卡推进，不互斥、无返工）：
- **S3.6 止血包 = B1 + B3**（≈1.5 人日，含消掉 P0 视图空白）→ 立即开工
- **S3.7 结构优化 = B2**（≈1.5~2 人日）→ 待 @user 确认后开工
- **B4 首帧优先** → 视 U6 结论再定


- **B1 线程化长任务（止血包）**：新增 `app/cc_task_runner.py`，`QThreadPool + QRunnable` 包装；workflow 侧保持纯函数式调用，worker 内完成 `read_point_cloud`/`estimate_normals`/八叉树构建，结果经 signal 回主线程。Open3D 对象**不跨线程共享**（worker 内 deepcopy 后再改）。
  - **取消语义（@dev 提议，采纳）**：Open3D `estimate_normals` 不可中断，取消 = **丢弃结果**，工作线程仍占一核跑完。UI 文案只承诺"进行中/取消后不再应用结果"，**不得写"已停止"**；**不做假进度百分比**（`estimate_normals` 无进度回调），只做"进行中态 + 可取消"。
  - **退化输入兜底（@verify 边界探针，纳入）**：清洗后剩 0 点时 loader 必须给用户可见提示（"已剔除 N 个非有限点 / 剩余 0 点，无法显示"）或直接拒收，禁止静默空白。
- **B2 LOD 缓存与增量刷新**：`CCNode` 增 `data_version:int`（几何/标量变更时 +1）；`set_pointcloud(..., geometry_version=None)`，版本未变则不重建八叉树；把 `_refresh_viewer` 拆成 `_rebuild_geometry()`（仅几何变更）、`_refresh_colors()`（走 `set_cloud_colors`）、`_refresh_visibility()`。11 处调用按语义归位，撤销/重做后强制 `_rebuild_geometry()`。
- **B3 非有限点清理与参数自适应（止血包）**：`load_from_file` 内 `pcd.remove_non_finite_points()` 并记日志（清理前后点数进状态栏）；法线面板暴露 `radius`（默认 = 3× 平均点间距，用 `pcd.compute_nearest_neighbor_distance()` 中位数估计）与 `max_nn`（默认 30）。
  - **双入口过滤（R7/R8，必做）**：`core/cc_octree_lod.py:89-92` 的 bbox 计算与 `PointCloudOctree.__init__` 入口同加 `isfinite` 过滤——只改 loader 会漏掉 viewer 侧喂进来的云（含全 NaN/全 Inf 极端形态）。viewer 侧把 NaN 置 0 的兜底（`cc_gl_viewer.py:270-271`）保留，但不再作为唯一防线。
  - **清洗留痕（低成本前瞻）**：清洗时记录被剔行号/数量（本原型当前无点↔像素索引依赖，grep 无命中；做点云↔照片对齐前需要）。
- **B4（可选）首帧优先**：载入时先用随机下采样（≤50 万点）出首帧，八叉树在后台补齐后替换。

**接口约束（沿用 S3.5 定稿，不得破坏）**：不改 workflow 语义与信号命名族；`core/cc_octree_lod.py` 公开 API 不动（仅新增可选参数）；新增能力一律以**可选参数 + 向后兼容默认值**形式加入。

## 6. 验证结论与剩余未验证点

**已由 @verify 独立复现并判定（报告：`docs/后处理原型性能优化_验证报告_20260924.md`）**：

- **U1 结案（机制表述修正）** 不是死循环，是"NaN 与有效点混杂导致超线性变慢"：同点数对照 70.89 s vs 5.69 s（12.5×）；纯 NaN 云 100 万点 0.87 s。
- **U2 结案（非 OOM）** 事件 **1002 Application Hang**（`AppHangB1/IsFatal=1`，rvc 的 python.exe "已停止与 Windows 交互"）；近 7 天 System 日志无 OOM、9/24 无 Application Error；复现特征为单核满载、RSS 625→665 MB 平台。
- **U3 结案（探针 bug）** `psapi` 探针 `GetCurrentProcess()` 未声明 `restype` → 返回 -1 得无效句柄，且不查返回值。修正写法 539.0 MB vs tasklist 同刻 219,492 K。`tools/perf_probe.py` 一行修。

**剩余未验证点**：

- **U4（构建耗时离散）** 八叉树构建 7.59 s / 12.85 s / 13.04 s，差异归属（内存压力/页缓存）未定；需 3 次重复取中位数。
- **U5（线程化前提）** Open3D 0.19 在 worker 线程内 `read_point_cloud`/`estimate_normals` 是否稳定（是否需在 worker 内独占调用）？需实测。
- **U6（首帧预算可达性）** B4 的"≤50 万点先出首帧"在 9.64M 云上能否稳定 ≤3 s（含 2.9 s IO），不可达则下调 G1 或改 IO 路径（mmap/分块）。
- **U7（新，等 @user 上下文）** 9/22 17:26 一起真实原生崩溃（Event 1000，`PySide6\Qt6Core.dll` 6.11.0.0，异常 `0xc0000409` / `FAST_FAIL_FATAL_APP_EXIT`）与本卡卡死不是同一现象，需单独定位（触发时用户操作未知）。
- **U8（新，等 @user 上下文）** 9/24 14:49 的挂起事件 WER 不含脚本名，而 prototype 日志 14:13:52 之后再无写入 → 该次挂起是否为本 GUI 未确认。
- **U9（新）** 内存口径未对齐：修正 `restype` 后的 probe 报 539.0 MB，同刻 `tasklist` 报 219,492 K（≈214 MB），差 ~2.5×（working set 口径定义/测量时刻差异待定）。G4 数字在口径统一前不作为验收依据。
