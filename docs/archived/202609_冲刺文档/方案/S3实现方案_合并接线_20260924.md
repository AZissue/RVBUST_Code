## 1. 目标与验收标准（门禁 G-S3，修订版）

**目标**：DB 树多选 → 合并信号 → `workflow.merge_clouds`（属性对齐路径），"处理"组有统一入口，结果入树可继续处理。

原文 G-S3 写的是"合并结果颜色/法线属性计数 = 输入并集；`can_undo` 计数按操作数递增"。**后者本轮实读后确认不可满足**：`can_undo()` 是布尔（`core/cc_workflow.py:266-267`），且 `add_cloud`（`:164-179`）**不推历史**，合并天然不产生历史项 → "计数递增"无从判别。故拆为四条，全部可机械核验：

| 编号 | 判据 | 方式 |
|---|---|---|
| **G-S3-a** | 属性并集：合并结果颜色/法线**逐点** = 各输入按顺序拼接；一侧无色 → 0.85 灰（`pcd_utils` 口径）、一侧无法线 → 零填充 | core 已有 4 条（`tests/test_cc.py:401/414/433/444`）+ S3 新增 **UI 路径**断言（混合属性输入） |
| **G-S3-b** | 历史口径：**合并 = 新增节点，不入撤销历史**（与 v1 `postprocess_workspace.py:1076-1090` 一致）。合并前后 `can_undo()`/`can_redo()` **状态不变**；对合并**结果**做一次处理后可 undo 复原 | 新增断言；README 写明 |
| **G-S3-c** | 接线闭环：offscreen 下树多选 2 朵 → 点"合并选中点云" → 新节点入树 + 入 workflow、日志一行、`set_state` 回 `loaded`、ICP 目标下拉含新节点 | 新增 `test_merge_wiring_offscreen`（仿 `tests/test_cc.py:650`） |
| **G-S3-d** | 低 fitness 残留边界（§10.5 裁定）：`0 < fitness < 0.90` 时 `judge_icp_result` 给出 warn 且文案含 fitness 值 | 新增纯函数断言；原 `:686` 局部极小断言不得回归 |

## 3. 候选路线对比

| 路线 | 做法 | 优点 | 代价/风险 | 结论 |
|---|---|---|---|---|
| **① 树为唯一真值**（推荐） | 树加 `selected_cloud_ids() -> List[str]` + `merge_requested = Signal()`；`_on_merge()` 直接读 `self._db_tree.selected_cloud_ids()`；面板只放按钮 + "已选 N 朵"标签，工作区在选中变化时调 `set_merge_state(n)` 控 enabled | 与 v1 `:1077-1083` **同构**（无 W8 回退风险）；无状态镜像 → 无陈旧 id 风险；测试走真实数据路径（树 → handler → workflow） | 测试需在 offscreen 下设树选中态（`item.setSelected(True)`），比只点按钮多一步 | **采用** |
| ② 面板持 id 镜像（复刻 ICP 模式） | `merge_requested = Signal(list)`，工作区 `set_merge_selection(ids)` 注入面板 | 单测只点按钮，写法与 S2 一致 | 树与面板两份选中状态；漏同步就用旧 id 合并（静默错）；结构偏离 v1 | 否 |
| ③ 树右键菜单"合并选中" | 在现有右键菜单（`:191-214`）加一项 | 交互自然 | 与"处理组统一入口"不一致；S4 裁切/ROI 仍需面板入口 → 两套入口维护；offscreen 难断言 | 否（S5 之后可补） |

**不选②③的理由**：S3 的门禁本身是"属性并集经 UI 路径"，②把"选中状态"从被测链路里挪走了（测试不再证明树→workflow 通），③把入口从面板拆开。①在保持 v1 结构的同时让被测路径最长。

## 5. 关键口径：合并输入顺序

`QTreeWidget.selectedItems()` 返回顺序 **≠** 树显示顺序，且随点击先后变化 → 合并结果点序不确定，"前 300 点=红"类断言会变成偶发。

**定口径**：`selected_cloud_ids()` 返回 **DB 树显示顺序**（按树遍历序，非点击序）。测试须用"先点 b 再点 a"证明结果与点击顺序无关。
