### 2.2 【关键发现】真正的耦合放大器不是那 5 行 import，而是 `ui/__init__.py`

`src/ui/__init__.py`（24 行）eager 重导出 `camera_card / viewer_3d / panels.* / main_window`。
Python 语义：导入任意子模块必先执行父包 `__init__`，于是**一行"只想拿个 numpy→QPixmap 的转换函数"就把整个旧 UI + open3d 拖进来**。

实测（conda rvc python，offscreen）：

```
from ui.camera_card import numpy_to_qpixmap   → 2.61s / 2033 modules
  open3d=True  ui.main_window=True  ui.viewer_3d=True  ui.panels.calibration_panel=True
from ui_v2.backend_bridge import BackendBridge → 3.82s / 2059 modules（open3d=True, ui.main_window=True）
from ui_v2 import LauncherDialog               → 2.19s / 2057 modules（open3d=True, ui.main_window=True）
```

→ **用户看到的第一个"模式选择"小窗，此刻在后台加载了 open3d 和 2112 行的旧 MainWindow。** 这与 `ui_v2/__init__.py` 自称的"可完全离线运行（无相机、无 PyRVC、无 **OpenGL**）"直接矛盾，是文档承诺与运行时的偏差。

`ui/__init__.py` 的重导出**全仓零调用点**（`grep -rn "from ui import\|import ui$"` 零命中；消费者一律走 `from ui.<子模块> import`）→ 直接清空即可，不需要任何延迟导出兼容层。

第二条放大器：`src/ui_v2/widgets/__init__.py` eager 导入全部 12 个控件（含 `viewer_panel` → `ui.viewer_3d`）。**但它不该改**——理由见 §4 Phase 0.3。

### 2.7 【v3 新增】WorkerThread 生命周期信号：@dev 的修复仍留一个竞态和一个挂死风险

读码 + PySide6 最小 spike（`scratch/qt_lifecycle_spike.py`，可复跑）：

```
WorkerThread.finished 是: finished(PyObject,PyObject)   ← 子类自定义信号
QThread.finished 是    : finished()                     ← 基类信号被遮蔽
  [结果信号槽] 收到 'res'；此刻 isRunning=True isFinished=False
QThread.finished.connect(...) 失败: AttributeError 'Signal' object has no attribute 'connect'
```

| # | 事实 | 证据 | 后果 |
|---|---|---|---|
| W1 | `src/ui/worker_thread.py:30` 用 `finished = Signal(object, object)` **遮蔽**了 `QThread.finished` | spike 输出第 1-2 行 | 生命周期信号**不可用**，全工程把"工作做完"当"线程退出"用 |

### 2.8 打包约束（PyInstaller 实测）

本工程 `MultiCameraCalibration.spec` 的 `hiddenimports` 只 collect PySide6/open3d/cv2/numpy/scipy/OpenGL，**没有任何本工程模块**，没有兜底。

- @feas 实测（PyInstaller 6.19）：`from pkg import Widget` 与 `import pkg; pkg.Widget()` 两种 `__getattr__` 写法**都不会**把 `pkg.impl` 打进冻结体 → 冻结版 `ModuleNotFoundError`。
- 我补测**函数级**延迟导入：`pkg/mod.py` 内 `def get_widget(): from pkg.impl import Widget`，冻结 exe 从无关 cwd 运行打印 `IMPL_OK`、rc=0；从 exe 内导出 `PYZ.pyz` 查实 `['pkg', 'pkg.impl', 'pkg.mod']` **确在包内**。

→ **规则：延迟导入只用「函数级 import」，禁止 PEP 562 `__getattr__`。** 前者有真实 `IMPORT_NAME` 字节码，modulegraph 递归扫 code object 会收；后者只是属性查找，静态分析看不见。`backend_bridge.py:1955` 现存那行函数内导入是安全的，Phase 1 换源时照抄该形状。

| E6 | ❌ `xxx.ply.tmp` 写法**不可用** | 实测 open3d 0.19：写 `final.ply.tmp` → `[Open3D WARNING] unknown file extension tmp`，**返回 False、不抛异常、文件根本没生成**；写 `final.tmp.ply` → True / 216 字节。配方必须是"临时名保留 `.ply` 扩展 + `os.replace`"。同理：全项目 6+ 处裸调 `o3d.io.write_point_cloud(...)` 都不检查返回值 → 静默不落盘（与 RVC SDK `SaveWithImage` 同款坑） |

| E8 | ⚠️ **两套等待机制语义冲突（新发现）** | `main_window.py:576` 的 `closeEvent` 早已实现 B 类等待：QMessageBox 保存/放弃/取消 → `_wait_for_session_save()` 用**局部 QEventLoop + 30 秒硬超时**，超时后弹"保存可能未完成，是否仍要关闭"，选 Yes 就 `event.accept()`。但 @dev 的 `cleanup()` 对 `must_finish` 是**无超时等待** → 用户明确选了"不等了"，`cleanup()` 仍会一直等下去。**"用户说放弃"与"实现说必须等"直接矛盾**，必须二选一 |
| E9 | ℹ️ 转台在**关窗路径上没有被保护**（@dev 已上报） | 转台有两套保存：① shell 保存按钮/关窗 → `save_session_requested` → `bridge._on_save_session`（**已 B 类保护**，含 `show_loading("正在保存会话...")`，按 `_current_mode` 分派到 `_save_turntable_session`）；② 转台工作区自己的"保存会话"按钮 → `turntable_workspace._on_save_session:911` → `_run_worker:952` → 该池 `_active_workers` **无人等待**。走 ② 时关窗 = QThread 运行中被析构 → **原崩溃可回归** |

**v6 决定（回答 @dev 的三个问题）**

| 问题 | 决定 | 理由 |
|---|---|---|
| Q1 转台池不受保护，本轮加吗？ | **加，但不是新增"注册表"机制**——把工作区的 `_run_worker` 改为委托 bridge 的 runner（`_run_background(func, on_done, must_finish=..., name=...)`）。shell 已持有 `_backend_bridge`（`main_window.py:87/307`，main.py:51 注入），`wire_all` 时把 runner 交给各 workspace | 全工程只留**一个**后台池 = 一套生命周期 + 一套 A/B 分级 + 一处 `cleanup()`。加注册表等于把同一件事做两遍。同时消灭 `_active_workers` 与 `_workers` 两套重复的信号接线 |
| Q2 B 类等待要可见进度 UI，现在做吗？ | **不新建**——它已经存在：`show_loading("正在保存会话...")` + closeEvent 的 QMessageBox + 局部事件循环。缺的只是"关键任务由 workspace 池启动时没有提示"，而这正好被 Q1 的改造覆盖 | 新增进度框是重复建设；1.0.8 的"可见进度"验收改为：走 bridge 的保存路径必定有 `show_loading`，且 E8 的语义冲突解决后不再被 30 秒静默吞掉 |
| Q3 B 类等待后结果回调可能不投递 | **接受**（退出阶段事件循环已停）——但要求把终态日志写进**worker 内部**（如 `logger.info("会话已保存: <path>")`），不依赖 UI 回调 | 否则日志只有"保存中"没有终态，事后无法判断到底存没存。原子写保证不会有半写落到最终路径，日志负责留下证据 |

E8 的统一规则（二选一，我建议前者）：
- **等待只保留一处**：closeEvent 不再设 30 秒硬超时，改为"显示进度 + 等待"；若用户明确选择放弃 → 把该任务标记 `abandoned` 降级为 A 类 → `cleanup()` 不再等它 → pending → 日志 + `os._exit`。
- 或者反过来：`cleanup()` 对 `must_finish` 也设超时，超时则告知用户"会话未能完整保存"再退出（更简单，但会在极端情况下丢数据）。

**任务分级（v5 的核心决定）**——D4 的 (b)+`os._exit` 对"可放弃"任务正确，对"必须完成"任务**有害**：

| 类别 | 典型任务 | 退出语义 |
|---|---|---|
| **A 可放弃** | 设备枚举 / Refresh、自动配 IP、预览类 | 不进退出关键路径：关窗即视为放弃，pending → 日志 + `os._exit`（@dev 现行实现正确） |
| **B 必须完成** | 会话保存、PLY/JSON 写盘、结果导出 | 关窗时**无超时等待 + 可见进度**（"正在保存会话…"），**禁止落进 pending→`os._exit` 名单**——否则用户以为存好了，实际静默丢数据 |

（@feas 的替代方案 ① 只覆盖了"不该等"的那一半；B 类必须有相反语义。方案 ② 进程隔离不做：Device 句柄不可跨进程，等于重写设备层。）

正确收口形状（采纳 @feas 的 try/finally，并补 task_name）：

```python
exit_code = 0
try:
    if launcher.exec() != QDialog.Accepted:
        return 0            # finally 仍会跑 cleanup
    exit_code = app.exec()
finally:
    pending = bridge.cleanup()
    if pending:
        # warning 已带 task_name；os._exit 直接终止进程，不受 return 影响
        os._exit(exit_code)
return exit_code
```

（`cleanup()` 无 pending 时 `finally` 不退出，正常 return —— 逻辑成立。）

## 3. 候选路线对比

| 路线 | 做法 | 优点 | 代价 | 风险 | 适用条件 |
|---|---|---|---|---|---|
| **A. 整包搬移** | 4 个可复用模块一次性 `git mv` 进 `ui_v2/` | 一步到位，A3 直接达标 | `viewer_3d.py` 2026 行牵动两个 workspace，回归面大；旧 UI 立刻不可运行 → 3 个 legacy 测试同时失效 | 高：单次改动跨越两条运行路径，出问题难二分 | 团队已决定旧 UI 停止使用 |
| **B. 分阶段解耦（推荐）** | ① 破 `__init__` 链 → 1.0 修线程信号 → ② 合并 icons、搬 worker_thread/camera_card → ③ 搬 viewer_3d → ④ 判定 legacy 退役 | 每阶段独立可验收、可回滚；旧 UI 全程保持可运行；改动面按依赖顺序递进 | 5 个提交 + 多次回归；中间态存在（两处 icons 并存） | 中低：Phase 0 单文件改动即回收 ~2s 启动开销 | 任何还有交付压力的项目（当前即此情况） |

**不选 A**：`viewer_3d.py` 2000+ 行、两个 workspace 都在用，一次搬完等于把 UI 重构和依赖清理绑在一颗提交里——违反小步原则，且出问题无法定位是移动还是改动引入。
**不选 C**：实测 2.19s/2057 modules 的启动代价 + §2.7 的线程缺陷都在旧 UI 代码里，冻结等于冻结缺陷。
**选 B**，理由：Phase 0 是单文件、改动 < 10 行、收益立刻可测（A4），是性价比最高的第一步；后续阶段按"依赖叶子→根"顺序推进，每步都能单独验收。

6. 依赖顺序不可颠倒：Phase 0 → 1.0 → 1.1 → 1.2/1.3 → 2。
