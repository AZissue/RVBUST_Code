# 阶段 7 增量：手眼标定位姿格式预设 + 离线计算防错

> 日期：2026-10-10 ｜ 范围：`src/logic/CalibrationService.*`、`src/logic/AppConfig.*`、
> `src/ui/ToolsPanel.*`、`src/app/MainWindow.cpp`、`src/logic/HelpContent.h`、`tests/test_calibration_service.*`
> 结论：**位姿格式（旋转表示 + 角度单位）成为一个可保存的全局预设**；离线计算给出
> 「试算各格式」对照表与残差提示。**卡片格式、识别链路、保存链路一行未动。**

## 1. 现象：算成功但算偏（静默错误）

采集完直接点「计算」，`CalibrationService` 把卡片里的 6 个数（`x y z rx ry rz`）**原样**
当欧拉角喂给 HandEyeSDK：

- `CalibrationService.cpp` 标定板与戳点两条路径都写死 `param.poseType = 0; // euler`；
- `isPoseDegree` 只决定那 3 个数乘不乘 π/180，**它不表示"这是哪一种姿态表示"**。

UR 报的 `rx ry rz` 是**轴角旋转矢量**（弧度）：示教器 `0.799 / 1.697 / -1.697`，
模长 √(0.799²+1.697²+1.697²) = 2.53 rad = 145°，正是当时的转角。把它当欧拉角喂进去，
SDK **返回成功**、结果是错的 —— 这是最危险的一类错：界面不会红，数字看着像结果。

## 2. SDK 实测约定（真 DLL 探针，不是手册抄写）

| `poseType` | 含义 | 备注 |
|---|---|---|
| 0 | 欧拉 `x y z rx ry rz`，静态 XYZ，`R = Rz·Ry·Rx` | 默认；本工具原有行为 |
| 1 | 四元数 `w x y z` | |
| 2 | 四元数 `x y z w` | |
| 3 | 16 个数，行主序 4×4 | 平移 3 + 旋转 9 + 末行 `0 0 0 1` |
| 4 / 5 / 9 | 返回 -1 | 不存在的槽位 |

- **没有轴角槽位。** 想让 SDK 按轴角理解，只能我们自己转成 16 数矩阵走 `poseType = 3`。
- `isPoseDegree` 是**纯 π/180 缩放**，与"哪一种姿态表示"无关。

## 3. 探针结论：欧拉顺序搜索救不了 UR

用户的线索是"官方 HandEye 软件会自动推断机器人的欧拉角顺序（每种顺序试一遍、留误差小的）"。
在真 DLL 上按这个思路做了实验：

| 实验 | 结果 |
|---|---|
| 合成数据，格式与真值一致 | `totalMeanError = 0`，恢复的 X 与真值逐位一致 |
| 同数据，把轴角当欧拉读 | SDK **返回成功**，`totalMeanError ≈ 30`（另一份数据上实测 119，见 §6.1） |
| 12 种欧拉顺序轮换（DLL 原生，不靠我的公式重建） | 全部落在 **30 ~ 119**，最好是"今天这条路径" |

**结论**：轴角与欧拉的差别不是"换个顺序"，顺序搜索的整个空间都够不到正确值。
所以正确的做法不是"自动推断"，而是**明确告诉程序卡片的格式是什么**。

（顺带记录一个未解现象：探针里 `xyz` 与 `zxy` 给出了完全相同的残差。因为本方案让
欧拉路径**原样透传**、不经过矩阵转换，这个未知不会影响既有行为。）

## 4. 改动

### 4.1 逻辑层（纯函数，可单测）

`CalibrationService`：

```cpp
QString toSdkPoseLine(const QString& raw, RotationFormat fmt, AngleUnit unit, int& poseTypeOut);
QString poseFormatName(RotationFormat fmt);         // 7 个名字
QString poseFormatDescription(RotationFormat fmt);  // 与坐标转换页共用同一份文案
constexpr double kPoseFormatSuspectError = 5.0;     // 只提示不拦截
```

- `fmt == EulerRpy` → **逐字节等于 `normalizePoseLine(raw)`**、`poseType = 0`。
  这是所有机器人改动前走的路，**已核定的 FANUC 结果因此不可能受这次改动影响**。
- 其它 3 数格式 → `TransformTools::poseToMat4()` 转 16 数矩阵、`poseType = 3`。
  复用现成几何代码，**没有新写任何旋转数学**。
- 4 数（四元数）/9 数（3×3）格式：卡片固定 6 个数，表达不了 → 返回空串
  （也顺手挡住了 `poseToMat4` 的 `std::invalid_argument` 跑到工作线程里去）。

`Params` 新增 `poseFormat` / `poseAngleUnit`，**删掉 `isPoseDegree`** ——
两份状态一定会在某天打架，改成由 `poseAngleUnit` 一处推导。

### 4.2 两处 SDK 参数（唯一改动的生产代码点）

- `calibrateMarker()`：位姿行改走 `toSdkPoseLine`，`param.poseType` 取返回值。
- `calibrateTcpTouch()`：**只有拍照位姿那一列**换（相机点/戳点是纯 xyz，不动）。
  眼在手外时 SDK 本来就收到空位姿，格式对结果无影响 —— 试算前会明确告知这一点，
  免得给出 8 行一模一样的数。

### 4.3 UI：手眼标定页新增「位姿格式」行

- 下拉框只列 **4 种 3 数值格式**（RPY / WPR / ZYX 内旋 / 旋转矢量），索引查表
  （枚举里夹着四元数/矩阵，**不能**像坐标转换页那样 `static_cast`）。
- **「应用」**写进 `AppConfig`（`calib_pose_format` / `calib_pose_angle_unit`，
  `QSettings` INI，`%APPDATA%\RVBUST\HandEyeTool.ini`），**全局生效**：主界面「计算」也按它算。
- **所见即所算**：改了下拉框但没点「应用」时，本页「计算」按眼前选的那个算，
  提示行写明"主界面「计算」仍按 &lt;预设&gt;"。读回配置时还会挡住卡片表达不了的格式。
- 主界面「计算」**不显示**该设置（用户已确认），但日志留一行
  「本次标定位姿格式：X · Y」，出问题能回溯。
- 行显隐跟随"有没有机器人拍照位姿这一列"（眼在手外 + 戳点标定时整行隐藏、试算按钮禁用）。

### 4.4 「试算各格式」对照表

同一份数据把 **4 格式 × {度, 弧度} = 8 次**标定各跑一遍（独立 `QFutureWatcher`，
**不开在 UI 线程**），按 `totalMeanError` 升序列出、标出「←当前预设」、失败行沉底。
标定板模式下每种组合都要重跑识别，点按钮先弹确认提示。
**不自动改任何设置** —— 这是用户提到的"官方自动推断"的诚实版：摆出证据，由人决定。

### 4.5 残差提示（不拦截）

`totalMeanError > 5.0` 时：工具页提示行、主界面日志各写一条「位姿格式可能选错」。
**结果照样给**（PROJECT.md §3 红线：质量告警不拦截）。阈值依据：格式对时实测 ≈0，
轴角当欧拉 ≈30；真机健康值的分布请用户拿一次真实会话核定后再调。

## 5. 明确没动

- **卡片格式**：`CaptureRecord::robotCapturePose` 仍是 6 个数（`x y z rx ry rz`），
  `CaptureFlow` 的 `numericCheck(…, 6)`、`PoseGuide`、`DataManager`、备份 JSON、导出 —— 全不碰。
- `normalizePoseLine` / `normalizeXyzLine` 的既有行为与既有单测。
- 识别回退链、质量告警不拦截、检测缓存等其余红线。
- 备份 JSON 不加键（用户已明确不做"格式随会话记忆"）。
- 机器人读取侧（`URRealtimeReader` / `URRtdeReader`）：**本方案不碰**。
  读回来的是轴角弧度就照实写卡片，由标定环节的格式设置来决定怎么读。

## 6. 验收

- `unit_tests`：**327 通过 / 0 失败**（27 个类）。其中 `calibration_service` **18 条**
  （新增 6 条）：欧拉路径逐字节回归、旋转矢量→矩阵 16 数、四种格式×两种单位对齐
  `TransformTools`、卡片表达不了的格式被拒、坏输入被拒、7 个格式名互异且完整。
- `ctest -C Release`：**3/3 通过**（`unit_tests` / `measurement_truth` / `circle_truth`）。
- 测试有牙（做了证伪实验，随后已还原）：把 `toSdkPoseLine` 的矩阵路径临时改成直通
  → `rotationVectorBecomesMatrix16` 等 3 条立刻失败（15 passed / 3 failed）。

### 6.1 端到端（走程序自己的代码，不是 numpy 复现）

临时探针把 **`src/logic/CalibrationService.cpp` + `src/sdk/HandEyeSDKBridge.cpp` 编进
一个控制台程序**，直接调 `CalibrationService::calibrate()`，喂同一份合成数据
（12 组，真值 X = R([0.30,-0.20,0.10]) + t[30,-20,50] mm，卡片位姿写成轴角弧度）：

| 运行 | `poseType` | `totalMeanError` | 恢复的 X |
|---|---|---|---|
| **旧行为**：轴角当欧拉（度） | 0 | **119.266056** | 旋转差 1.01、平移差 **144.9 mm** |
| **新预设**：旋转矢量（弧度） | 3 | **0.000000** | **max\|dR\| = 0，max\|dt\| = 0.0000 mm（逐位一致）** |

两次都 `retCode = 0`（**都"成功"**）—— 这正是格式错的危险之处：只有误差数字会说话。
`toSdkPoseLine` 第一行的输出（新预设）：`0.4336247347,-0.8999785033,…,0,0,0,1`
（16 个数、行主序 4×4、`poseType = 3`）。

### 6.2 欧拉路径 = SDK 原路（既有结果的回归证据）

所有机器人在这次改动前走的都是「卡片行 → `normalizePoseLine` → `poseType = 0`」。
用同一份数据把两条路并排跑：

| 运行 | 结果 |
|---|---|
| A：程序代码，`RotationFormat::EulerRpy` + 度 | `totalMeanError = 119.266056` |
| B：**直接调 SDK**，`poseType = 0`、mm、度 | `totalMeanError = 119.266056` |

**总平均误差逐位相同，矩阵 16 个数 `max|delta| = 0`。** 也就是说欧拉路径仍然
"就是 SDK 本身"，已核定的 FANUC 结果不可能因为这次改动而移动。

（B 在这份**故意喂错**的数据上误差也很大 —— 那正是它该有的表现：这说明 A 与 B
比的是同一条换算链，而不是"两边都恰好算对"。）

## 7. 现场复测清单（界面，用户手动执行）

1. 工具 → 手眼标定 → 「位姿格式」选「旋转矢量（轴角，UR 优傲）」+ 角度单位「弧度」
   → 点**「应用」** → 提示行应显示"已应用为全局预设…"。
2. 用 UR 那次会话点**「计算」** → 总平均误差应显著变小、矩阵与之前不同（这才对）。
3. 点**「试算各格式」** → 「旋转矢量 · 弧度」应排在第一行（误差≈0），欧拉那几行明显偏大。
4. 改选「欧拉角 RPY」但**不点**「应用」→ 提示行应说明"主界面「计算」仍按 旋转矢量 · 弧度"。
5. 关掉程序重开 → 位姿格式仍是上次应用的值。
6. 故意把格式设错再算 → 出现"位姿格式可能选错"提示，**但仍然给出结果**。
7. 标定板模式点「试算各格式」→ 先弹耗时确认；期间界面不卡（工作线程）。
8. **回归**：拿一次已核定的 FANUC 会话（欧拉 + 度）算一遍 → 矩阵与总平均误差应与改动前
   **逐位相同**（欧拉路径原样透传的实证）。

## 8. 已知风险 / 待确认

- `TransformTools::EulerRpy` 是否逐位等于 SDK 的 `poseType = 0`：**未证实**（探针给了
  矛盾信号）。本方案**绕开**了它 —— 欧拉路径原样透传。若日后想统一走矩阵，
  必须先拿真机 FANUC 数据做 A/B。
- `kPoseFormatSuspectError = 5.0` 是合成数据推出的粗阈值，需真机数据核定。
- 「试算各格式」在标定板模式下 ≈ 8 次识别，现场可能几分钟（已有确认提示）。
