# 机器人通信真机联测任务书

- 版本：v1（2026-10-08，对应程序 2.0）
- 面向：现场操作者
- 目的：把 `STATUS.md` 里「待真机确认」的机器人通信假设，逐条变成**有证据的结论**

---

## 0. 一页速览

| # | 任务 | 需要什么 | 预计耗时 | 产出 |
|---|---|---|---|---|
| A | Modbus TCP 寄存器布局 / 字节序 | 一台支持 Modbus TCP 从站的机器人 | 40 分钟 | `probe_modbus_pose.<时间>.txt` |
| B | UR Realtime 位姿字段偏移 | 一台 UR（或 URSim 仿真器） | 20 分钟 | `probe_ur_offset.<时间>.txt` |
| C | 博纳斯/纳博特 NRC 协议取证 | 一台纳博特/博纳斯控制器 | 30 分钟 | `runtime_<日期>.log` 里的 `[NRC]` 行 |
| D | 埃夫特 EfortSDK 单位与角度约定 | 一台埃夫特机器人 + EfortSDK | 30 分钟 | 记录表 + `runtime_<日期>.log` |

四项**互不依赖**，有哪台做哪台；一台都没有就只做 A 或 B 也行。

**没有真机时的替代**：UR 可装 URSim 仿真器（免费，虚拟机镜像），
能完成 B 的全部步骤；Modbus 可用任意 Modbus 从站模拟器先跑通脚本流程，
但**得不出真机结论**，判定表里会标成「未证实」。

### 安全须知（先读）

- 本任务书里所有脚本**只读**：
  - `probe_modbus_pose.py` 只发功能码 `0x03`（读保持寄存器），不写任何寄存器；
  - `probe_ur_offset.py` 只连一次、只读一个数据包，不发任何指令给机器人。
- 但脚本会**占用一次机器人通信连接**。如果现场还有上位机在轮询同一台机器人，
  先确认它不会被顶掉。
- 操作期间机器人保持**停止**状态，急停按钮在手边。
- 改示教器姿态时，先在**手动/低速**模式下改，确认不会撞到工装/相机/标定板。

## 2. 任务 A：Modbus TCP 寄存器布局与字节序

### 2.1 为什么要做

`src/logic/RobotPose.cpp` 把三件事**写死**了，代码里没有任何开关能改：

1. 位姿从配置的「起始寄存器」开始，6 个值**连续无间隔**；
2. Float32 占 2 个寄存器、Int32 占 2 个、Int16 占 1 个；
3. 字节序是**大端**（`QDataStream::BigEndian`，相当于 ABCD）。

> ⚠️ 注意：`STATUS.md` 里曾写着「当前默认 Float32 大端，**可配置**」——
> 这是错的，代码里没有字序/字节序开关。本次任务的目的之一就是确认到底要不要加。

### 2.2 操作步骤

**步骤 A1** — 让机器人停在一个好认的位姿。

用示教器把机器人 TCP 设成（或直接手动挪到）：

```
x = 100.000 mm
y = 200.000 mm
z = 300.000 mm
A =  10.000 度
B =  20.000 度
C =  30.000 度
```

停不到精确值也没关系，**照实记录实际值**即可。

**步骤 A2** — 在界面上确认/填写 Modbus 参数（先按最可能的默认值）：

| 界面项 | 先填 |
|---|---|
| 协议 | `Modbus TCP` |
| IP / 端口 | 机器人 IP / `502` |
| 格式 / 系数 | `Float32` / `1.0` |
| 起始寄存器 / 站号 | `0` / `1` |

点「连接」。记下连接是成功还是失败（失败也要记，含界面上的提示文字）。

**步骤 A3** — 在工具页点「读取当前位姿」（或主界面「拍照位姿」），
把读到的 6 个数记到记录表。**这一步只为了对照，不用追求正确。**

**步骤 A4** — 跑转储脚本，拿到原始寄存器：

```bash
cd /d D:\MyCode\MyHandEyeTools
python reports\tools\probe_modbus_pose.py --host <机器人IP> --port 502 --unit 1 --start 0
```

脚本会同时把结果写成 `reports\tools\probe_modbus_pose.<时间>.txt`。

**步骤 A5** — 如果脚本报告「表里找不到 0x42C8」，说明起始寄存器不是 0：
从 0 开始分段扫，找出这三个特征值出现的位置：

```bash
python reports\tools\probe_modbus_pose.py --host <机器人IP> --start 0   --count 125
python reports\tools\probe_modbus_pose.py --host <机器人IP> --start 125 --count 125
python reports\tools\probe_modbus_pose.py --host <机器人IP> --start 250 --count 125
```

把「0x42C8 / 0x4348 / 0x4396 出现在第几号寄存器」记进记录表 —— 那个地址就是要填的起始寄存器。

**步骤 A6** — 姿态约定三连（每个只改一个量，改完重跑一次 A4）：

| 子步骤 | 示教器设定 | 要回答 |
|---|---|---|
| A6a 顺序 | 依次只设 `A=+90`（B,C=0）、`B=+90`（A,C=0）、`C=+90`（A,B=0） | 90 分别出现在第 4 / 5 / 6 个值的哪一个？ |
| A6b 符号 | `A = -30`（其余 0） | 读回是 `-30` 还是 `330`？ |
| A6c 单位 | `A = +90` | 读回是 `90` 还是 `1.5708`？ |

**步骤 A7** — 模式按钮回归（用「模拟连接成功」即可，不必接真机）：
把标定方式切到**眼在手外 + 戳点**，确认「拍照位姿」按钮隐藏；切回其余三种模式，
确认它出现。

### 2.3 预期结果与判定

机器人停在 x=100 y=200 z=300 A=10 B=20 C=30 时，**若代码三条假设全部成立**，
原始寄存器应当正好是：

| 值 | 寄存器对 | 十六进制 |
|---|---|---|
| x=100 | 第 0、1 个 | `42C8 0000` |
| y=200 | 第 2、3 个 | `4348 0000` |
| z=300 | 第 4、5 个 | `4396 0000` |
| A=10 | 第 6、7 个 | `4120 0000` |
| B=20 | 第 8、9 个 | `41A0 0000` |
| C=30 | 第 10、11 个 | `41F0 0000` |

判定表：

| 看到的 | 结论 | 我要做的事 |
|---|---|---|
| 与上表逐对一致 | 布局/连续性/大端 Float32 全部成立 | 把这三个假设从「待确认」升级为「已证实」，**不用改代码** |
| 每对两个寄存器**左右互换**（如 `0000 42C8`） | 字序颠倒（CDAB） | `RobotPose` 加一个字序开关（WordSwap），界面加一栏 |
| 4 字节**整体反序**（如 `0000 C842`） | 全字节反序（DCBA） | 同上，加第二种开关值 |
| 找不到 `42C8/4348/4396`，但有 `0001 86A0` 这类小整数 | 是 Int32×系数 | 起始寄存器 + 系数填对即可；如仍需字序开关同上 |
| 6 个值**不连续**（中间夹着别的量） | 布局有间隔 | 加「取值步长/逐值地址」配置，或改成按地址表读 |
| 单个寄存器 1 个值、量级/100 才对 | Int16×系数 | 已有该格式，确认系数即可 |
| 数值对但符号/顺序与 A6a/A6b 不符 | 角序或符号约定不同 | 在 `RobotPose` 里加角度重排/取反（只动纯逻辑 + 单测） |
| A6c 读回 1.5708 | 机器人报的是**弧度** | 在 Modbus 路径加「原始角度单位」换算（UR 路径已是弧度，别混） |
| 连接就失败 | 端口/站号/寄存器类型不对 | 按界面提示逐项排查后重试 |

## 3. 任务 B：UR Realtime 位姿字段

### 3.1 为什么要做

`src/logic/URRealtimeReader.cpp` 里写死了：

```cpp
constexpr int kPoseOffset = 8 + 48 * 4;   // 200
constexpr int kPoseBytes  = 48;           // 6 个大端 double
```

即假定包体 = 8 字节时间戳 + 若干 48 字节块，**第 5 个块**是 `actual_TCP_pose`。
注释里写着 "Empirically confirmed"，但仓库里没有任何证据文件，而且
**不同固件的块集合并不完全一致**。另外它假定：位置单位是**米**（代码里 ×1000 转 mm）、
姿态是**轴角弧度**（原样透传，不转欧拉角）。

### 3.2 操作步骤

**步骤 B1** — 用示教器把 TCP 停在一个好认的位置，例如 `x=123.456 y=200.000 z=300.000`。
**记下示教器上显示的这三个数**（是 mm）。

**步骤 B2** — 跑脚本（示教器坐标按 mm 填）：

```bash
python reports\tools\probe_ur_offset.py --host <机器人IP> --expect 123.456,200,300
```

脚本自己会同时按「米」和「毫米」去找，结果写成
`reports\tools\probe_ur_offset.<时间>.txt`。

**步骤 B3** — 姿态约定：

1. 姿态归零（`rx=ry=rz=0`）→ 读一次，三个数应当≈0。
2. 只绕一个轴转 `+90°` → 读一次，看是 `1.5708` 形式（轴角弧度）还是 `90` 形式（度）。
3. 把该轴改成 `-90°` → 看读回的值是负，还是轴向量反号（轴角在两解之间不唯一）。

**步骤 B4** — 记录**控制器型号 + 固件版本**（示教器：关于/系统信息），
以及协议下拉选的是 `UR Realtime (30003)`、端口 `30003`。

### 3.3 预期结果与判定

| 看到的 | 结论 | 我要做的事 |
|---|---|---|
| 偏移 `200` 处的 xyz 与示教器一致 | 偏移/单位/姿态类型全部成立 | 把「待确认」升级为「已证实」，并补一份 URSim 取证脚本进仓库 |
| 找到一个块但偏移 ≠ 200 | 固件块布局不同 | 把 `kPoseOffset` 改成实测值，并做成**可配置**（不同固件共存） |
| 找到的是偏移 `344`（`target_TCP_pose`） | 读了「目标位姿」而不是「实际位姿」 | 改选块，并把块选择提到配置项 |
| 单位是毫米（`123.456` 而不是 `0.123456`） | 单位假设反了 | 去掉 ×1000，加单位开关 |
| 姿态读回 `90` | 不是弧度 | 加「原始角度单位」换算 |
| 连不上/端口无数据 | 端口或 realtime 接口被禁 | 按脚本提示排查，记录固件版本后重试 |

> 没有真机时：装 **URSim**（Universal Robots 官方免费仿真器），
> 同样能跑 B1–B4，结论对固件差异的覆盖度差一些，但**能确认偏移 200 是否成立**。

## 4. 任务 C：博纳斯/纳博特 NRC 协议取证

### 4.1 为什么要做

`src/logic/NrcJsonReader.cpp` 的注释写得很直白：

> 应答字段名**未经真机确认**，所以候选表故意列得很宽，取第一个 ≥6 个数字的数组。

候选字段名顺序是：
`posValue` / `currentPos` / `realPosMCS` / `realPosACS` / `pos` / `position` /
`jointPos` / `axisPos` / `curPos` / `cartPos` / `pose` / `data` / `value`
（顶层找不到就下探一层）。

**仓库里从来没出现过一条真实的、能解析出位姿的应答。** 所以这个任务**不是验证，是取证**：
把真实应答抓回来，我照着固定字段名。

### 4.2 操作步骤

**步骤 C1** — 协议选 `博纳斯(纳博特) JSON/TCP`，IP 填控制器 IP，
端口先填 `6001`（默认）。点「连接」。

**步骤 C2** — 连接成功后，在工具页点一次「读取当前位姿」（或主界面「拍照位姿」）。
**连接失败也要重复点 2~3 次**，让日志里留下尝试记录。

**步骤 C3** — 关掉程序（确保日志刷盘），打开：

```
D:\MyCode\MyHandEyeTools\build\src\Release\logs\runtime_<日期>.log
```

把**所有**以 `[NRC]` 开头的行复制出来。重点是这几类：

| 日志开头 | 含义 |
|---|---|
| `[NRC] handshake 0x2002 -> ...` | 握手结果与字节数 |
| `[NRC] <命令> resp <n> bytes: <hexdump>` | 原始应答的十六进制 |
| `[NRC] <命令> resp text: <文本>` | 原始应答当文本看 |
| `[NRC] pose ok: x=... rx=...` | **解析成功了**（本次最想看到的一行） |
| `[NRC] pose parse failed: <原因>` | 解析失败及原因 |
| `[NRC] skip ... frame while waiting for ...` | 收到了别命令的帧（可能是在推流） |

**步骤 C4** — 记录：控制器型号、固件版本、实际端口、`handshake` 那行的命令字。

### 4.3 预期结果与判定

| 看到的 | 结论 | 我要做的事 |
|---|---|---|
| 有 `pose ok:` 且与示教器一致 | 候选表已经命中 | 把命中的字段名**钉成主字段名**（不再靠猜），加一条基于真实应答文本的单测 |
| 有 `resp text:` 但 `parse failed` | 拿到了真实 schema，只是名字不在候选表 | 把真实字段名加进候选表并置顶，用真实应答文本补单测 |
| 只有 `handshake` 没有 `resp` | 命令字或握手格式不对 | 按 hexdump 反推帧格式，改命令表 |
| 连不上 | 端口/网段/协议名不对 | 记录实际端口后重试 |
| 一条 `[NRC]` 都没有 | 界面路径没走到该协议 | 确认选的是「博纳斯(纳博特) JSON/TCP」并已点连接 |

## 5. 任务 D：埃夫特 EfortSDK 单位与角度约定

### 5.1 为什么要做

`src/logic/EfortPoseReader.cpp` 里写死：

```cpp
if (!normalizePose(raw, true, true, out)) { ... }   // 原文注释：真实单位未经真机确认
// «位置按 mm、姿态按 度，静态 XYZ（R = Rz*Ry*Rx）»
```

即假定 **mm + 度 + 静态 XYZ**。而 SDK 结构体用 m 或弧度也很常见。

### 5.2 操作步骤

**步骤 D1** — 协议选 `埃夫特（EfortSDK）`，IP 填机器人 IP（端口框会隐藏），点「连接」。

**步骤 D2** — 读取一次当前位姿，把 6 个数记下来，与示教器对比：

| 要判断的 | 怎么看 |
|---|---|
| 位置单位 | 读回是 `345.67` 量级（mm）还是 `0.34567` 量级（m）？ |
| 姿态单位 | 读回是 `90` 量级（度）还是 `1.57` 量级（弧度）？ |
| 姿态类型 | 是三个欧拉角，还是轴角/四元数？（单轴转 90° 试） |

**步骤 D3** — 单轴实验定欧拉顺序（每个只改一个量，改完重读）：

| 示教器设定 | 读回三个数的位置 |
|---|---|
| 只 `+90°` 绕第一个轴 | 90 在第几个？ |
| 只 `+90°` 绕第二个轴 | 90 在第几个？ |
| 只 `+90°` 绕第三个轴 | 90 在第几个？ |

**步骤 D4** — 抓 `runtime_<日期>.log` 里 SDK 调用的返回码/错误行（如果有）。

### 5.3 预期结果与判定

| 看到的 | 结论 | 我要做的事 |
|---|---|---|
| mm + 度，单轴实验与静态 XYZ 一致 | 假设成立 | 把注释里的「未经确认」改成「已确认 + 日期 + 现场证据」 |
| 位置是米 | `rawIsMillimeter` 该传 `false` | 改调用点（`normalizePose(raw, false, ...)`），补单测 |
| 姿态是弧度 | `rawIsDegree` 该传 `false` | 同上 |
| 顺序与静态 XYZ 不符 | 欧拉约定不同 | 加一个「欧拉顺序」枚举，在转矩阵处生效（纯逻辑 + 单测） |
| 是轴角/四元数不是欧拉 | 类型不同 | 加轴角→欧拉的换算（纯逻辑 + 单测） |
| 连不上 | SDK 许可/网络/地址串问题 | 记录 SDK 返回码后重试 |
