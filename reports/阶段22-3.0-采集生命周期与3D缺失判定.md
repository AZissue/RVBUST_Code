# 阶段 22：采集超时/相机生命周期 + 「2D 有、3D 无」仍报识别成功（3.0 安全项 2 + 现场缺陷）

> 2026-10-23。来源：
>
> 1. 用户列出的安全项第 2 条：采集超时后 UI 恢复，但 SDK 线程可能仍在相机里，
>    关窗等待会误判"已结束"，随后销毁相机对象。
> 2. 用户现场反馈：I3360（序列号 I1UM338B003）拍照时 2D 能识别到同心圆，
>    3D 没有点云（目标超出 3D 工作范围），程序仍然提示"识别成功"。
>
> 同批可测机型：I2120（I1GM112B652）、I3360（I1UM338B003）。

## 0. 一句话

「界面不再等」和「后台任务真的退出」现在是两个独立状态：超时只让界面恢复，
不再放行新的采集/关窗销毁；后台任务退出前，关窗宁可故意泄漏对象也不释放
worker 正在使用的内存。识别是否成功不再只看 2D：2D 找到但 3D 点云为空/无效
时返回 `No3d`，不提"识别成功"、不自动填 `0 0 0`、自动保存不落盘。

## 1. 问题与证据

### 1.1 采集超时与对象销毁（安全项 2）

代码核对（改动前）：

| 位置 | 问题 |
|---|---|
| `CameraManager::onCaptureTimeout()` | 置 `m_captureInProgress=false`，但 worker 可能仍卡在 `x1/x2.Capture()` |
| `CameraManager::captureFullFrame()` | 只检查 `m_captureInProgress`；超时后可再次 `setFuture()`，覆盖旧 watcher，旧 worker 失控 |
| `CameraManager::waitForCaptureIdle()` | `if (!m_captureInProgress || !watcher->isRunning()) return true;` —— 超时后第一项为假，直接返回"空闲" |
| `CameraManager::~CameraManager()` | 只无上限等待 preview future；不等待 capture/scan；`shutdown()` 设备锁 3 s 超时后仍 `m_impl.reset()` |
| `CameraManager::scanDevicesAsync()` | lambda 捕获裸 `this`、无 token；连续调用会覆盖仍在跑的 scan watcher |
| `CaptureFlow::waitForIdle()` | 同款短路：检测超时后 `m_detecting=false`，关窗不再等待 worker |
| `DeviceListDialog` / 主窗口刷新 | 刷新 future 持裸指针，对话框/窗口关闭时不等待 |

关键事实：RVC SDK 的 `Capture()` 无法取消。真正的卡死只能等它自己返回，
所以"等待"必须有上限，不能用无限等待掩盖问题（沿用项目红线：关窗有上限）。

### 1.2 I3360：2D 有、3D 无仍报成功

改动前三条识别路径的"成功"判定都只看 2D：

- Caliboard：`pixelXy` 非空且长度为偶数 → `Status::Ok`（`CaptureFlow.cpp` 原 265/294 行）；
- 同心圆原生缓存：`!nativePixels.empty() && !nativePoints.empty()` → `Ok`，但
  `nativePoints` 即使是全 0 也非空；
- 同心圆文件回退：只判 `res.first`（2D）非空。

另外 `DetectionEngine::firstValidPoint3d()` 只过滤 NaN，**`0,0,0` 被当作有效点**，
会把「相机目标点」自动填成 `0.000 0.000 0.000`，而保存校验只检查"3 个数值"。

## 2. 改动

### 2.1 新增纯策略 `src/logic/CaptureLifecycle.h`

状态只有三个布尔量，语义互相独立：

- `workerRunning`：线程池任务真的还在跑（唯一可信的"忙"）；
- `timedOut`：界面已放弃等待，迟到结果必须丢弃；
- `shuttingDown`：已进入释放流程，结果不再应用。

规则（全部有单测）：

- `canSubmit` = `!workerRunning && !shuttingDown`；
- `onTimeout` 不清 `workerRunning`，只置 `timedOut`，且只报一次；
- `onFinished` 返回 `apply`（超时/关闭后为 false）并清 `workerRunning`；
- `onShutdown` 保持 `workerRunning` 真实值；
- `onReleased` 只清 `shuttingDown` —— 释放结束允许再次连接，但旧 worker
  仍在跑时新采集继续被拒绝，直到 `onFinished` 真正收到它退出。

### 2.2 `CameraManager`

- 用 `CaptureLifecycle::State m_captureState` 取代 `m_captureInProgress` /
  `m_captureTimedOut`；
- `captureFullFrame()`：`canSubmit` 不通过时**明确报错**（"上一次采集仍未结束"
  /"相机正在释放"），不再静默丢弃点击；X1/X2 都未命中的异常路径会复位状态；
- `onCaptureTimeout()`：只报超时，workerRunning 保持；提示文案加"在后台采集
  退出前不能再次拍摄"；
- `onCaptureFinished()`：真完成才清 workerRunning；超时/关闭后的迟到结果丢弃并
  写日志；
- `waitForCaptureIdle()`：只看 `m_captureWatcher->isRunning()`；
- 新增 `waitForScanIdle()`、`hasRunningWorkers()`（capture/scan/preview/health）；
- `scanDevicesAsync()`：检查 shutdown、worker 前先读 token；扫描中再次请求改为
  `m_scanPending` 排队，扫描结束后自动执行（不再覆盖 watcher）；
- 析构：preview/capture/scan 都有上限等待（`SHUTDOWN_DEVICE_WAIT_MS`）；
  仍有 worker 在跑时**故意泄漏 `m_impl`** 并写日志，而不是销毁 SDK 对象；
- `shutdown()`：进入关闭时 `onShutdown`；结束 `onReleased`。

### 2.3 主窗口关窗

`closeEvent` 在 `shutdown()` 之后检查 `hasRunningWorkers()`：仍有 worker 卡在
SDK 里时，把 `CameraManager` 从父对象摘下来（`setParent(nullptr)`、`m_camera=nullptr`）
并写日志，让整个对象活到进程退出。正常关窗不受影响；这样 worker 不会访问已释放的
`this`/`m_impl`。`~MainWindow`、`aboutToQuit` 都已有空指针检查。

### 2.4 3D 缺失判定

- `DetectionEngine::isValidPoint3d()`：三轴均有限且不是 `(0,0,0)`；
  `countValidPoints3d()` 统计可用点；`firstValidPoint3d()` / `formatXyzForCard()`
  改用同一判据（不再把 `0 0 0` 当有效点）；
- `CaptureFlow::DetectResult` 新增 `valid3dCount` 与 `Status::No3d`；
- 统一状态规则 `CaptureFlow::classifyDetection(2D 数, 3D 数)`：
  2D ≤ 0 → `NoMarkers`；2D > 0 且 3D = 0 → `No3d`；否则 `Ok`；
- 三条识别路径都改用该规则；
- `applyDetectionResult()`：
  - `No3d` 仍画 2D 标记（让操作员看到"确实找到了标记物"），但按失败处理：
    tip + toast「识别不完整：未获取到 3D 点云」+ warning 日志，
    **不出现"识别成功"**，`detectionFinished(false)` → 自动保存跳过；
  - 记录里的 `marker_count` / `camera_error_pct` 仍按本次 2D 结果写入；
  - 手动保存保持可用（帧本身有效，戳点流程不受影响）——不违背
    "质量告警不拦截"红线：这里不是质量告警，是关键数据缺失；
- 黑底白圆部分点有 3D 时给**不拦截**的告警："仅 x/N 个圆点有有效 3D 坐标…"；
- `CaptureFlow::onCaptureReady()`：整帧点云为空时立即提示 + warning 日志
  （I3360 现场表现），不拦截保存；
- `CaptureFlow::waitForIdle()` 改为只看 watcher（同款短路修复）。

## 5. 人工验收清单（现场，I2120 / I3360）

### A. 3D 缺失不再报成功（I3360 = I1UM338B003）

1. 连接 I3360，把标定板放到 2D 能拍到、但明显超出 3D 工作范围的位置
   （太近/太远），拍照。
2. 预期：若整帧点云为空，左侧提示「采集完成，但 3D 点云为空…」，操作日志有
   对应 warning；保存按钮仍可用。
3. 点「识别」：2D 圆点/同心圆照常画在图上；提示为「识别到 N 个…但未获取到
   3D 点云…」，toast 为「识别不完整：未获取到 3D 点云」；日志是 warning；
   **不得出现**「识别成功」。
4. 「相机目标点」卡片**不得**被自动填成 `0.000 0.000 0.000`。
5. 若开启「识别后自动保存」：日志出现「自动保存跳过：本次识别未成功」，
   记录数不增加。
6. 把标定板移入 3D 范围后重拍、重新识别 → 恢复「识别成功」，卡片填真实坐标，
   保存正常。
7. 用 I2120（I1GM112B652）重复 1–6：同样行为（正常在 3D 范围内时应全部成功）。

### B. 采集超时 / 关窗上限

制造阻塞：拍照过程中禁用相机所在网卡（或断电/拔网线），等待 60 s 采集超时。

1. 超时后界面恢复；toast/日志提示超时，并说明后台采集退出前不能再次拍摄。
2. 马上再点拍照：预期提示「上一次采集仍未结束（可能已超时），请稍候再拍」，
   **不会**第二次进入 SDK/覆盖后台任务。
3. 恢复网卡/相机，让阻塞调用返回：日志出现
   `capture finished late (timedOut=1); result discarded`，之后可以正常拍照。
4. 在超时未恢复的状态下关窗：窗口应在有限时间内关闭（最多约 6 s：
   3 s 采集等待 + 3 s 设备锁）；日志出现
   `worker(s) still inside the SDK … deliberate leak`；进程退出无崩溃。
   若 worker 在等待内退出，则正常释放，不应出现该日志。
5. 正常拍照/识别/关窗：日志不出现 late / deliberate leak，设备释放成功。
6. 打开设备列表，快速连续点「刷新」多次（两台相机各试一次）：
   日志最多出现 `scan queued`，列表最终结果正确，不崩溃。
7. 关窗过程中断网：窗口仍能关闭，不卡死；下次启动能正常连接。

如出现崩溃/挂死，请保留 `logs/` 下当次运行日志（含 `[CAM]`、`[DEV]`、`[FLOW]`
行）反馈。

## 6. 风险与回退

- **行为变化**：超时未退出时再次拍照会被明确拒绝（原来静默忽略或覆盖）；
  关窗卡住时对象故意泄漏（只在异常路径，进程退出即回收）；
  `0,0,0` 不再算有效 3D 点，也不再自动填卡；2D 有 3D 无不再显示"识别成功"。
- **不改变**：质量告警仍不拦截；手动取点/戳点后保存仍可用；关窗仍有上限。
- **回退**：删 `CaptureLifecycle.h` 与测试，恢复 `m_captureInProgress`/
  `m_captureTimedOut` 实现；`classifyDetection` 恢复为只判 2D；
  `firstValidPoint3d` 恢复只过滤 NaN。

## 7. 没做

- 没有引入相机后端抽象/可注入的模拟相机（改动面太大）；真实 SDK 行为仍靠现场。
- 没有在 `CameraManager` 内部重构 worker 为持有独立 `shared_ptr` 状态；当前用
  "仍有 worker 时整对象延迟销毁"达到同样的安全边界。
- 3D 有效点阈值取"至少 1 个"，没有按覆盖率/面积做更细的判定；部分覆盖只告警。
