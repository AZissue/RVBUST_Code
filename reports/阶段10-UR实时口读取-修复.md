# 阶段 10 · UR 机器人位姿"读一次就不再变" —— 定位与修复

> 2026-10-10 · 现场三问 → 两问根因确定并修复，第三问的机制已坐实一半，残留一个
> **未证实**的独立可能。**本轮未做真机验证**（开发机没有 UR），只做了"先复现后修"的单测。

---

## 1. 用户现场报告（另一台工控机，包 = `HandEyeCalibrationTool_test2.1`）

连接 UR 成功、第一次"获取拍照位姿"正常，**移动机器人之后再点却没有变化**，只有
**断开重连**才有新值。由此提出三问：

1. 连上机器人后，**开关工具窗口变慢、打开时无交互**（"起初以为卡了，过一会儿才弹出来"）；
2. 连接期间**位姿只能读一次**；
3. **"戳点位姿"怀疑同样**。

用户给出的两条现场证据：任务管理器里**程序内存一直涨**；那台机器的 `runtime` 日志。

## 2. 根因（问题 2、3）：实时口是"推流"，而读取器每次只取一包

UR 实时口（30003）**不需要客户端请求**，控制器每控制周期（默认 8 ms）推一包：

```
[int32 BE 长度含自身][body]，body 内 actual_tcp_pose(6×double) 在偏移 200
```

而修订前的 `URRealtimeReader::readPose()` **每次调用只从 socket 取走一个包**
（读 4 字节长度 + 一个 body），从不排空：

| 时刻 | 实际发生 |
|---|---|
| 连接后 | 控制器持续推包，Qt 全**攒在接收缓冲里**（我们从不读走） |
| 第 1 次点"获取拍照位姿" | 取到缓冲里**最老的一包** ≈ 刚连上时的位姿 → 看起来正常 |
| 移动机器人后再点 | 只取走第 2 包 —— 它是"连上后约 8 ms"的位姿，**几乎等于上一次** |
| 继续点 | 每点一次只推进一个控制周期，**永远追不上当前** |
| 断开重连 | 新 socket、缓冲归零 → 取到的就是当前位姿 ✅ |

**戳点位姿走的是同一条路**（`RobotReadTouchPose` → 同一个 worker → 同一个 `m_urReader`），
所以**必然同病，同修一处即可**。

全仓核查：`readAll()` 只出现在 Modbus（`ModbusTcpReader`）与博纳斯（`NrcJsonReader`）
这两条**请求-应答**通道里；**UR 这条路一次都没有**。三条请求-应答通道**一行未动**。

### 2.1 为什么一直没被测出来

`tests/test_robot_pose.cpp` 的 `MockURServer`（修订前）**只推一包就关连接** —— 它模仿了
报文的"形状"，没有模仿"时间/连续性"。这与 `circle_truth` 的盲区是同一类错误：
**假件必须模仿真实世界的时序，而不只是格式**。

### 2.2 先复现，再修（修订前红 / 修订后绿）

扩展 `MockURServer`：新增 `startStreaming(intervalMs)` —— 每 `intervalMs` 推一包、
**x 递增**、**永不关闭**，与真控制器一致。新用例
`TestRobotPose::urRealtimeStreamsNewestPose`：

* **修订前（红）**：`second.xyz[0] >= 1100.0` 失败 ——
  `readPose returned x=200 mm (13 packets behind)`。
  即"已推 13 包，第二次读取仍返回第 2 包"，**现场症状在单测里复现了**。
* **修订后（绿）**：第二次读取返回**当前最新**位姿。

## 3. 根因（问题 1）：永不排空 → 内存持续增长

用户的现场证据是**内存一直涨**。这与"从不排空"完全吻合：

```
UR 实时口 125 Hz × 约 1.1 KB/包 ≈ 138 KB/s ≈ 9 MB/min ≈ 0.5 GB/h
```

涨到换页（工控机内存小则更快）之后，**整机**变慢 —— 开一个只是
`show()/raise()/activateWindow()` 三行的非模态窗口（`MainWindow.cpp:626`，面板启动时
就构造好了，`WA_DeleteOnClose=false`）也会"过一会儿才弹出来"。这解释了两件事：
为什么慢的**不只是某个功能**，以及为什么**在内存更小的工控机上更明显**。

## 4. 修法

只动 `src/logic/URRealtimeReader.*`，改成"**持续排空、只留最新**"：

1. `readyRead` → `drain()`：把已到达的数据全部解析，**只保留最后一包的位姿**。
   这样**没有人点读取时也在消费**，socket 缓冲不再堆积（第 3 节的内存问题随之消失）。
2. `readPose()`：**立即返回最新缓存**；只有"还没收到过任何一包"时，才按超时等待**首包**。
   顺带把点击路径上原来最多 1.5 s 的阻塞等待去掉了，界面更跟手。
3. 长度字段不可信时按 **1 字节重同步**（扫描游标一次 `remove`，不是逐字节搬移，
   避免 O(n²)），缓冲封顶 1 MiB。
4. **新增安全网**：数据流停了（控制器掉线、TCP 尚未察觉）超过 `timeoutMs` 就返回
   `Timeout`，**不再把过期位姿当当前值填进卡片** —— 对一把标定工具来说，
   悄悄记下一个过期位姿比报错更糟。用例 `urRealtimeStaleStreamTimesOut` 钉住。

**刻意不做的**：不用 `setReadBufferMaxSize` 之类的**回压**。对机器人的实时推流施加背压，
可能卡住控制器那一侧的发送 —— 那是机器人的事，不在我们的权限内。

## 6. 尚未确定的部分（**不要凭猜改**）

### 6.1 用户给的日志并不覆盖那次机器人测试

那份 `runtime` 日志里**一条机器人记录都没有** —— 既没有"机器人已连接（…）"
（`MainWindow.cpp:1351`），也没有"机器人 TCP 点读取成功 / 机器人位姿读取成功"
（`:1417` / `:1439`）。所以它来自**没有连机器人的一次运行**，不能用来判断
"机器人连上之后"的行为。

### 6.2 日志里确实有**与机器人无关**的 UI 卡顿

```
[11:46:21.228] [WATCHDOG] UI stall 998 ms (预览=否 拍照=否 3D上传=否 点数=0)   ← 启动，设备扫描
[12:22:51.144] [WATCHDOG] UI stall 687 ms (…)                                  ← 会话中，无机器人记录
```

启动那两次（998 / 922 ms）紧挨着 `scan finished … in 372/1039 ms` —— 设备扫描在 UI 线程，
属**启动开销**。但 **687 ms 那一次发生在一次完全没有机器人活动的会话里**，
说明**至少还有一个与机器人无关的 UI 阻塞源**。

**若换新包复测仍然慢**，按这个顺序查：

1. 内存是否**仍然在涨**？（按本修复，连上机器人后应保持平稳 —— 这是最直接的判据）
2. 卡顿那一刻在做什么（日志时间点 + 当时的操作）。特别留意工具页是否停在
   **"像素→3D + 离线图像"**：`ToolsPanel::showEvent → updateOfflineFreeze()`
   会触发 `MainWindow::onPixelTo3DOfflineImageRequested()`（`MainWindow.cpp:1117`），
   **在打开面板时同步做 QImage 解码 + 冻结主视图** —— 每次重开都会重解一次图。
