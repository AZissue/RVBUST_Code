# UR 位姿读回全零：根因、证据与修复（2026-10-10）

面向问题：核对 UR 位姿准确性时，机器人回零、示教器特征选「基座」，
示教器 TCP 显示 `(0, 193.74, 1000.96, 0, 2.224, 2.219)`，
程序读回 `(0, 0, 0, 0, 0, 0)`。

---

## 1. 结论

**这不是"解析出错"，是"读对了错的字段"**：`src/logic/URRealtimeReader.cpp` 里
`actual_TCP_pose` 的字节偏移写成了 `8 + 48*4 = 200`，真实位置是 `8 + 48*3 = 152`。
200 处是 **`actual_TCP_speed`** —— 机器人静止时它**恒为 0**，所以程序"成功地"读回
六个零，且不报任何错，一路写进卡片。

## 2. 证据链（为什么能断定，而不是猜）

1. **六个精确的 0 不可能是位姿。** 机器人静止时，关节角、关节电流、力矩、TCP 位姿
   全都非零（顶着重力）。静止时唯一恒为 0 的只有**速度类**字段。
2. **这些 0 是真实字段值，不是"读到包外"。** 修改前的实现先读长度字段并校验，
   `body.size() < kPoseOffset + kPoseBytes` 时返回 `ProtocolError`，**不会**给出 0。
   包长足够（30003 典型 1044–1108 字节），读的就是合法范围内的真实数据。
3. **该现象同时排除了另一种流传的字段布局。** 30003 有两种互相矛盾的公开描述：
   - A（q_actual 在前）：`time, q_actual, qd_actual, I_actual, actual_TCP_pose@152, actual_TCP_speed@200`
   - B（五个 target 块在前）：`…, I_target@152, M_target@200, q_actual@248, …, actual_TCP_pose@440`

   在 B 下 body 200 是 `M_target`（指令力矩）—— 顶着重力绝不可能为 0。**观测到的全零
   只在 A 下成立**，所以位姿在 152。（B 若成立，程序当初也不会读到零，而是读到力矩值。）
4. **字段网格是 `8 + 48k` 而不是 `48k`**：time 占 8 字节，把其后每个 6-double 字段
   整体挪了 8 字节。`tools/ur_realtime_probe.ps1` 早期版本只扫 48 对齐的块，
   因此把 152 处的位姿显示在 `[144]` 行的槽 1 里 —— 已改为扫全部 8 字节对齐位置。

## 3. 用户三条判断的核对

| 用户假设 | 结论 |
|---|---|
| 数据包解析错误 / 字节偏移 | **对**，且是本次全零的**唯一**原因 |
| 旋转向量被当成欧拉角 | **确实有这个问题，但是独立的另一件事**。若只是姿态表示错，xyz 仍会读出 `0 / 193.74 / 1000.96`，不会是全零 |
| 官方库 `Universal_Robots_Client_Library` 有没有用 | **有用，但不是这次症状的解药**。该库实现的是 **RTDE (30004)**；30003 自 URSoftware 3.5 起已被 UR 废弃并推荐 RTDE。RTDE 按**变量名**取字段，从根上消灭"偏移写错"这一类 bug，但需要握手，不是换个端口就行 |

示教器的数字自证单位是**弧度**：`√(2.224² + 2.219²) = 3.1417 ≈ π`，即 180° 旋转；
按"度"解释只有 3.14°。所以机器人回的 rx/ry/rz 是**轴角旋转向量、单位弧度**，
与代码里"原样透传"的处理一致（`HelpContent.h` 早已写明）。

## 4. 改动

### 4.1 偏移修复（`src/logic/URRealtimeReader.cpp`）

```cpp
constexpr int kPoseOffset = 8 + 48 * 3;   // 152（原为 8 + 48 * 4 = 200）
```

注释里写清推导依据与探针用法。头文件里那张写错的字段表也一并改正。

### 4.2 安全网：全零位姿不再当位姿

位姿块六个分量全为 0 → `parsePacket()` 判为不可信，`readPose()` 返回
`ProtocolError` 并给出中文文案（"很可能是字段偏移错位；请用
`tools/ur_realtime_probe.ps1` 抓一个真实数据包核对"）。物理上 UR 的 TCP 不可能
落在基座原点，所以这条判据不会误伤真实位姿。

### 4.3 单测的 mock 改到真实布局（`tests/test_robot_pose.cpp`）

`MockURServer` 原来按**错误的**偏移造包，且把位姿以外的字段全填 0 —— 这意味着
"偏移错一个字段"在测试里**看不出来**（错误的那个块也是 0）。现在：

- 布局改为真实的 `timestamp + q_actual + qd_actual + I_actual + actual_TCP_pose@152 + speed`；
- 位姿**周围**的字段填**有辨识度的非零值**（`actual_TCP_speed` 填 7.0, 8.0, …）；
  偏移若再错一个字段，读到的是 7000 mm，测试立刻红。

新增测试：
- `urRealtimeZeroPoseIsAnError` —— 全零位姿必须报错，不许当位姿；
- `urRtdeStreamsNewestPose` / `urRtdeUnavailablePoseIsRejected` —— 见下。

## 5. 新增协议：UR RTDE (30004)

用户提出改用 30004。可以，但要说清三件事：

1. **不是端口替换，是一套握手流程**：`REQUEST_PROTOCOL_VERSION(86)` →
   `SETUP_OUTPUTS(79)`（频率 + 变量名，按**名字**要 `actual_TCP_pose`）→
   `CONTROL_START(83)`，之后控制器按 `floor(125/频率)` 推 `DATA_PACKAGE(85)`。
   每个包是 `[uint16 BE 长度][uint8 类型][负载]`。
2. **RTDE 不会自动解决姿态表示问题**：`actual_TCP_pose` 同样是**轴角弧度**。
   标定环节拿它当欧拉角度数用的问题（`CalibrationService.cpp:200/321` 硬编码
   `poseType = 0`）依然存在，**需要单独决定怎么改**，本次未动。
3. **两条现场限制**（已写进界面提示与帮助）：机器人**同时只允许一个 RTDE 客户端**；
   本版**只实现协议 v2**（只支持 v1 的老控制器会得到明确报错，不会硬猜布局）。

实现：`src/logic/URRtdeReader.{h,cpp}`，协议分派新增 `protocol == 4`，
界面协议下拉新增「UR RTDE (30004)」，默认端口 30004。解析侧沿用 30003 那套
"持续排空、只留最新、超时即报错"的模型（不这么做会重现"位姿冻住"和内存上涨）。

## 6. 现场工具

`tools/ur_realtime_probe.ps1`（30003 抓包，打印每个 6-double 字段并与示教器数字比对）
与 `tools/ur_rtde_probe.ps1`（30004：跑完整握手、打印位姿、与示教器数字比对）。
两者都是**纯 ASCII** PowerShell（PS 5.1 会把无 BOM 的 UTF-8 当 ANSI 解析），
已在本地用假控制器/合成包端到端跑通。打包脚本现在会把 `tools\*.ps1` 一并放进交付包。
