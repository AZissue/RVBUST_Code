# UR 位姿读回全零：根因、证据与修复（2026-10-10）

> 本文件曾在 2026-10-10 上午记录过一版**推理得到的**根因（偏移 152、以及"RTDE 名字表
> 用 `'\0'` 结尾"）。当天下午用用户提供的虚拟机 UR（URSim `192.168.0.37`）与真机反馈
> 实测后，**152 这个值和当时的推理链被推翻**，下面的内容已按实测改写。被推翻的推理细节
> 保留在 §2.3，因为它是一个值得记的教训，不是一段可以删掉的历史。

面向问题：核对 UR 位姿准确性时，示教器特征选「基座」显示一组真实 TCP 位姿，程序读回
`(0, 0, 0, 0, 0, 0)`（真机）或连接失败（30004）。

---

## 1. 结论

两个互相独立的根因，都在**活控制器**上定位：

1. **30003 全零 = 位姿字段偏移错。** `actual_TCP_pose` 在 body **440** 字节
   （`8 + 48*9`），不是 200，也不是 152。之前那两版常量分别落在 `M_target` 和
   `I_target` 上；**控制器没有输出力矩时，这两个字段就是六个零**（真机静止且未跑程序
   正是这种状态），于是程序"成功地"读回零并写进卡片。
2. **30004 连不上 = RTDE 输出配方的变量名表发错。** 名字用 `'\0'` 结尾时，控制器把
   `'\0'` 当成名字的一部分，应答 `NOT_FOUND`；正确做法是**逗号分隔、末尾不留分隔符**
   （包长界定最后一个名字）。

## 2. 证据链

### 2.1 位姿在 440：量出来的，不是推出来的

在浏览器可用的虚拟机 UR 上抓一个 30003 包（`tools/ur_realtime_probe.ps1`），
按 `8 + 48k` 的网格打印每个 6-double 字段：

| body 偏移 | 字段 | 实测值 |
|---|---|---|
| 152 | `I_target` | `4.67e-17, -3.0798, 0.9399, -0.0962, 0.0648, 0` |
| 200 | `M_target` | `4.64e-16, -30.584, 9.334, -0.748, 0.504, 0` |
| **440** | **`actual_TCP_pose`** | **`-0.208714, -0.232900, 0.880178, 0.798727, 1.697482, -1.697482`** |
| 488 | `actual_TCP_speed` | 恰好六个 0 |
| 584 | `target_TCP_pose` | 与 440 相同（静止时目标 = 实际） |
| 680 起 | 电机温度 | `25.5, 25, 24.5, 24, 23.5, 23` —— 跨块边界，佐证网格 |

440 处的六个数正好是示教器（特征=基座）显示的 `-208.71 / -232.90 / 880.18 mm`、
`0.799 / 1.697 / -1.697 rad`，**最大分量差 0.004**（示教器只显示 2–3 位小数）。
包长 1220 字节，这个包已作为 fixture 内嵌进单测（见 §5）。

### 2.2 字段网格是 `8 + 48k`，不是 `48k`

time(8) 之后的每个 6-double 字段整体挪了 8 字节。`ur_realtime_probe.ps1` 早期版本只扫
48 对齐的块，会把真实位姿显示在 `[144]` 行的槽 1 里 —— 已改为扫全部 8 字节对齐位置。

### 2.3 被推翻的推理（教训，保留）

上午那版结论断言：*"布局 B（`I_target@152 / M_target@200`）下 200 处是 `M_target`，
顶着重力不可能为 0，所以观测到的全零只在布局 A 下成立，位姿在 152"*。

**这条推理是错的。** 实测：**控制器没有输出力矩时 `I_target`/`M_target` 就是 0**
（30003 的这两组是**指令值**，不是实测值；机器人静止且未运行程序时指令就是 0）。
所以"152/200 全零"两种布局都能解释，观测**无法区分**它们。这个常数只能靠量。

同类的第二种错：**自造的 mock 不能证伪自己写下的假设。** 当时的 `MockURServer` 按
错误偏移造包，且把位姿以外的字段全填 0，因此"偏移错一个字段"在测试里看不出来。

### 2.4 RTDE 名字表

对着真/虚拟控制器做对照实验，同一条 `SETUP_OUTPUTS` 负载：

- 变量名 = `"actual_TCP_pose\0"` → 应答 `NOT_FOUND`
- 变量名 = `"actual_TCP_pose"` → 应答 `VECTOR6D`（recipe id 1）

UR 官方库 `src/rtde/control_package_setup_outputs.cpp` 的写法是
`variables += (piece + ","); variables.pop_back();` —— 逗号连接、**末尾不留分隔符**。
30003 的"读一次就不再变"与这里无关，但 30004 的"连接失败"就是这一条。

## 3. 用户三条判断的核对

| 用户判断 | 结论 |
|---|---|
| 数据包解析错误 / 字节偏移 | **对**，且是 30003 全零的唯一原因（只是**值**不是 152 而是 440） |
| 旋转向量被当成欧拉角 | **确实存在，但是独立问题**。若只是姿态表示错，xyz 仍会读出真实值，不会是全零。示教器的数字自证单位是**弧度**：`√(2.224²+2.219²)=3.1417≈π`，即 180° 旋转（按"度"解释只有 3.14°） |
| 官方库 `Universal_Robots_Client_Library` 有没有用 | **有用**。它实现的是 **RTDE (30004)**：按**变量名**取字段，从根上消灭"偏移写错"这类 bug。30003 自 URSoftware 3.5 起已被 UR 废弃并推荐 RTDE —— 但换端口要写一套握手 |

## 4. 改动

### 4.1 偏移修复（`src/logic/URRealtimeReader.cpp`）

```cpp
constexpr int kPoseOffset = 8 + 48 * 9;   // 440（原为 8 + 48*4 = 200，一度改为 8 + 48*3 = 152）
```

注释与头文件里那张字段表改成实测得到的经典布局（440 在位姿、488 是速度、584 是目标位姿）。

### 4.2 解析判据：全零与非有限值都不当位姿

- **非有限值**（NaN/Inf）→ 判为错位，返回 `ProtocolError`；
- **六个精确的 0** → 同样报错（UR 的 TCP 不可能落在基座原点）。
  物理上不会误伤真实位姿，但它把"静默写错值"变成"明确报错"。

> 注：真机上这次"依旧全零"的读数与这条判据不一致 —— 判据命中时界面走的是
> `poseReady(kind=false, …)` 分支，只会弹提示并记日志（`MainWindow.cpp:1407`），
> **不会**把零写进卡片。所以现场那次看到的如果是六个 0，说明用的可能是带判据之前的包，
> 或读的是卡片里残留的旧值。**待 test2.4 现场确认**（清单见 STATUS.md 之十二）。

### 4.3 RTDE 输出配方（`src/logic/URRtdeReader.cpp`）

```cpp
QByteArray setup = beDouble(kFrequencyHz);
setup.append(kPoseVariable);          // 无尾随 '\0'；多变量时用 ',' 连接
```

## 5. 单测：两个 mock 都改成"能吃下并证伪"

这是本次真正补上的缺口 —— 上一版之所以让两个 bug 都溜过去，是因为 mock 只会
**确认**实现里写下的假设：

- **新增真实抓包回归** `urRealtimeReadsCapturedPacket`：把虚拟机抓到的 **1220 字节包
  base64 内嵌**进 `tests/test_robot_pose.cpp`，断言解析结果 = 示教器数字（1e-6 / 1e-9）。
- `MockURServer` 改到经典布局，位姿**周围字段填 ≥0.5 m 的哨兵值**（原来填 0，偏移错一格
  也测不出来）。
- `MockRtdeServer` 现在**真的解析名字表**：频率是大端 double、名字以逗号分隔、不带尾随
  分隔符，否则回 `NOT_FOUND`。原来它**无条件**回 `VECTOR6D`，所以 NUL bug 测不出来。
- **做实验证明测试有牙**：把 `kPoseOffset` 改回 152 → 抓包回归**失败**
  （`qAbs(pose.xyz[0] - (-208.71414676390157)) < 1e-6` 返回 FALSE）；把 `'\0'` 加回
  RTDE 名字表 → `urRtdeStreamsNewestPose` **失败**（`connect()` 返回 FALSE，报 NOT_FOUND）。
  两次都已还原。

## 6. 活控制器实测（跑的是工程实际代码）

把 `URRealtimeReader.cpp` + `URRtdeReader.cpp` + `RobotPose.cpp` 临时编成控制台程序，
连 `192.168.0.37`（不是脚本副本，是交付用的同一份源码）：

- `30003` → `x=-208.7141 y=-232.9000 z=880.1776 mm rx=0.798727 ry=1.697482 rz=-1.697482`
- `30004`（RTDE）→ 同上，recipe id 1、类型 `VECTOR6D`
- 空闲 2 s 内包计数**自己涨**（30003 ≈433 Hz、RTDE ≈108 Hz）而位姿稳定 ——
  「位姿冻住 / 内存上涨」在真控制器上也不复现。

## 7. 现场工具

`tools/ur_realtime_probe.ps1`（30003：打印整张字段表，并**指出与示教器数字匹配的是第几个
块**）与 `tools/ur_rtde_probe.ps1`（30004：完整握手 + 位姿比对）。两者都是**纯 ASCII**

一并放进交付包。

## 9. 待办（本次未做）

- **姿态表示**：UR 给的是**轴角弧度**，HandEyeSDK 只有 euler/四元数/矩阵、**没有轴角**；
  标定环节 `CalibrationService.cpp:200/321` 硬编码 `poseType = 0`（欧拉）、`isPoseDegree`
  来自界面下拉 → 会把"弧度轴角"当"欧拉角度数"算且不报错。需决定"读进来就转"还是"只在
  标定边界转"，以及卡片是否记录协议/单位来源。
- **RTDE 协议 v1** 未实现（只支持 v1 的老控制器会得到明确报错）。
- 现场复测清单见 `STATUS.md` 之十二。
