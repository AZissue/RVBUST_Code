# 阶段 16 — 架构收敛：控制器 + 状态机（第 1 批）

> 用户提出：项目已从「清晰分层」滑向「总控大对象 / 设备大类」。
> 目标：**保留现有功能行为不变**，把 MainWindow 收敛成 UI 组装与事件转发，
> 把状态机与领域服务拆出去，后续扩展不再往 MainWindow 里堆。
>
> **本轮只做第 1 批（低风险、可独立验证的两个接缝），只本地提交，未打包、未推送。**

## 1. 为什么不是"按清单一次性建 5 个 Controller"

评审建议的 ApplicationController / CameraController / RobotController /
CaptureWorkflowController / CalibrationController 如果一次性建出来，其中会有一半只是
**把 MainWindow 的方法换个文件、再回调 MainWindow 改控件** —— 层数增加，耦合没减少。
本轮按"**这个状态/线程现在有没有第二个入口**"来选接缝：

- 有独立线程和网络对象的（机器人通道）→ 值得独立；
- 有三个以上写入点的状态（预扫描 / 设备缓存 / 待连接）→ 值得独立；
- 纯 UI 编排（弹设备列表、toast、busy 文案）→ 留在 MainWindow，不包一层转发。

## 2. 本批改动

### 2.1 `app/RobotController.{h,cpp}`（新增 358 行）

从 `MainWindow.{h,cpp}` 整体搬出：

| 内容 | 原位置 | 现位置 |
|---|---|---|
| `RobotReadKind` 枚举 | MainWindow.h | RobotController.h |
| `RobotWorker`（四个 reader + socket 协议分派 + 模拟位姿） | MainWindow.h/.cpp | RobotController.h/.cpp |
| `QThread` 创建/启动/有界停止 | MainWindow 构造/析构/closeEvent | `RobotController::shutdown()` |
| 逻辑状态 `connected / simulated / autoRead` | MainWindow 三个 bool | RobotController 私有字段 |

接口：`connectToRobot / disconnectRobot / simulateConnect / readPose /
setAutoRead / isConnected / isSimulated / autoRead / shutdown`，
信号只有 `connectFinished` 与 `poseReady`。
MainWindow 保留的全是 UI：状态文案、tip、日志、卡片填充、按钮显隐。

线程模型**逐字保留**：所有阻塞调用仍经排队调用进入 worker 线程；
AutoConnection 把结果排队回 UI 线程；`shutdown()` 仍是有界（3 s）+ 幂等。
唯一的实现细节变化：UI → worker 的投递改用
`QMetaObject::invokeMethod(worker, lambda, Qt::QueuedConnection)`（带上下文对象），
不再走 MainWindow 的四个转发信号，参数也不需要元类型注册。

### 2.2 `app/CameraConnectionFlow.{h,cpp}`（新增 122 行）

把三个散落在 MainWindow、由多个入口写入的标志收进一个状态机：

| 原字段 | 含义 |
|---|---|
| `m_preScanning` | 启动预扫描是否在跑 |
| `m_cachedDevices` | 上次枚举结果 |
| `m_connectRequested` | 预扫描期间用户已点「连接」 |

接口：`preScan()`（启动）、`requestConnect()`（用户点连接）、
`refreshCache()`（释放相机后重扫）；信号 `scanStarted` / `devicesReady` / `rescanned`。
MainWindow 只剩：busy 文案、设备列表对话框、`initWithDeviceSerial()`、toast 与日志。

行为保持：
- 预扫描期间点连接 → 只记待办，扫描完成后自动弹列表；
- 有缓存 → 直接用缓存，不再重扫；
- 无缓存 → 重新枚举，完成后清 busy 再弹列表；
- 释放相机 → 清缓存 + 重扫，日志文案不变。

**连接本身仍留在 MainWindow**：RVC 设备对象必须在之后驱动预览的线程（UI 线程）创建，
把它藏进控制器只会把线程约束变得不透明。

## 3. 量化结果

| 文件 | 前 | 后 |
|---|---:|---:|
| `src/app/MainWindow.cpp` | 2368 | 2164（−204） |
| `src/app/MainWindow.h` | 334 | 260（−74） |
| 新增独立单元 | — | 480（RobotController 358 + CameraConnectionFlow 122） |

MainWindow 减少的不只是行数：机器人的**线程生命周期、socket 亲和性、连接状态**
现在只有一个所有者；相机预扫描的三个标志也只有一个写入者。

## 5. 后续路线（按收益/风险排序，尚未实施）

| 批次 | 内容 | 风险 | 说明 |
|---|---|---|---|
| 2 | `CalibrationController`：`onCalibrate` + QFutureWatcher + 会话数据收集 | 低 | 已是异步；结果经信号回 UI |
| 2 | `CameraFrameCache`：`lastGrid / lastCorrespond / nativeMarkerResult / releaseFrameCaches` | 低 | 纯缓存值对象，可从 CameraManager 委托 |
| 3 | `CameraHealthMonitor`：health/reconnect 两个 timer | 中 | 与设备锁、重连策略交织，需保持锁顺序 |
| 3 | `GuidancePresenter`：位姿引导 + 质量报告文案 | 低 | 纯文案/判定，可补单测 |
| 4 | `CameraCapturePipeline`：capture/preview 从 CameraManager 拆出 | 高 | 与 `m_rvcMutex`、yieldGen 强耦合，**不建议近期动** |
| 4 | 全局 `SystemState` | 中高 | 只有把所有标志都迁过去才有意义；否则是第二份真相 |

**明确不推荐**：
- 为 `onCapture / saveFromCards` 再包一层 `CaptureController` —— 它们已经只有转发到
  `CaptureFlow` 的几行，增加的是层数不是边界；
- 按模块复制 `RuntimeLog` 的"分级日志器" —— 当前全局日志是现场诊断的证据链，
  拆散后跨模块事件反而更难按时间线阅读。诊断分类可以加，但不要替换落盘路径。

## 6. 人工验收清单（请按顺序操作并反馈）

1. 启动程序，等右下角/侧栏提示稳定（预扫描完成）。
   点「连接相机」→ **预期**：不再出现"正在搜索相机..."，直接弹设备列表。
2. 重启程序，在预扫描完成前立刻点「连接相机」→ **预期**：显示"正在搜索相机..."，
   扫描结束后**自动**弹设备列表（不需要再点一次）。
3. 选中相机连接；再断开；相机维护 →「释放相机」→ **预期**：
   日志出现"释放后重新扫描：发现 N 个设备"，下次连接直接弹列表。
4. 工具页 → 机器人 →「模拟连接」→ 点「拍照位姿」/「戳点位姿」
   → **预期**：卡片按当前标定模式填充；30 秒内不出现界面冻结。
5. 有真机时：任选一种协议连接 → 连接成功提示与协议名正确；读位姿正确；
   **预期**：连接/读取期间 UI 可拖动，不触发 `[WATCHDOG] UI stall`。
6. 勾选「自动读取机器人位姿」→ 重启 → **预期**：勾选状态保持；拍照前自动读仍生效。
7. 关闭程序 → **预期**：无卡顿、无崩溃；runtime 日志无
   `[ROBOT] worker thread still busy after 3000 ms`。
