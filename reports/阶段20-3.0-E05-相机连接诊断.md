# 阶段 20 · 3.0 E-05：相机连接失败的可执行诊断

> 2026-10-22 · 状态：**代码与单测完成**，界面待人工验收
> 对应：`reports/3.0-规划.md` §2.4 E-05「相机连接失败提示过于通用——
> 未区分驱动/网段/占用原因」
> 分支：D 工作区 `HandEyeTools-3.0`（AICode `handeye-tools-3.0-sync` 同步）

---

## 0. 一句话

连接失败不再只剩一句「相机连接失败」：现在分成 **SDK/驱动、没枚举到、枚举报错、
掉线、读信息失败、型号不支持、占用、网段不可达、IP 冲突、一般 Open 失败** 十类，
每类给一句短标题（toast）+ 一段可执行的排查顺序（左侧提示与日志）；网段类还会
把**相机 IP 和本机每张网卡的地址/掩码**直接列出来。设备列表在点「连接」之前
就能显示 占用 / 不可达 / IP 冲突。

---

## 1. 为什么改这里

现场只看到「相机连接失败」时，三种最常见原因的处理动作完全不同：

| 实际原因 | 现场该做什么 | 旧提示给出的信息 |
|---|---|---|
| 被占用（上一次没释放 / 厂商软件开着） | 等 10 秒、关掉占用进程、释放相机 | 无 |
| 网段不对（GigE 最常见） | 改网卡 IPv4 / 改相机 IP | 无 |
| 驱动/SDK 没装好 | 重装驱动或补运行时 DLL | 无 |

旧代码其实已经有 `CameraRelease::classify()`（3.3 的文本关键字规则）与
`operatorHint()`，但：

- `initWithDeviceSerial()` 里有 4 条失败路径直接 `emit` 原始字符串
  （「未找到指定设备」「无法获取设备信息」「设备不支持 X1 或 X2」）；
- GigE 状态只用了 `In_Use` 一个值，`Not_Reachable`（网段）与 `Conflict`
  （IP 冲突）被丢掉了；
- 主界面在失败后固定弹一句「相机连接失败」，把左侧提示里的细节盖住；
- 扫描结果为空时只提示「请检查连接」，没有告诉操作员本机有哪些网段。

---

## 2. 判据从哪来（没有猜 SDK 语义）

全部来自 SDK 头文件里写明的状态，或代码里本来就存在的证据：

- `third_party/RVC/include/RVC/RVC.h`：
  `NetworkDeviceStatus_OK / Not_Reachable / In_Use / Conflict` 四个值，
  以及 `GetNetworkConfig()` 返回的相机 IP / 掩码；
- `DeviceInfo.type`：USB 相机没有网络状态，不能判成「不可达」；
- `RVC::SystemInit()` 的返回值与异常（驱动/运行时就绪与否）；
- 3.3 已有的错误文本关键字规则（`CameraRelease::classify`），新分类**委托**
  它，避免两套说法；
- 本机网卡：`QNetworkInterface`（系统事实，不是猜测）。

> 未做的事：没有尝试识别"具体是哪个驱动没装"。那种判断需要读设备管理器/驱动
> 数据库，超出本工具范围，也没有可靠 SDK 证据。

## 3. 改动

### 3.1 新增纯逻辑（可单测）

| 文件 | 内容 |
|---|---|
| `src/logic/CameraConnectDiagnosis.h` | `Cause` 枚举、`Evidence` 事实包、`diagnose()` 判定顺序、`retryCanHelp()`、`headline()` 短标题、`advice()` 完整建议、`anyHostOnSubnet()` / `ipv4MaskValue()` 网段判断。header-only，不依赖 RVC/UI |
| `src/logic/CameraNetworkInventory.h` | `hostIpv4Subnets()`：本机 IPv4 网卡快照，格式 `以太网=192.168.0.10/255.255.255.0`（薄封装，不做单测） |

判定顺序 = 排查顺序：SDK → 枚举报错 → 没枚举到 → 设备丢失 → 读信息失败 →
型号不支持 → GigE 硬状态（占用 / 不可达 / IP 冲突）→ 文本关键字 → 未知。

### 3.2 CameraManager

- `deviceInUse()` → `readLink()`：一次读到 `NetworkStatus` + 相机 IP/掩码；
  设备列表的 `DeviceEntry` 用 `network` 取代 `occupied`。
- 所有连接失败出口统一走 `emitConnectFailure()`：补本机网卡（仅需要的两类）、
  写 `connect DIAG:` 日志行、发 `cameraError(advice)`、记 `lastConnectHeadline`
  给 toast。
- `connectFirstAvailable()`：枚举报错与"枚举成功但 0 台"分成两类；
  多台设备都读不出信息时报「读信息失败」而不是「没插相机」；删掉了最后
  那句会盖住具体原因的「无法连接任何相机设备」。
- 行为修正：`initWithDeviceSerial()` 以前忽略 `RVC::SystemInit()` 的返回值
  （只有异常才报错），现在与 `listDevices()` 一致，返回 false 也按
  SDK 未就绪处理。

### 3.3 界面

- `MainWindow`：连接失败 toast 显示原因短标题；扫描为空时，左侧提示列出
  本机网卡地址/掩码并给出"同网段"检查顺序。
- `DeviceListDialog`：状态列从「占用 / 可用」扩展为
  「占用 / 不可达（查网段）/ IP 冲突 / 可用」；仍然只有"占用"不可选中。
- `HelpContent`：常见问题里"相机明明插着"那条改成按状态列排查，并指向
  RVCManager 的「一键配置」修网段。

### 3.4 文案定稿（现场反馈）

网段不匹配时，原先把操作员引到"改网卡 IPv4"，但现场装相机用的就是
RVCManager，那里本来就有「一键配置」和拍摄参数调试。定稿文案改成先指
RVCManager、再给手动改网卡作为备选：

> 当前 RVC 相机与网卡不在同一网段：可以在 RVCManager（RVC 厂商工具）里用
> 「一键配置」把相机配到本机网段，拍摄参数也在那里调试。也可以手动把网卡
> IPv4 改到与相机同网段（例如相机 192.168.0.10/255.255.255.0 → 网卡
> 192.168.0.100/255.255.255.0）。

同一套说法同时用于「没枚举到任何相机」「相机网络不可达」「IP 冲突」三条
建议（见 §8 关于不内置一键配置的决定）。

## 4. 测试

新增 `tests/test_camera_connect_diagnosis.{h,cpp}`，19 个用例（注册于
`tests/CMakeLists.txt` 与 `test_main.cpp`）：

- 判定优先级：SDK 失败压过"没设备"；枚举报错 ≠ 没设备；掉线 ≠ 没插；
- 四个 GigE 状态各归一类；
- 文本回退：busy / unsupported / SDK 错误 / 空文本；
- 只有 占用 / Open 失败 / 未知 允许重试；
- 每个 Cause 都有非空且互不相同的短标题、非空建议，且建议里不许残留 `%1`；
- 网段建议：列出本机网卡；不同网段时指向 RVCManager 的「一键配置」并给出手动
  改网卡的例子；同网段时说"网线/防火墙"且**不**提「一键配置」；读不到相机 IP
  时不做"不同网段"的断言；
- `anyHostOnSubnet()`：带名字/不带名字、点分掩码/前缀写法、坏数据跳过、
  用相机掩码比较、空输入不猜。

## 6. 人工验收清单（界面不做自动化测试）

| # | 操作 | 预期 |
|---|---|---|
| 1 | 不接相机 → 点「连接」 | toast：「未找到相机」；左侧提示列出本机网卡（名称=IP/掩码）与 ①–④ 检查顺序 |
| 2 | 接相机但网卡不同网段 → 打开设备列表 | 该行状态为「不可达（查网段）」，黄色；仍可选中 |
| 3 | 上一步点确定连接 | toast：「相机网络不可达」；左侧提示含相机 IP/掩码、本机网卡，并指向 RVCManager「一键配置」，另给手动改网卡的例子 |
| 4 | 让厂商软件占着相机 → 连接 | 设备列表显示「占用」且不可选；若从其它入口连接，提示含"已自动重试 N 次"与"等待 10 秒" |
| 5 | 正常连接一台相机 | 连接成功，不再出现任何失败 toast |
| 6 | 按 F1 → 常见问题 → "相机明明插着" | 能看到按「占用 / 不可达 / 一条设备都没有」三类排查的说明，不可达那条提到 RVCManager「一键配置」 |
| 7 | 连接失败后看运行日志 | 有一行 `connect DIAG: cause=… sdk=… enum=… net=… retries=… ip=…` |

> 第 2/3 条需要能改网卡的机器；没有现场条件时可跳过，但第 1、5、6、7 条
> 在任何机器上都能验。

## 7. 风险与回退

- **文案即行为**：没有改任何连接/重试的**判定结果**，只是把已有事实说得更清楚。
  唯一的行为变更是 `SystemInit()` 返回 false 时不再继续（与扫描路径一致）。
- 若现场反馈提示过长：`headline()` 与 `advice()` 是分开的，缩短 advice 不影响
  toast；不建议退回单一文案。
- 回退：删除 `CameraConnectDiagnosis.h` / `CameraNetworkInventory.h` 与
  `emitConnectFailure()` 调用，恢复各 `emit cameraError(...)` 原字符串即可；
  设备列表的 `network` 字段回退为 `occupied`。

## 8. 没做 / 下一步

- **没有在相机列表加"一键配置 IP"**。SDK 有 `RVC::AutoConfigureNetwork()`，但按
  头文件说明它是"把所有非 OK 状态的设备配好"，不是"配我选中的这台"：
  - 会连带改 LightMachine —— 客户机上的光源配置不是本工具该动的；
  - `In_Use` 也算非 OK —— 别的程序正在用的相机可能被改 IP；
  - 自动挑的地址未必符合现场固定 IP 的约定，事后没人知道改过；
  - 多网卡机器上"配到哪个网卡"没有唯一答案。
  本工具的定位是标定辅助，改的是采集/标定数据，不该悄悄改设备网络。下一步
  交给 RVCManager（厂商工具，操作员熟悉，顺便能调拍摄参数）是更稳的分工。
  如果以后确实要写，应该用 `SetNetworkConfig()` 只改**用户明确选中的那一台**，
  改前显示 旧 → 新 并二次确认，绝不用 `AutoConfigureNetwork()`。
  可考虑的折中：设备列表只读显示"相机 IP / 本机网卡 / 建议地址"并支持复制，
  写入仍交给 RVCManager。
- 没有把「驱动是否安装」做成自动检测（缺可靠 SDK 证据，见 §2）。
- 控制台/机器人连接的错误提示是另一套（`RobotController`），本轮没动。
- 现场若拿到「某类提示对不上实际原因」的日志，优先补**该类**的判据与用例，
  不要在文本里加模糊形容词。
