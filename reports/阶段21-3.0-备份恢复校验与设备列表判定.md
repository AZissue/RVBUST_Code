# 阶段 21：备份恢复校验 + 设备列表判定统一（3.0 安全项 1/3/4）

> 2026-10-23。来源：用户列出的 5 项安全/一致性问题，本阶段处理第 1、4 项
> （备份恢复）与第 3 项（设备列表双击行为）；第 2 项（采集生命周期）见 §8.1
> 的结论与方案（待实施）；第 5 项（机器人流程）按用户决定改为独立文件，
> 见 §8.2 与 §9。

## 0. 一句话

恢复备份不再"信 JSON 就改状态"：版本/必需字段/逐条记录/路径归属全部先校验，
任何一项不通过都保持当前会话原样；删除记录文件前再查一次归属。设备列表的
单击、双击、确定按钮改用同一条可连接判定。

## 1. 问题

### 1.1 备份恢复可能删掉会话目录外的文件（第 1 项）

`DataManager::loadBackup()` 原来直接信任文件内容：

- 相对路径 `../..` 不拦，绝对路径原样收下（`resolve` 里 `isAbsolute → 直接返回`）；
- 恢复后，`removeLast()` / `clearAll()` 按记录里的路径 `QFile::remove()`；
- 于是一份被改过的备份 → 恢复 → 撤销，就能删掉会话目录外的任意文件。

### 1.2 格式校验不足（第 4 项）

- 没有版本检查；
- `records` 缺失时 `root["records"].toArray()` 得到空数组，**被当成"成功恢复 0 条"**，
  把当前内存记录替换为空；
- 模式字段缺失时 `toBool()` 静默取 false，悄悄改掉 in-hand / marker 模式；
- 失败只返回 `false`，界面上只有一句"请确认文件格式正确"，没有原因。

### 1.3 双击与单击判定不一致（第 3 项）

- 单击：`NetworkStatus::InUse` 才禁止选中（item flags 去掉 `ItemIsSelectable`）；
- 双击：`statusItem->data(Qt::UserRole).toBool()`。UserRole 存的是
  `static_cast<int>(dev.network)`（0=Ok, 1=NotReachable, 2=InUse, 3=Conflict,
  -1=Unknown），`QVariant(int).toBool()` 对**所有非 0** 都返回 true ——
  于是"不可达""IP 冲突""未知"在双击时全被当成禁止，和单击/确定按钮矛盾。

## 2. 改动

### 2.1 新增纯逻辑 `src/logic/BackupDocument.h`

| 函数 | 作用 |
|---|---|
| `parseForSession(json, sessionDir)` | 校验版本（当前 1）、`eye_in_hand`/`marker_type` 为 bool、`records` 为数组、逐条 `index ≥ 1` + `png_path`/`ply_path` 非空，并把路径解析到会话目录内；任一失败返回可读原因 |
| `resolveStoredPath()` | 相对路径按会话目录拼接；绝对路径也接受（兼容旧备份/手工编辑），但必须落在会话目录内 |
| `isWithinDir()` | 两端都规范成绝对路径后比较（存在的路径用 `canonicalFilePath`，解析符号链接；Windows 大小写不敏感）；`s1` 与 `s10` 这种前缀相同但不是后代的情况不会误判 |
| `cleanStoredPath()` | 反斜杠、`./`、`a/../b` 统一折叠 |

不检查图片文件是否存在：备份可能只带了 JSON，图片稍后补；删除前还有第二次
归属校验兜底。

### 2.2 `DataManager`

- `loadBackup()`：先完整解析（含全部路径），全部通过后才一次性提交
  `m_eyeHand / m_calibType / m_saveDir / m_backupDir / m_records`。失败时当前
  会话**一个字段都不变**。
- 新增 `lastLoadError()`：失败原因（"备份版本 99 不受支持"、"第 2 条记录的
  png_path ../../outside.png 不在会话目录内"）。
- `removeLast()` / `clearAll()`：删除前经 `removeRecordFile()`，`isWithinDir()`
  不通过就拒绝并写警告日志 —— 不依赖导入时的校验。
- `findLatestBackup()`：候选文件用**同一个** `parseForSession()` 判定"完整"，
  不会再挑出一个 `loadBackup()` 会拒绝的文件。
- `SettingsDialog`：恢复失败弹窗带具体原因，并说明"当前会话未被修改"。

### 2.3 设备列表判定统一

- `CameraConnect::connectable(NetworkStatus)`：只有 `InUse` 不可连接；不可达 /
  IP 冲突 / 未知都允许尝试（操作员可能刚在 RVCManager 里改好）。
- `DeviceListDialog` 的 item flags、`onSelectionChanged`、`onDoubleClicked`
  三处都调用它；双击改为按 int 读取状态后再判定。

## 6. 风险与回退

- **兼容性**：版本仍是 1；会话内绝对路径继续可用；只有"结构性不合格/越界"
  的备份被拒（这类备份按原逻辑恢复后本来就有删文件风险）。
- **记录路径来源**：`addRecord()` 仍接受任意路径（采集流程只传会话内路径）。
  若将来有入口传入会话外路径，备份里会存成 `../../…`，恢复时会被拒绝——
  这是有意行为，不静默丢弃记录。
- 回退：删除 `BackupDocument.h` 与 `m_lastLoadError`，恢复 `loadBackup()` 旧实现；
  设备列表三处判定恢复各自写死的状态判断。

## 7. 没做

- 没有给"备份里的图片文件是否存在"做校验（见 §2.1）。
- 没有改 `addRecord()` 的入参契约（见 §6）。

## 8. 第 2、5 项的结论

### 8.1 第 2 项：采集超时与相机对象生命周期 —— 已确认存在，待实施

> 2026-10-23 已实施，见 `reports/阶段22-3.0-采集生命周期与3D缺失判定.md`。
> 实施时补充了一处原方案没写到的点：只泄漏 `m_impl` 不够——worker 调用的是
> 成员函数，`this` 本身也会被释放，所以主窗口在仍有 worker 时把整个
> `CameraManager` 摘下来活到进程退出。

代码证据（`src/logic/CameraManager.cpp`）：

- `onCaptureTimeout()` 置 `m_captureInProgress = false`，但 worker 可能仍卡在
  SDK 调用里；
- `captureFullFrame()` 用 `m_captureInProgress` 做守卫 → 超时后可以再提交，
  `m_captureWatcher->setFuture()` 覆盖 watcher，旧任务继续写临时文件；
- `waitForCaptureIdle()` 先看 `!m_captureInProgress` → 超时后直接返回 true，
  关窗不再等 worker；
- 析构只等 preview future；`shutdown()` 设备锁 3 s 超时后会跳过 Close/Destroy，
  但随后 `m_impl.reset()` 仍然销毁 worker 正在使用的 `RvcImpl`（UAF）；
- `scanDevicesAsync()` 的 lambda 捕获 `this`，无 token、析构不等待；
  `DeviceListDialog` 的刷新 future 也持有相机指针，对话框销毁不等待。

建议方案（保持"关窗有上限"，不改成无限等待）：

1. 引入纯策略 `CaptureLifecycle`（`src/logic/`）：区分"界面不再等"（TimedOut）
   与"worker 已退出"（watcher `isRunning()==false`），录入
   submit/timeout/finish/shutdown 事件，单测覆盖超时后重复拍摄、关窗等待上限、
   扫描中断销毁的组合；
2. `captureFullFrame()` 在 `watcher->isRunning()` 时明确拒绝新任务并告知原因；
3. 超时不清"任务在跑"的标记，只置 TimedOut；`onCaptureFinished()` 收到真完成
   才清状态并丢弃超时结果；
4. `waitForCaptureIdle()` 只看 `watcher->isRunning()`；
5. 析构顺序：preview 等待 → scan 等待（有界）→ `shutdown()`（已有界）→
   若 capture/scan 仍在跑，**故意泄漏 `m_impl`** 并写日志，而不是 `reset()`；
6. 扫描 worker 入口检查 token，`scanBusy` 期间拒绝重复扫描。
   真实 SDK 的阻塞行为仍需现场验证（模拟后端只能验策略，不能验 SDK）。

### 8.2 第 5 项：机器人程序是否进会话备份 —— 没有，丢失是必然

结论（2026-10-23 核对代码）：

- 备份 JSON 只有 `version / eye_in_hand / marker_type / records`；
- `RobotProgram::saveToFile/loadFromFile` 已实现且有单测，但**全项目没有任何
  UI 调用**（即规划里的 R-03）；
- 所以：关程序 → 程序节点列表丢失；从设置恢复备份 → 只恢复记录与模式，
  程序仍然丢失。

用户决定：机器人流程**不并入会话备份**，按独立文件 `*.program.json` 单独
保存/导入。理由：流程是"标定流程"而不是"某次采集的数据"，跨会话复用；
混进备份会让恢复动作同时改机器人侧的执行内容，风险更大。

## 9. 第 5 项落地：机器人流程独立文件（2026-10-23）

### 9.1 改动

- `RobotProgramPanel`：节点列表底部、「🗑 删除选中」右侧新增「💾 保存流程」
  （`robot_program_save`，与删除同尺寸，非危险色）。`onSaveProgram()`：
  - 无控制器或流程为空 → toast 提示，不弹文件框；
  - 默认目录 = 上次保存/导入目录，否则「文档」；默认文件名
    `<流程名>.program.json`（流程名里 `\ / : * ? " < > |` 换成 `_`）；
  - 过滤器 `机器人程序 (*.program.json);;所有文件 (*.*)`；
  - 走 `RobotProgram::saveToFile`（UTF-8 JSON，`kProgramJsonVersion=1`），
    成功/失败都写 toast 与操作日志，失败不改变当前流程。
- `SettingsDialog`：新增「机器人流程」组，内含「导入流程...」+ 状态文案。
  选择文件 → 二次确认「导入将替换当前流程」→ 调用控制端注入的
  `ProgramImportFn`；失败在对话框内显示原因（含"程序正在运行，请先停止"），
  成功后显示「已导入：<流程名>：N 个节点」。
- `RobotProgramController::setProgram(program, error)`：运行中拒绝导入，
  否则交给 `ProgramRunner::setProgram()`（它会发 `programChanged`，
  面板按稳定节点 id 刷新并保持选中）。
- `MainWindow::showSettingsDialog()` 注入导入实现：
  `RobotProgram::loadFromFile` → `setProgram` → 写操作日志 →
  `ToolsPanel::showRobotProgramPage()` 切到控制台页，导入结果立即可见。
- 导入立即生效，和「从备份恢复」一致，不等对话框的「确定」。

### 9.2 人工验收清单（UI 不做自动化）

1. 打开机器人控制台：节点列表底部「💾 保存流程」紧贴「🗑 删除选中」右侧，
   两者等高、保存按钮不是红色。
2. 流程为空时点「保存流程」→ 顶部 toast 提示流程为空，不弹文件框。
3. 添加几个节点 → 点「保存流程」→ 文件框默认名 `<流程名>.program.json`；
   保存后 toast 成功、操作日志有记录，文件存在且可读。
4. 关闭程序重开 → 控制台节点为空（预期：流程是独立文件，需要手动导入）。
5. 打开「设置」→「机器人流程」→「导入流程...」→ 选上一步的文件 →
   确认替换 → 对话框显示「已导入：…N 个节点」，并且界面切到控制台页，
   节点表与保存前一致。
6. 导入一个非 `*.program.json` 的普通 JSON → 对话框内显示导入失败原因，
   当前节点表不变。
7. 流程正在运行时导入 → 提示「机器人程序正在运行，请先停止后再导入。」，
   节点表不变。
8. 在文件框点「取消」→ 不提示、不改变任何状态。
