# 阶段 13 — 预览「停在某一帧一会又好了」的排查，以及机器人读取侧同一类问题

> 现场环境：I2120（序列号 I1GM112B652）+ VM 里的 UR 虚拟机器人（192.168.0.37）。
> 用户报告：**预览开着、时间够久，视窗会卡顿 —— 停在某一帧一会儿，然后又正常。**
> 本轮**只本地验证，不打包**（用户明确：等他说话再打包）。

---

## 1. 结论先说

| # | 成因 | 是不是现场看到的那个 | 处理 |
|---|---|---|---|
| **A** | **无操作暂停预览**（默认 60 s 闲置 → 主动停掉取流把相机让出去） | **主因。** 时长触发、画面冻在一帧、有任何输入立刻恢复 —— 三个特征全中；而且**在此之前界面上完全不显示**，按钮还写着「停止预览」 | **已修**：画面中央显示「预览已暂停」浮层 + 操作日志留一行 |
| **B** | 3D 视窗里的操作**不算"有操作"** | 帮凶。Vis 的 OSG 子窗口是本机(alien) HWND，鼠标消息进不了 Qt 事件过滤器 → 在 3D 里转点云/滚轮缩放 1 分钟，仍被判为无操作，于是 A 被触发 | **已修**：1 Hz 光标位置轮询，光标动过就算有操作 |
| **C** | UI 线程被别的活占住 | 有可能，但**已有埋点**（`[WATCHDOG] UI stall`） | 不动，只在文档里对齐判别方法 |
| **D** | 预览在等设备锁（让位给拍照/总线扫描） | 有可能，**已有埋点**（`[DEV] … acquired device after N ms`，≥50 ms 才记） | 不动 |
| **E** | **相机/SDK 这一次调用本身就慢** | **原来完全没埋点** —— 这一格空白正是"只能猜"的原因 | **已补埋点**：`[PREV] slow round` / `[PREV] frame gap` |

一句话：**主因是 A（外加 B 让它更容易发生），E 因为缺埋点无法在日志里自证，这次一并补上。**
先把"能看到"补齐，再靠现场日志把 C/D/E 彻底定性 —— 不靠猜。

## 2. 排查过程（为什么是 A，而不是别的）

### 2.1 先看症状的形状

- **"时间够久"** → 触发条件是**时长**，不是数据量、不是帧号、不是某张图。代码里所有跟时间挂钩、又会停住画面的东西只有一条：`idle_pause_preview_sec`（默认 60）。
- **"停在某一帧"** → 不是黑屏、不是错误画面，是**最后一帧留在那里**。主动停掉取流的典型样子（`stopPreview()` 只是不再投递新帧，画面上那一帧不会消失）。
- **"一会又正常"** → 没有点任何按钮就恢复，说明恢复是**自动**的。`onUserActivity()` 正是"任何输入即 `resumePreview()`"。

三条对上同一条路径。

### 2.2 逐条排除（都有证据，不是感觉）

| 怀疑对象 | 证据 | 结论 |
|---|---|---|
| 浮层毛玻璃（每帧重算模糊）拖慢渲染 | T-010 实测 `[OVERLAY] per_frame_us` 中位数 **148.8 µs/帧**，`frames=N` 也说明帧率正常 | 排除 |
| 健康巡检与预览抢相机 | `onHealthTick()` 在预览中直接早退（不占用设备） | 排除 |
| 日志膨胀拖慢 | `LogManager` 有上限；每帧日志本身有节流 | 排除 |
| 像素转换 `rvcToQImage` 悬垂/深拷贝 | 深拷贝，无悬垂 | 排除 |
| 视窗重绘被自己拖住 | 无 `[WATCHDOG] UI stall`、无 `[UI] Image2DView::render` 长耗时（现场日志） | 排除 |
| Qt 不投递 hover 移动事件（我以为的另一个坑） | 读 Qt 5.14.2 源码：`qwindowsmousehandler.cpp` 只在**无按键且位置未变**时丢弃 WM_MOUSEMOVE；`qapplication.cpp::pickMouseReceiver` 只在 `MouseMove && buttons` 时返回 0；`qwidget.cpp` 无条件派发 MouseMove | **推翻**，Windows 上 hover 是投递的 |

### 2.3 真正的盲区：3D 视窗是本机(alien) HWND

`src/ui/VisSceneView.cpp:379` 用 `SetParent(d->visHwnd, viewport->winId())` 把 Vis 自己创建的
OSG 子窗口塞进 Qt。**那个 HWND 不是 Qt 建的**，它的鼠标消息按定义不进 Qt 的事件过滤器 ——
所以在 3D 视窗里操作不产生任何一种"用户活动"，60 秒到点照样暂停。

这条与 A 叠加，解释了"为什么在别的测试机上更容易看到"：那台机器上的人更多是在 3D 视窗里看/转点云。

## 3. 改动清单

### 3.1 让"暂停"自己说出来（A）

| 文件 | 改动 |
|---|---|
| `src/ui/Image2DView.{h,cpp}` | 新增 `setPreviewPausedHint(bool, int idleSec)`：画面正中浮层「预览已暂停（无操作 N 秒）／移动鼠标或按任意键继续」，复用既有毛玻璃浮层组件（与缩放标签同一套观感）；`resizeEvent` 重新居中并 `raise()`；`clear()` 里撤掉 |
| `src/app/MainWindow.cpp` | `onIdleTimeout()` 显示该提示 + 往**操作日志**写一行「预览已暂停（无操作 60 秒，相机让给其他工具）；移动鼠标或按任意键恢复」；`onUserActivity()` / 相机断开 / 拍照前 `stopPreview()` / 设置里关掉该功能 —— 四处都撤掉提示 |

要点：暂停是**设计行为**（把相机让给别的工具），不是缺陷。之前的缺陷是它**没说自己停了** ——
现场只能看到"画面不动了"，与程序卡死完全同形。

### 3.2 光标位置轮询（B）

| 文件 | 改动 |
|---|---|
| `src/app/MainWindow.{h,cpp}` | 新增 `m_activityPoll`（1 Hz `QTimer`，`Qt::CoarseTimer`）+ `m_lastCursorPos`；位置变过就调 `onUserActivity()`；新增 `armIdleDetection(bool on)` 统一"装/卸事件过滤器 + 起/停两个定时器"，替掉原来散在 4 处的 `m_idleTimer->stop()` / `removeEventFilter` |

开销：每秒一次 `QCursor::pos()`，可忽略。收益：**"无操作"判定不再依赖"事件是否进得来 Qt"**，
alien HWND、原生弹窗、甚至别的进程挡住光标，都能被覆盖。

### 3.3 把"相机自己慢"这一格补上埋点（E）

`src/logic/CameraManager.{h,cpp}`：`PreviewFrames` 新增 `roundMs`（worker 里用 `QElapsedTimer` 量
"设备锁等待 + SDK 采集 + 像素转换"整轮的墙钟时间），UI 线程里据此出两行日志：

- `[PREV] slow round <ms> ms (timer=… failures=… gen=…)` —— 单轮 ≥ **500 ms**（正常一帧 30~60 ms）
- `[PREV] frame gap <ms> ms (timer=… paused=… failures=… gen=…)` —— 两帧间隔 ≥ **1000 ms**

两个阈值写在文件顶部一处常量（`kPreviewSlowRoundMs` / `kPreviewLongGapMs`）。
`startPreview()` / `stopPreview()` 都会把 `m_lastPreviewFrameMs` 归零，**故意的停止/重启不会被误报成卡顿**。

### 3.4 现场 20 秒判别法（交给现场用）

画面停住时**不要点**，先看 `logs/runtime_*.log` 的最后几行，谁在就是谁：

| 日志行 | 含义 | 怎么办 |
|---|---|---|
| `[CAM] preview paused after 60 s idle` | **我们自己暂停的**（就是本轮主因） | 动一下鼠标即恢复；界面现在也会写着 |
| `[WATCHDOG] UI stall …` | UI 线程被别的活占住 | 看同一行的「最近重活=」 |
| `[DEV] preview-x1 acquired device after N ms` | 预览在等设备锁（拍照/总线扫描占着） | 看 N 有多大、当时是不是在拍照 |
| `[PREV] slow round N ms` | 相机/SDK 这一轮自己慢 | 再看它上面那行 `[DEV]` 判断是锁还是 SDK |
| `[PREV] frame gap N ms` | 压根没在投帧 | 结合 `paused=` 字段区分"停了"还是"哑了" |
| 预览连续失败 ×20 | 相机掉了 → 自动重连 | `[CAM] camera error` 附近 |

## 4. 其他机器人读取侧：UR 上发现过的问题有没有重复

用户问的是："UR 优化得差不多了，其他机器人会不会有同一类问题。"
把 UR 那两类已被现场证实的缺陷（**① 全 0 位姿被当成 Ok 返回 ② 非有限值被当成 Ok 返回**）逐个 reader 对照：

| Reader | 全 0 位姿 | NaN/Inf | 本轮处理 |
|---|---|---|---|
| `URRealtimeReader`（实时口 30003） | 已拒绝 | 已拒绝 | **一行未动**（它是基准） |
| `URRtdeReader`（RTDE） | 已拒绝 | 已拒绝 | **一行未动** |
| `ModbusTcpReader` | **会静默接受** | **会静默接受** | **已修** |
| `NrcJsonReader`（博纳斯/纳博特） | **会静默接受** | **会静默接受** | **已修** |
| `EfortReader`（埃夫特 SDK） | **会静默接受** | 由 `normalizePose` 挡住 | **已修** |

**修复方式**：把 UR 那条规则提到**共用一层**，避免以后再各写一份。

- `src/logic/RobotPose.h` 新增 `enum class PoseSanity { Ok, NotFinite, AllZero }` +
  `checkPoseSanity()` + `poseSanityText()`（判据与文案的唯一出处）。
- `RobotPose.cpp`（Modbus）：解出 6 个数之后先过判据，不过就 `ProtocolError`，文案后缀带上起始地址
  「（Modbus 起始地址 N，请核对机器人的寄存器表）」。
- `NrcJsonReader.cpp`：新增 `poseFromArray()` = `arrayToPose()` + 判据。**关键一点**：
  失败时**继续试下一个候选字段**（理由只记第一次），所以"某个字段恰好全是 0"不会掩盖真正的位姿字段 ——
  该文件的候选字段列表本来就宽（`posValue/currentPos/realPosMCS/…`），这条不变量必须保住。
  另外 `out` 只在**全部通过后**才赋值，失败路径不动调用方现有的位姿。
- `EfortPoseReader.cpp`：SDK 调用返回成功、结构体里却是 6 个 0 —— 恰是"没读到/读错对象"的样子；
  判据不过即 `ProtocolError`，文案带上 x/y/z/a/b/c 实际值。

**为什么这条值得修**：全 0 位姿不会报错、不会红，它会**安静地写进卡片**，最后变成一次"成功但偏掉"的标定 ——
这与阶段 7 那个"轴角当欧拉读"是同一类静默错误，也正是 UR 现场踩过的坑。

### 4.1 看出来了但**故意没改**的（缺现场证据，按项目规矩不动）

| 项 | 为什么不动 |
|---|---|
| Modbus MBAP 的 transaction id / protocol id / length / unit id 未做校验 | 属加固，不影响当前可用性；真机跑通优先 |
| NRC 的候选字段"猜名字"，可能命中一个 6 元素的关节角数组 | 应答 schema 未与真机核对；日志已 dump 原文，等现场一次真实应答再定 |
| NRC / 埃夫特的单位与 schema 未经真机确认 | 同上 |
| 埃夫特缺 keepalive / 超时 | 需要真机行为作依据 |

新增测试的两个细节：

- `zeroPoseIsRejected` 还断言 **失败时 `out` 不被改写**（先塞一个哨兵位姿，再解析 `[0,0,0,0,0,0]`）。

  所以断言的是结果而不是具体文案。`NotFinite` 分支本身由 `poseSanityPredicate` + Modbus 的 NaN 用例覆盖。
  埃夫特侧 `readPose()` 需要厂商 SDK DLL，不进单测（判据已由上面两条覆盖）。

## 6. 用户手动复测清单

**A. 暂停提示（核心）**

1. 连接相机 → 开始预览 → **手不要碰鼠标键盘**，等 60 秒。
   - 预期：画面正中浮层出现「预览已暂停（无操作 60 秒）／移动鼠标或按任意键继续」。
   - 预期：操作日志（界面日志窗 + `logs/app_*.log`）出现「预览已暂停（无操作 60 秒…）」。**以前这里是空的。**
   - 预期：**画面不再像卡死** —— 有明确文字说明为什么不动。
2. 动一下鼠标（或按任意键）→ 预期：提示立刻消失、预览继续出帧、日志出现
   `[CAM] preview resumed (user activity)`。

**B. 3D 视窗操作算不算"有操作"（这次一起修的）**

3. 开始预览 → 进入 3D 视窗，**只在 3D 里**转点云/滚轮缩放（鼠标始终在 3D 视窗内，全程 70 秒以上）。
   - 预期：**不会**出现「预览已暂停」；预览一直在出帧。
   - （修复前：这里会到点暂停 —— 因为 3D 的 alien HWND 消息进不了 Qt。）

**C. 埋点（给下一步定性用）**

4. 预览正常时翻 `logs/runtime_*.log`：预期**没有** `[PREV] slow round` / `[PREV] frame gap`。
5. 如果现场再遇到"停在某一帧"：**先别动鼠标**，把最后 20 行 runtime 日志留档，
   按第 3.4 节的表对照 —— 这一次必须能落到**某一行**上，而不是继续猜。

**D. 机器人读取（改了三个 reader）**

6. UR 虚拟机器人（192.168.0.37）：**行为应与之前完全一致**（两个 UR reader 一行未动）。
7. Modbus / 博纳斯 / 埃夫特：正常读到非零位姿时**照旧工作**；若地址写错读到全 0，
   预期界面报错并写明「六个分量全为 0，不是真实位姿（很可能是地址/字段错位）」，
   **不再**安静地写进卡片。
