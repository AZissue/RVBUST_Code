# 阶段 25（3.0）— 各品牌运动能力补齐方案

> 2026-10-31。来源：用户提问「博纳思和埃夫特的也是提供的 SDK 的，为什么也是只能读位姿，
> 法奥的也是为什么不支持程序运动？这些应该都要支持的。先说下当前的算法逻辑，
> 再说说是否可以实现？出个方案」。
>
> **当前状态：方案已定、实施暂缓**。2026-10-31 用户答复：① 博纳斯
> `nrc_host.dll` 可随绿色包分发；② 暂无埃夫特/博纳斯真机，也没有厂商手册，
> 「可以先留着」。因此本文只记录能力模型、逐品牌可行性证据与分阶段方案，
> **不落任何运动代码**——运动指令的单位/欧拉约定/权限语义无法在无真机、
> 无手册的情况下验证，写出来只会是"看起来支持、现场一按就错"的不可验证代码。

---

## 1. 当前能力模型（代码实际逻辑）

### 1.1 一个品牌一个后端对象 + 一个布尔能力位

所有品牌都实现 `RobotMotionBackend`，UI 与程序执行器只看两件事：

- `supportsMotion()` —— 这个品牌能不能运动；
- `moveCartesian() / moveJoint() / jogCartesian() / jogJoint() / stopMotion()`。

Modbus / 博纳斯 / 埃夫特 三个品牌共用 `logic/PoseOnlyMotionBackend`，能力位写死为假：

```cpp
bool supportsMotion() const override { return false; }   // PoseOnlyMotionBackend.h
```

由此形成闭环：

1. `RobotProgramPanel::applyBackendCapabilities()`（`RobotProgramPanel.cpp:1863`）
   读到 `poseOnly` → 隐藏模式切换/控制盘/步长/速度+使能/「添加移动」，显示一行
   「只支持读取位姿」提示；拍照/等待节点仍可加（`onAddPhoto/onAddWait` 的守卫
   改成 `(!m_enabled && !poseOnly)`）。
2. 运行列表里混进移动节点 → `RobotProgramController.cpp:359` 调
   `moveCartesian()` → `refuseMotion()` → `motionFinished(false, "…只支持读取位姿")`，
   **明确失败，不静默跳过**。

「只能读位姿」是合并那次划定的实现边界，不是硬件能力判断。

### 1.2 为什么这三个品牌当时被套成只读

| 品牌 | 合并前已有的 | 缺的 |
|---|---|---|
| Modbus TCP | `ModbusTcpReader`：按寄存器读 6 个 float/int32 | 通用运动寄存器协议（寄存器表是客户自定义的）→ **这一类是真做不了** |
| 博纳斯 (NRC) | `NrcJsonReader` 自实现 4 条读命令（0x2002/0x2202/0x2F07/0x7012），帧格式由官方 SDK 抓包验证 | 运动命令号与应答 schema 未确认（当时 324 组候选字段全 `RECEIVE_FAILED`）；原设计为绿色包**不引入厂商 DLL** |
| 埃夫特 (Efort) | `EfortReader`：仅 `ConnectRobot` + `GetBaseCoordinatePos`（mm/度），头文件故意不含 SDK 头 | 没有运动分支：`EfortPoseReader.h` 明写「只实现 `RobotPose::Reader`」 |

### 1.3 法奥的实际情况（用户前提是误会）

法奥是**完整运动后端**：

- `FairinoMotionWorker::moveCartesian()` → `MoveL`（`FairinoMotionBackend.cpp:591`），
  `moveJoint()` → `MoveJ`（`:606`）；速度百分比、`blendR = -1` 到位停、
  发指令前先 `GetInverseKin` 解逆解、工具/工件号取 20004 当前值；
- 程序列表的移动节点就走它（`RobotProgramController.cpp:359`）；
- 运动前有 `ensureReady()` 四重门（`FairinoMotionBackend.cpp:318` 起）：
  已连接 → **已上使能**（`RobotEnable(1)` 且 20004 `rbtEnableState`）→ 20004
  位姿 1 s 内新鲜 → 无故障码（`mainCode/subCode == 0`）。

现场"法奥不支持程序运动"最可能是撞在这几道门上（只连接没使能 / 有故障码未复位 /
20004 被防火墙挡），或把**步进式点动**（短距 `MoveL` + 松手 `StopMotion`，`:447`）
理解成"不支持运动"。真正缺的是**连续点动**（阶段 24 报告 §5 的 P3）。

## 2. 可行性结论（逐品牌证据）

| 品牌 | 点动 | 目标位姿 / 程序节点运动 | 厂商接口证据 | 结论 |
|---|---|---|---|---|
| UR | 已有（步进） | 已有 | — | 已支持 |
| 法奥 | 已有（步进），缺连续点动 | **已支持**（MoveL/MoveJ） | `FairinoMotionBackend.cpp:591/606` | 补连续点动 + 模式/门限提示 |
| 埃夫特 | 可做，且是**原生连续点动** | 可做 | `EfortSdk.h`：`Jog1Plus(bool flag)`…`Jog6Minus`、`MLIN(double pos[], int speed)`、`MJOINT`、`MOVEHOLD()`、`GetMoveState(bool&)`、`WaitCartPosition(RobotPos, accuracy)`、`EnableApiControl`、`GetCurrentServoStatus`、`SetJogMode` | **可行，成本最低** |
| 博纳斯 (NRC) | 可做 | 可做，**只能"作业(job)"方式** | `nrc_interface.h:520/527` `robot_start_jogging/stop_jogging`；`nrc_job_operate.h:181/189` `job_insert_moveJ/moveL`；`set_servo_poweron`、`set_current_mode`、`clear_error`、`set_speed` | **可行**，路线 A（DLL）/ B（自实现协议）|
| Modbus | 不行 | 不行 | 无标准运动寄存器 | 保持只读 |

`Jog1Plus(true/false)` 与 `robot_start_jogging/stop_jogging` 都是"按下/松开"语义，
正好对应报告 §5 设想的 `jogStart/jogStop`——**埃夫特、博纳斯做连续点动比 UR 更容易**。

## 3. 方案

### 3.1 能力矩阵（替代单一布尔）

```cpp
struct MotionCapabilities {
    bool move    = false;   // moveCartesian / moveJoint（移动节点）
    bool jog     = false;   // 单步点动
    bool jogHold = false;   // 按住连续点动（jogStart/jogStop）
    bool enable  = false;   // 需要"上使能"这一步
};
virtual MotionCapabilities capabilities() const;
```

- `supportsMotion()` 保留为 `capabilities().move || capabilities().jog` 的兼容入口；
- UI 从"整块运动区显隐"细化为逐项显隐，提示文案点名缺哪一项；
- 运行列表遇到不支持的移动节点仍然明确失败（语义不变）。

新增两个后端，沿用 `PoseOnlyWorker` 的线程模型（私有 `QThread` + 轮询 +
`BlockingQueuedConnection` 析构）：

```
logic/EfortMotionBackend.{h,cpp}   // 埃夫特：读+写共用同一个 SDK 会话
logic/NrcMotionBackend.{h,cpp}     // 博纳斯：读走现有 JSON 帧，写走 job/jog
```

### 3.2 P1 — 埃夫特（先做，收益/风险比最高）

- 新增 `logic/EfortCommand.h`：纯函数拼 `MLIN/MJOINT` 参数，可单测；
- worker 线程：`ConnectRobot` → `EnableApiControl(true)`（取控制权）→
  `GetCurrentServoStatus`，未上电则 `PowerOn`（**只在用户点"使能"时执行**）；
- `moveCartesian` → `MLIN(pos, speed)`；`moveJoint` → `MJOINT(joints, speed)`；
  `stopMotion` → `MOVEHOLD()`；
- 到位判据：50–100 ms 轮询 `GetBaseCoordinatePos` / `GetJointPos`，与目标比
  容差，配 `settleTimeoutMs`；超时 → `motionFinished(false)`；
- 连续点动：`SetJogMode()` 切坐标 + `Jog{n}Plus(true)` 起、`(false)` 停；
- 风险：`EnableApiControl` 会夺走示教器控制权，UI 必须写明；`log4cpp.conf`
  已随包部署（绿色包既有约束）。

### 3.3 P2 — 博纳斯（用户已批准路线 A：随包带 DLL）

- 链接官方 `nrc_host.lib/.dll`（`.codex-loop/bonas-probe` 已有 msvc2017/2022 版本，
  此前验证可编译可链接），按埃夫特的方式部署到 `third_party/NRC/bin` → exe 旁边；
- 点动：`robot_start_jogging(axis, dir)` / `robot_stop_jogging(axis)`；
- 移动节点：`job_create → job_insert_moveL/moveJ → job_run → job_stop`（临时作业，
  名字固定，跑完删除）——这就是字面意义的"程序运动"；
- 使能：`set_servo_poweron` / `set_current_mode` / `clear_error`；
- 备选路线 B（不落）：继续用探针 + mock 服务器抓 `send_message` 的运动命令字节，
  保持无 DLL；成本约为 A 的两倍，留作将来"去 DLL"优化。

### 3.4 P3 — 法奥补齐

- 程序运动已通，把"使能 / 无故障码 / 20004 新鲜"三条前置条件显示在运动区旁边，
  而不是只出现在日志与 toast；
- 可选：解析 20004 模式位，非自动模式时提前提示，而不是等 `MoveL` 被拒；
- 连续点动：优先 `StartJOG/StopJOG` 或 `ServoMoveStart + ServoCart/ServoJ`，
  退化方案为现有"短距 MoveL + 松手 StopMotion"。

### 3.5 P4 — UI / 文档 / 测试

- `applyBackendCapabilities()` 按能力矩阵逐项显隐；
- 帮助页「机器人控制」章节按新矩阵重写（现在写的是"UR/法奥有运动，其余只读"）；
- 单测：`efortCommandParams`（数组长度/单位/速度夹取）、`nrcJobFrames`（若走 B）、
  `capabilityMatrix`（每品牌能力位 + `supportsMotion()` 兼容值）；
  `poseOnlyBackendRefusesMotion` 收窄为"只有 Modbus 拒绝"；
- 双工作区构建 + ctest 全绿，本地提交。

### 3.6 安全与失败关闭（不可让步）

- 使能是唯一进入运动态的入口；断开 / 切品牌 / 关窗一律先 `stopMotion()` 再下使能；
- 运动指令只在后端 worker 线程发出，UI 线程只发信号；
- 到位判据 + 超时 + `motionFinished(false)`；失败不进入下一节点；
- 拍照节点继续要求"无在途运动 + 位姿新鲜"。

### 3.7 工作量

| 阶段 | 内容 | 估时 |
|---|---|---|
| P1 | 埃夫特运动后端 | 2–3 天 |
| P2 | 博纳斯（路线 A） | 2–3 天 |
| P3 | 法奥连续点动 + 门限提示 | 1–2 天 |
| P4 | UI/文档/单测/双工作区 | 1–2 天 |

## 4. 实施前必须确认的厂商细节（现场核对清单）

无真机、无手册时**不写运动代码**，解冻前先拿下列事实：

**埃夫特**

1. `MLIN/MJOINT` 的 `pos[]` 长度：6 元，还是需要带 cfg（`cfgx/cfg1/cfg4/cfg6`）的 10 元；
2. `speed` 单位：`MLIN` 为 mm/s、`MJOINT` 为百分比——需手册或示教器对照确认；
3. `RobotPos.a/b/c` 的欧拉约定（内旋/外旋、轴序），必须与卡片约定一致，否则标定数据错 90°；
4. `Jog{n}Plus(flag)` 的 flag 语义（true=按下、false=松开）与 `SetJogMode` 的取值表；
5. `EnableApiControl` 是否需要示教器侧授权/钥匙开关状态，`PowerOn` 是否可重复调用。

**博纳斯**

6. `MoveCmd.coord` 取值（关节/直角）、`targetPosValue` 7 元含义、`velocity` 单位、`pl` 平滑、
   `configuration` 形态位；
7. `job_run` 之后的完成判据：`get_robot_running_state` 轮询还是 `job_get_current_line`；
8. `robot_start_jogging(axis, dir)` 的轴编号（1–6 还是 0–5）与方向语义；
9. `set_current_mode` 的模式值（手动/自动）与 `set_servo_poweron` 的前置条件。

**通用**

10. 运动时是否必须在"自动模式"；软件退出/断连时后端的兜底停止是否生效。

以上任一项未定就上代码，等于把"未验证的单位/约定"直接写进现场运动指令，
是本项目明确要避免的失败模式（参见圆圈真值回归的教训）。

## 5. 解冻条件与回退

- **解冻条件**：有埃夫特或博纳斯真机可联调（至少一台），或拿到厂商手册中
  `MLIN/MJOINT` 与 `MoveCmd` 的字段定义。届时按 P1 → P2 → P3 → P4 顺序推进，
  每阶段单独提交并附真机验证记录。
- **回退**：新增文件独立；工厂分支切回 `PoseOnlyMotionBackend` 即回到当前行为。
  只读路径（`EfortReader` / `NrcJsonReader`）不改动，最坏情况退化为
  "读位姿 + 明确拒绝运动"，不会引入静默错误。
